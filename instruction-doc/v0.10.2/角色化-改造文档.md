## 1. 背景与评估结论

**评估结论：合理。** 依据 = 确认单 §3 的 **6 份单元只读取证**（`ec4f5cf7` / `e98e8649` / `cf99f8a9` / `0952d59c` / `925922fa` / `1841c534`）+ 本文件 §2 的三轮边界确认。

**四条事实订正（实现前的口径校准，全部来自单元核实）**

1. **`model` / `mode` / `systemPrompt` 的「下发」本来就是会话级**（`session/set_config_option {sessionId, configId:"model"}`，new/load/resume 三路都 set）⇒ 要改的是**值来源**（构造器 → per-request）；**真正不可降的只有 `agentKind` / `backendCmd`**（桥进程的命令本身）；`risk` 半可降（权限处理器进程级单注册，但 `session/request_permission` 带 `sessionId` ⇒ 可加路由）。
2. **会话复用机制现成**：`contextId` 两个生成点都是「调用方传入即沿用」⇒ orch **零改动**即可支持「同（需求, step, project）复用」；纪律而非代码。
3. **`task_type` 在 orch / machine 两侧源码零命中** ⇒ 本版新维。
4. **`metadata` 全仓零命中**（`PROTOCOL.md` 与两侧代码均无）⇒ 它是**新载体**，非既有通道（决定 §2.3 的 F-M2 分层）。

**无新依赖、不动主链**：不碰 Step 0–3 主链 / 两道确认门 / DAG 派发 / 调度串行语义；协议 `PROTOCOL_VERSION` 保持 **2.3** 不升。

## 2. 方案设计

### 2.1 一句话方案

**职责位 = 派发属性（`taskType`），不是会话身份。** `taskType` 随派发链透到 machine，由 **machine 本机的 `agentConfig.roles` 映射**决定该次会话的 **`model` / `systemPrompt` / `mode` / `risk`**（四旋钮，per-request 覆盖）；会话按「需求 × step × project」**复用**（**多轮续接传同一 `contextId`**；不传则新起）；**PjM 定版本 = 改造方案确认之后的一道工序，结论经既有归属写口落库（不由 PjM 自行写库）**。

## 4. 验收标准

1. **`taskType` 端到端**：`a2a_call(taskType="dev_manager")` → 落 `tasks.task_type` → `toDispatchCommand` 顶层透传 → machine `metadata` → **`agentConfig.roles.dev_manager.model` 真生效**；不传 ⇒ `unit_agent`；非法值 ⇒ **结构化拒绝**且**进任务终态可见面**（token `unknown_task_type=<原值>`，禁造 `failureKind` 第 7 值）。
2. **四 kind 真机探针（F-N1）**：≥ 8 枚断言（四 kind × `model` / `systemPrompt`）+ 1 枚全 kind 真机；**判据事实源 = `a2a_task_status` 结果文本**；**不得只离线断言**。
3. **会话复用（F-C3）**：同一（需求, step, project）内的**多轮续接同一 `contextId`**（**正常用法，非可选**）且**拿到该职责位首轮注入的 `systemPrompt`**；**换职责位 / 换 project / 换需求 ⇒ 另起**；**同一 step 内的并行节点不共享**（各起一条会话线）；`retryTaskIds` / `answer` 语义不变。
4. **PjM 工序（F-C5）**：`approve` 后**不落**归属初版 ⇒ PjM 出**版本规划评估** ⇒ 用户确认 ⇒ **先 `POST /api/project-versions` 建版 → 再 advance 写归属** ⇒ 版本经 `feature_projects` 可读；**PjM 不自行写库**。
5. **板零回归（F-C10）**：板两处写面调用（create / advance 排期特例）**未被新入参打断**；`a2a_tasks` 扩字段不触发板解析错误。
6. **配置兼容**：**存量全部 `config.json*` 过校验**（`roles` 收窄范围后）；
7. **自检**：只跑 `unit_agent`（真跑 1 条）；其它职责位**配置级校验**有产出。

## 5. 风险面（**推断，非实测**）

- **写档职责位 + 自检**：角色 `systemPrompt` + write 档 + 权限自动放行下，模型可能被话术引向动手 ⇒ 自检或留脏工作树（**推断、无实测**，已登记 §6）。
- **`agentConfig` 两套语义并存**（`roles` 子对象 fail-closed vs 顶层静默忽略）⇒ 后人易误判为不一致。
- **混跑期静默错配**：`machine 先升、orch 后升`为前置；反序部署会出现「配了不生效」且无告警。
- **前瞻约束（F-前瞻）**：**闭集成员扩员 = 协议升版事件**（按 `需求流程.md` §7「变更取值集合成员 ⇒ 升版」）—— 组级角色卡落地时**不得再按「加个可选键」处理**。

### 用户追加要求（2026-10-10）—— **原则：任务始终由研发经理制定**（含**二次拆分**）

**原话**：「如果第一次任务拆分后，执行上还是会出现超时情况，涉及到**二次拆分任务**，那么**还需要由研发经理介入**（也就是**任务始终是由研发经理制定的**）」。

**⇒ 原则落成一句**：**节点的产生与再切分（一次拆分 / 执行期二次拆分）一律由该 project 的研发经理制定；宿主只做「收敛 + 登记 + 贴用户」，不新增 / 不删除 / 不合并 / 不拆小任何节点。**

**由此细化的四条**

1. **会话线模型（每 `(需求, project, 职责位)` 一条线，长期存活）**：研发经理线 = Step 1 边界轮那条 ctx（R1–R3 续用）⇒ **Step 2 一次拆分续用** ⇒ **执行期二次拆分仍续用同一条**（同角色 ⇒ 复用安全，machine 已证）。与**执行节点各起全新 session**（规则③）**并行共存**：同 project 上同时存在「1 条研发经理线 + 各执行节点各自的线」。
2. **二次拆分的形态与触发判据（必须写死，否则会退化成「每次都拆」）**：触发 = **该节点满窗（`timeout`）且（无实质产出 ∨ 续跑后仍满窗）**，或**同节点第二次仍失败**（既有 playbook）。**判定方 = 宿主**（读账面），**拆分方案 = 研发经理**。
   - ⚠ 与既有超时纪律的边界：`timeout` ∧ `timeoutScope=acp-prompt` ∧ 有产出 ∧ 余量 > 0 ⇒ **machine 自动续跑一次**（不归宿主）⇒ **二次拆分只在其后仍不成立时启动**，不得抢在续跑之前。
3. **宿主「只反馈、不改任务」**：宿主若认为某节点体量不当（过大 / 过小），**只能把判断反馈给该 project 的研发经理**，由研发经理重出清单；**宿主不得自行拆小或合并**（{这样才与「任务始终由研发经理制定」自洽}）。⇒ 「单节点约 10 分钟」的窗口纪律**仍是宿主把门，但把门手段只有「反馈 + 退回研发经理」**。
4. **必须容忍「复用失败」**：`SessionMap` 有 TTL/prune（默认 7 天）、Launcher 重启亦会丢运行时；复用失败 ⇒ machine 回落 `new`（全新会话、重新注入）⇒ **正确性不受影响、只是失去上下文** ⇒ 纪律不得把「必须复用成功」写成硬判据。

**⚠ 待核实（已派 orch `c5226bc4`，product_manager 出场）—— 二次拆分能否落地取决于这条**：**引擎侧「一大节点拆成 N 个小节点」怎么表达**？具体未知：① 已 `failed` 的节点**如何处置**（有无「取消单节点」的工具）；② **`failed` / `cancelled` 节点会不会永久挡住 Feature 收口**（`executing → integrating` 的收敛判定读哪个状态集合、是否要求全部 `completed`）；③ 节点**能否删除**；④ 新增节点**能否依赖一个 failed 节点**（v0.10.1 踩过跨 Feature 依赖 ⇒ DAG 悬空 ⇒ 67ms fail-fast）。**核实回来前，(b) 的落实方案不写死。**

**⚠ 核实结论（orch `c5226bc4`，product_manager 出场）—— 二次拆分目前【无引擎支撑】，且与「谁拆」无关**

- **收敛判据硬要求全部 `completed`**：`reduceConvergence`（`bridge/scheduler.ts:494-502`，判定点 **`:498`** `every(n => n.state === "completed")`）⇒ 一个 `failed` 节点**永久卡住** `executing → integrating`，Feature 停在 `executing` **静止**（`featureAtRest` `:967-973` ⇒ `reportFailureAtRest` `:873-876`）。
- **节点态闭集无 `cancelled` / `superseded`**：`TaskState = working | completed | failed | input-required | blocked`（`types.ts:70`；回传校验 `runner.ts:166-172`）。
- **`a2a_cancel(taskId)` 打不动 `failed` 节点**（`task_already_settled`，`index.ts:1531-1538`）；**`a2a_feature_cancel` 明确「不动节点账面」**（`feature-tools.ts:1802-1804`）。
- **没有删除节点的运行时口**：`store.ts` 节点级写口 `:5014/5019/5029/5075/5080/5085/5090/5168/5173` **全是 UPDATE、无 DELETE**（`DELETE FROM tasks` 只在 `pruneTasks` `:5507`）。
- **唯一可行形态**：原大保持 `failed` + 新增 N 小**依赖原大的上游**（不能依赖原大本身 —— 否则 `depStateOf` 走 `upstreamFailed`，`:256`，新节点永不 ready；而 `validateDag` `:1172-1198` 只看 id 存在、**不拦**）⇒ 新节点能跑完，但 **Feature 不能自动进 `integrating`**，只能**宿主强推 `advance(to=integrating)`**（引擎允许 `state-machine.ts:58` + `feature-tools.ts:1530`，**规范不认可**）。
- ⇒ **这是结构性缺口，不是 (b) 独有的**：**宿主拆也一样撞**（这正是 v0.10.0/v0.10.1 反复用「**cancel + 另立承接 Feature**」代替真正拆小的原因 —— `42cbd9db`→cancel→`31155242`、`3df58f98`→cancel→`c6fa6ff4`；代价 = 承接轨**不得挂跨 Feature 依赖**，否则 67ms fail-fast）。

**宿主建议（三档）**
- **不采纳 (A) 越位强推**：会留下「账面有 `failed` 而 Feature 已 `completed`」的**自相矛盾**，且破掉「`executing → integrating` 是引擎自动」这条唯一性 ⇒ 读账 / 验收 / 审计全受影响。
- **采纳 (b) 的「一次拆分」，把「二次拆分」另立卡**：已建 **`引擎原语：超时节点可被「拆小」消解（\`superseded\` 良性终态）`**（入需求池 · 未来版本；⚠ 按 `需求流程.md` §7「变更取值集合成员 ⇒ 升版」**极可能触发协议升版**，Step 0 须先裁「升版 / 不升版的表达」）。
- **过渡期两条兜底（零引擎改动）**：① 超时**优先走既有 `retryTaskIds` 重派**；② 确需拆小时**沿用既有 playbook**「cancel 相关轨 + 另立承接 Feature」（不挂跨 Feature 依赖）。二者与「任务由研发经理制定」不冲突：**清单仍由研发经理出，宿主只执行处置**。

**⇒ B-4 的裁法据此收窄为**：**(b) 用于「一次拆分」**（不动 Step 1 产物边界 + 照做前述四件要件）+ **「二次拆分」另立卡等引擎原语**；不是「(b) 含二次拆分」，也不是「(a) 全盘」。
