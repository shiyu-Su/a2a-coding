## §2 方案设计

### 2.1 主链 6 态 → 8 态（★用户）

```
waiting_approval → version_planning → decomposing → executing → integrating → testing → reviewing → completed
                    ↑ 新增·PjM        ↑ 新增·拆分
```

| 新 state | 进入 | 完成判据（可推进） | 驱动 |
|---|---|---|---|
| `version_planning` | `approve` 后 | 各 project PjM 结论收敛 + **归属落库**（先建 Project Version、再写归属） | 宿主 `advance` |
| `decomposing` | 上一态后 | 各 project 本侧任务清单回传 + **DAG 节点登记完毕** | 宿主 `advance` |

**位置硬约束**：两态只能在 `approve` 之后 —— 归属写口引擎判据要求 `approval=已通过` ∧ `version` 非空，二者只有 `approve` 后才可能成立。

### 2.2 `stage` 值域 5 → 6 且全启用（乙案，★用户）

`需求分析 → 改造方案 → 改造 → 回归 → 验收 → 发版`（新增「验收」）。

**半派生映射表（定稿 6 格，全态覆盖 —— ★R3 n1）**：

| state | stage | 派生方 |
|---|---|---|
| `waiting_approval` | `需求分析` / `改造方案` | **宿主写**（门①，两值不可由 state 决定） |
| `version_planning` | `改造方案` | **引擎派生**（approve 当轮） |
| `decomposing` | `改造方案` | **引擎派生**（出 version_planning 当轮） |
| `executing` | `改造` | **引擎派生** |
| `integrating` | `回归` | **引擎派生**（**仅宿主 `advance` 时** —— 引擎自动 `executing→integrating` 不经派生点，实测停 `改造`，见下「派生点覆盖面」与 §6） |
| `testing` | `回归` | **引擎派生** |
| `reviewing` | `验收` | **引擎派生** |
| `completed` | `验收`（发版后→`发版`） | 不派生（`发版` 宿主写） |
| `needs_input`/`failed`/`cancelled` | 保留当时值 | 不派生 |

**派生写形态**：引擎随 `state` 迁移**同轮派生写**（非宿主显式登记）；**不触发 §5 文档动作绑定**（不产生修订历史 +1、不要求搬文档）。映射表单源归 orch 代码，flow 不重述、board 不硬编码。

> **派生点覆盖面（v3 订正，2026-10-13）**：`deriveStageForState` 的**唯一调用点**是 `handleFeatureAdvance`（主链迁移之前）——**引擎自动迁移边不经该口**。本版由引擎自动迁移的边只有一条 = `executing → integrating`（`bridge/scheduler.ts` 经 `updateFeatureState` 直写 `state`，`grep stage` 零命中）⇒ 该格 `stage` **实测停在 `改造`**，随宿主 `advance(to="testing")` 才归 `回归`。故上表 `integrating` 行的「引擎派生」**应读作「宿主 `advance` 时派生」**（`O7` 专项断言即按此实测锁定）。要让引擎自动边也派生，须**另派节点**把派生点补进 `scheduler.ts` 的自动迁移路径 —— 本版未采（A/B 两案见 §6 遗留项）。

### 2.3 门① version 守卫（★用户）

门①（需求确认）触发时，引擎判 `features.version` 是否为空 ⇒ **空则结构化拒绝**（`feature_group_version_required`），**整单拒绝、零写入**（`state`/`stage`/`approval` 全不动）。

- **落点**：三条 advance 路径分叉之前的**单一早退点**（紧跟 `checkVersionWriteLocks`、`hasFeatureRegistration` 之前）。
- **判据**：`reg.patch.stage` 存在 ∧ `≠需求分析` ∧ 当前 `stage=需求分析` ∧ `version` 为空 ⇒ 拒。
- **被拒 ⇒ stage 仍 `需求分析`** ⇒ 排期锁仍开 ⇒ 补 version 重试。`stage`「需求分析→改造方案」**迁移留在门①**（★R3：撤回"迁移归门②"）。
- **不判 `state`、不校验 stage 迁移序**。

### 2.4 `create` 契约重构（★用户）

**移除 `a2a_feature_create` 的 `stage` / `approval` 两个入参**；create **硬编码初值 `stage=需求分析` + `approval=未发起`**（与板建卡现状一致）。

- **依据**：新流程「提需求即入板」⇒ 一切卡从 `需求分析` 起步，create 是纯构造器，不应能指定中间态。**化石来源**：`stage` 缺省 `改造方案` 是 v0.9.3 前「Step 1 后建 Feature」的遗留。
- **效果**：门① 守卫的绕过口**从根上消失**（无 stage 可传）；**A/A′/B 三项消解**（原"改缺省""加守卫""拒派生值"随入参移除而消失）。
- **`version` 保留**（未登记桶 / 撤排期语义 / released 锁 / 板拖拽建卡路径依赖它）。
- `DEFAULT_FEATURE_STAGE`/`DEFAULT_FEATURE_APPROVAL` **常量保留**（读侧归一 + ctor 脏值归一的落点），只改注释。
- `parseRegistration` 本体**不动**（两枚 create 侧错误码转"不可达"，非删代码）；zod 默认 **strip 未知键** ⇒ 未升级的板继续传两参**静默丢弃、不报错**。

### 2.5 同版串行占用口径（★用户）

**占用名额 = {活跃 `executing`, `version_planning`, `decomposing`}**；**主轨「失败静止」（无可派发、无在飞）不占名额**；**增补轨与承接轨同规**（都取主轨校验、都不计为第二条主轨）。

- **消解 R2 死锁**：承接轨在主轨失败静止时可进 ⇒ 失败节点可拆小，**不用 cancel 主轨、不废原地重派**。
- **措辞钉（★R3）**：`需求流程.md:200`「增补与主需求及其它增补不得同时 `executing`」**原样保留**（解除的是跨子树误计，不得读成同子树可并行）；补**同子树互斥句**「同一主轨子树内同时至多一个 Feature 活跃；主轨重派前须确认子树内无其它活跃轨」。占用口径**单处定名、别处回指**。
- **纯流程纪律，引擎不执法**（§4.1 既有「引擎只提供项目粒度串行、不提供需求间串行」不变）。

### 2.6 其余定稿项

## §4 验收标准

**实现级**：
- `orch` `npm run typecheck` + `npm test`（~600 行测试面改造后全绿）；`state-machine.test.ts` 转移表断言重写、新态专项 ~120 行、门① 守卫/两出态判据/准入门扩集/存量 waiting_approval 走新链/`decomposing` 期不派发。
- `board` `npm run typecheck` + 全量（基线 1509/1509 须保持）。
- `flow` spec 一致性自检（E 组九条门禁）：`analyzing|planning`=0、「6 态」=0、「显式传 stage=需求分析」=0、「验收段（integrating」=0、完整链式列举 ≤1、stage 值域 6 枚含「验收」、四戳同值。

**回归级**：根回归全绿（根 pin 联动归**发版门**，不进本 DAG）。

**真机验收清单（动作级）**：
1. 建一张新需求卡 ⇒ `state=waiting_approval` · `stage=需求分析` · `approval=未发起`（**create 已不收 stage/approval 入参**）。
2. 门① 未排期直接确认 ⇒ **被拒** `feature_group_version_required`，且 `state/stage` 逐字不变。
3. 排期写 `version` 后再确认 ⇒ 过门①（`stage→改造方案`）。
4. `approve` ⇒ `state→version_planning`（**不是 executing**）；PjM 落归属后 `advance` ⇒ `decomposing`；登记 DAG 后 `advance` ⇒ `executing`。
5. 板面：新态标签「定版中/拆任务中」显示；步条 6 段；`executing` 起 `stage` 显示「改造中」。
6. 存量卡（老 `executing`）**不受影响**（`stage` 不回填，显示滞后为已知噪音）。
7. **不触协议**：`PROTOCOL.md` 2.3 不变、machine 不随升。
