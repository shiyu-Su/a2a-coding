## §1 背景与评估

**目标**：① **声明层** —— DAG 节点 `dependencies` 只填**直接前置**，凡可由已声明边传递闭包推出的前置**不得重复声明**；② **呈现层** —— 依赖图渲**本质边**，并把「声明 / 本质 / 省略」三数**显式写在标题行**。

**现状 = 病态**：登记侧按声明原值入库（`orch/bridge/index.ts:1296` 只做 Set 去重），板忠实照画 ⇒ 一个「等全部前序」的末位节点被登记成 **N 条扇入边**，图上 N 条线射向同一枚 chip、长边全部下探通道带再横穿整幅图。

**根因不在引擎、也不在板**，而在**规范正文的一句命令式指令**：`flow/spec/需求流程.md:159`「载体升级（标准动作条）：…在 DAG 末位登记「载体升级」节点（**依赖全部实现节点**；…）」。研发经理照它写「★依赖 N1–N8 全部」、宿主照它原样登记 ⇒ **冗余是规范要求的产物**。

**实测证据**（board 只读，判据与 `buildTaskGraph` 同款：去重 / 去悬空 / 滤环）：27 个有边 feature 中 **15 个含冗余 = 55.6%**；声明并画出 **254** 条 ⇒ 本质 **188** ⇒ **冗余 66 条 = 26%**；每需求分布 `1×4 · 2×3 · 3×2 · 4×1 · 7×1 · 8×1 · 9×2 · 13×1`；最差五例 `1f937738` 47→34 · `4ca97bcd` 21→12 · `bb437c9f` 15→6 · `f2dcb141` 18→10 · `804a578d` 16→9。**归因**：66 条冗余中 **42 条（64%）落在标签含「载体升级」的节点**、47 条（71%）落在本 feature 入度最大的节点 ⇒ 形态即「末位节点全前缀扇入成星形」。

**评估结论：合理。** (a) 纪律面治「生成器」、(b) 呈现面治「存量已脏的图」；二者互补且都不可省 —— **存量唯一出路是 (b)**（completed 卡不可重登记，可挂载态白名单 = `executing` / `waiting_approval`，`index.ts:1230`）。**引擎面自动约简不采**（对派发零收益 · 须回写他行 · 丢声明审计面）。

## §2 方案设计

### §2.1 口径地基（一句话总纲）

> **事实源 = 已声明边集；板上的依赖图是投影。** flow 侧管「**应当声明什么**」（只声明**极大元**），board 侧管「**把任意声明集恢复成极大元集**」（**传递约简**）—— 二者是同一关系的两个方向；**flow 纪律落地后 board 的约简恒为恒等（`R = 0`）**，这正是两侧「无顺序依赖、互不阻塞」的数学形式。呈现侧的约简**不构成第二事实源、不改变引擎派发语义**。
