1. 「我的想法是：弱化flow spec，通过引擎来约束llm的执行」
2. 「如果由引擎来框定流程，这样只要引擎升级，就能确保orchagent一定是按照最新流程执行的了」

## 一、问题定义（现状，已核实）

「需求到哪一步」散在**多个正交轴**，无单一权威来源；部分约束只靠 flow spec 散文，执行体（含异机 agent）读不到。三个具体痛点：

1. **Step 2 整段压在 `executing` 一格**：PjM 版本规划 / dev_manager 拆分 / 节点执行 / 载体升级全在同一 `state`，读面看不出卡在哪道工序。
2. **门① 在 `state` 上不可见**：门① 只动 `stage`（登记字段）、主链不动 ⇒ 从入板到 `approve`，`state` 恒为 `waiting_approval`。
3. **门① 之后无 version 的需求无合规补写路径**（排期写状态锁：写 `version` 仅 `stage=需求分析 ∧ approval=未发起`）。

## 二、目标（用户裁定）

**靠 `state` 约束流程** —— 把 Step 2 的工序、以及「Group Version 未规划」纳入引擎状态 / 守卫，使流程**不可静默漏做**（引擎升级 ⇒ 全网络生效），而非靠 spec 自觉。

## 三、设计方案（用户逐条拍定）

### 3.1 主链 6 态 → 8 态（+异常 3）

```
waiting_approval → version_planning → decomposing → executing → integrating → testing → reviewing → completed
                    ↑ 新增·PjM        ↑ 新增·拆分
```

| 新 state | 进入 | 完成判据（可推进） | 驱动 |
|---|---|---|---|
| `version_planning` | `approve` 后 | 各 project 的 **PjM 结论收敛 + 归属落库**（先建 Project Version、再写归属） | 宿主 `advance` |
| `decomposing` | 上一态后 | 各 project **本侧任务清单回传 + DAG 节点登记完毕** | 宿主 `advance` |

**位置硬约束**：两态**只能在 `approve` 之后** —— 归属写口的引擎判据要求 `approval=已通过` ∧ `version` 非空，二者只有 `approve` 后才可能成立。（用户曾问的「PjM 提前到 Group Version 之后」经核实**不可行**。）

### 3.2 `stage` 值域 5 → 6，**全启用**（乙案）

```
需求分析 → 改造方案 → 改造 → 回归 → 验收 → 发版
```

`stage` 改为**跟着 state 走**（不再"只补盲区"），与 state 部分重叠但粒度更粗：`version_planning`+`decomposing`→改造方案；`integrating`+`testing`→回归；`reviewing`→**验收**（新增值）。

### 3.3 门① 加 version 守卫

门①（需求确认）触发时，引擎判 `features.version` 是否为空 ⇒ **空则结构化拒绝**（拟 `feature_group_version_required`），提示先规划 version；**拒绝时 step/state/stage 全不动** ⇒ 补写窗口（`stage=需求分析`）保持打开。`stage`→`改造方案` 的迁移归**门②（`approve`）**。

### 3.4 回归段去用户门（**待核实**）

用户语「reviewing到验收（这样的话 整个回归，就不要用户介入了）」⇒ 理解 = 主链 `integrating`/`testing` 由引擎/宿主推进、**不再设用户门**，用户验收收敛为 `reviewing` 那一格。⚠ 改动 Step 3 现有语义，**须核实用户本意**。

### 3.5 存量卡过渡 = (i)

**只对新需求生效**；老卡（已 `executing` 等）不受新态影响。
