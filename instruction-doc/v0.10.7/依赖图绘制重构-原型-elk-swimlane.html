先认错：上一版的度量确实没量到那个缺陷 —— 它量的是声明给 ELK 的 label 盒（41×16@0,0，横排、容器左上角），而渲染层画的是容器左缘竖排的字（rotate(-90)）。两个盒不是同一个位置 / 形状，所以「被节点盖 0」是真的、但说的是声明盒；字本身没被量过 ⇒ 报给了用户一个不成立的结论。

三条判定

方向更新（用户本轮已定，判定的读法随之变） —— 放弃「容器按本仓形状并列（贯穿全宽 / 左缘对齐 / 内容定宽 / projectId 升序带序）」这组要求，容器的形状 / 排布 / 顺序全交 ELK。所以下面判定 1 与 3 的「ELK 侧不能」不再是阻塞项，而是被放弃的要求；本轮唯一要修的是容器标题「画出来的字」被节点压（见上节，用了 (b)：竖排尺寸声明 + 容器 left padding 留带）。判定 2 仍成立且是本路线的立身依据：根 = layered 时 ELK 确实路由跨容器边（3/3、穿节点 0、端点达标 3）。
判定 1 · 泳道能不能出来：ELK 侧不能
ELK 里有 partition 的实现、但 JSON 面开不出来：bundle 内确有 PARTITION_PREPROCESSOR / PARTITION_MIDPROCESSOR / PARTITION_POSTPROCESSOR 与 elk.partitioning.activate，但对 elkjs 0.12 的 JSON 图，这些开关全是空转 —— 合成数据上三种写法（泳道 type:"partition" / 泳道挂 elk.partitioning.activate / 根挂）输出逐字节相同、入参 width:400 被忽略；真机数据（eb86d5e8 28 节点）更硬：上表前三行（三种 partition 写法）带几何完全一致（本轮 = board 779×110@345,524 / flow 507×446@522,12 / orch 486×254@12,204），且与第四行「不加任何 partition 开关」的对照组 compound-plain 一字不差 ⇒ partition 在 JSON 面无效果。第五行 compound-noport（把边的端点参照从 port 换回节点本体）带几何变了、但照样是三个孤立方框 ⇒ 差异来自 port，不来自 partition。
带是各自孤立的方框，不是横贯整幅的带：三条带 x=345/522/12、宽=779/507/486 vs 画布 1136 ⇒ 贯穿全宽=false、左缘偏差 510px。
⇒ 泳道带（贯穿全宽）与带间整条分隔线只能由渲染层补（② 侧：带 x=0 宽=画布全宽 1258、2 条全宽分隔线）。左侧竖排标签这一条本轮被推翻：它不需要渲染层留列 —— 容器 elk.padding[left] 就能把那条带留出来（(b)），字仍由渲染层 rotate(-90) 画在 ELK 回读的盒里。
判定 2 · 跨泳道边由 ELK 路由吗：会路由，但不是前几轮那个坑、也不是好事
① 侧跨带边 3/3 条有 sections（根 = layered 时 ELK 会路由跨容器边；前一轮「3/3 空 sections」只在根 = fixed / box 下成立）。穿节点 0 条、端点 rightMid→leftMid 达标 3/3（偏差 0/0/0px）⇒ 线本身合格。
但代价与判定 1 是同一个：ELK 为了路由，把带位、带宽、带内布局全重排（① 侧带 board:779×110@345,524 / flow:507×446@522,12 / orch:486×254@12,204）⇒ 「带贯穿全宽」与「跨带边交 ELK 路由」在 elkjs 里不能同时成立。② 侧把跨带边收回归渲染层走廊路由后：3/3 条全有几何、穿节点 0、带内 0、端点达标 3/3（偏差 0/0/0px）。
判定 3 · 泳道顺序能否固定为 projectId 升序：ELK 侧不能，渲染层侧天然是
① 侧 ELK 给的带序自上而下 = flow → orch → board（由拓扑定），期望 board → flow → orch；considerModelOrder=NODES_AND_EDGES 上一轮实测零效果（与不设逐字节相同），elk.layered.strictLayering/固定 elk.position 又会退化成「无边路由」⇒ 层序不可钉。② 侧带序由本仓按 projectId 升序直接生成 = board → flow → orch ⇒ 天然固定。

顺带一句结论 · 这条路下本仓几何栈是否整族退休

是 —— 走「容器全交 ELK」这条路，本仓那套几何栈在这一格里没有调用点了。 依据一句：ELK 一次 layout() 同时产出节点坐标与全部边（含跨容器边）的 sections，而 layerOfGraph / pipeGridLayout / planCanvas / planPipeGrid / canvasLayout 与走线全族 routeIntraEdges · packLanes · bandCorridor · pickCrossCorridors · layerCrossApproach · routeCrossFrameEdges 吃的都是本仓自己的网格模型（PipeGridCell 的 col/row/gapW/lanes/busLanes）——该模型在这条路上不再被生成，族也就无处入参（上一轮已实测：ELK 的绝对坐标喂不进 routeCrossFrameEdges）。随之上桌的代价（用户已裁定接受）：带序改由拓扑定（本轮 ① = flow → orch → board，非 board → flow → orch）、带不贯穿全宽、左缘不对齐（510px）。—— 本条只作一句结论，逐族「删 / 留 / 改」与体量估算按纪律不在本轮做。
