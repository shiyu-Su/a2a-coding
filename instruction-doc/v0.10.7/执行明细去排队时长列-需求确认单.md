## 要解决什么问题

> 确认点 =「我理解你要解决的是不是这个问题」——确认的是**问题**，不是方案。

- **当前行为**：需求详情页「**执行明细**」单表（列序事实源 `src/web/views.ts:713-726` 的 `EXECUTION_COLUMNS`，**共 12 列**：`#` / `taskId` / `项目` / `职责位` / `状态` / `要点` / `为什么没跑` / `失败类` / `重派` / `依赖` / **`排队时长`** / `执行时长`）里，**「排队时长」一列对任何任务都显示 `0s`**（用户实测）。
- **该列口径**：`formatDurationBetween(t.queuedAt, t.claimedAt)`（`views.ts:781`）——「入队时刻 → 首次领取时刻」之差，**秒级取整**（`derive.ts:99-110`；0–999ms 一律渲染 `0s`；缺任一端则显示 `—`）。
- **⚠ 根因（关键，与直觉不同）**：这**不是数据坏了、也不是口径 bug**。判据是「**恒 `0s` 而非恒 `—`**」—— 若 `claimedAt` 未落会显示 `—`，说明**两端时刻都落了、且落在同一秒内**。两因叠加：
  1. **认领即时** —— 引擎按 `dependencies` 拓扑派发，就绪节点在同一无死拍被领取 ⇒ `queuedAt ≈ claimedAt`；「同版串行 + 同 project 写互斥」又把这层的排队压掉了；
  2. **秒级 floor** —— 亚秒级真实等待也被归成 `0s`；
  3. 真正的等待（等上游 / 等写门）**不进这一列**，而由「**为什么没跑**」列（`waitReason` / `已等待`）承载 —— 被挡节点此时是 `—` 而非大数。
- **期望行为**：**从「执行明细」单表去掉「排队时长」这一列**（12 → 11 列）；该列要表达的等待语义已由「为什么没跑」列覆盖，保留一个恒 `0s` 的列本身就是噪音。
