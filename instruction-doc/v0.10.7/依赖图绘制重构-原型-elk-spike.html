C. 判定：框排布不能交给 ELK ⇒ canvasLayout 的框排布算术保留、不走 elk.position 单跑
  1. 交给 ELK 根级算法 = 拿不到本仓规则位：根 layered+DOWN 把三框摊到 x=12/317/938 量级（左缘偏差实测 305px），根 box+SOUTH 偏差 492px 且不路由跨层级边（3/3 条 sections 为空）；elk.nodePlacement.strategy=INTERACTIVE + 入参框位与不加结果完全相同（layered 不吃入参位）。本轮单探（见 E 块）已把这条判据修正：根 layered+DOWN+INCLUDE_CHILDREN 确实路由跨框边（3/3 条有 sections、穿节点 0、带 port 后端点偏差 0），但框位与框内布局由 ELK 重排（flow/orch 同层横铺、左缘偏 305~512px、三框宽高全变、层序按拓扑非 projectId 升序、considerModelOrder 零效果）⇒ 结论仍是「不能交给 ELK」，理由从「不产线」更正为「产线但改框位」。
  2. 钉死框位（根 fixed + 入参 x/y）= 位对了但没线：stacked/左缘/标题带全达标（左缘偏差 0px），但跨框边 3/3 条不被 ELK 路由（空 sections）—— 与 box 同病：ELK 只在 layered 这类「会自己摆位」的算法里跑正交路由器。
  3. ⇒ 可行的塌缩边界：框内分层 + 框内走线可整族交给 ELK（本页 28 chip / 28 条框内边即逐框 layered 的产出，纯 H/V 100%、标题带未被压）；框排布（升序纵堆 + 左缘对齐 + 内容定宽 + gapH 带高公式）必须留在本仓算术（canvasLayout 约 50 行可留，但其内部分层/走线的族可摘）；跨框边路由与框位互斥 —— 要保住本仓框位，跨框边必须有自己的走线器（本页已换成走廊路由，穿节点 0 / 端点偏差 0，见注①与数字表）。
