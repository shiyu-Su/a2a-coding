# a2a-coding 未来发展方向与产品战略参考

> 本文用于明确 `a2a-coding` 后续产品定位、技术架构、竞争策略及 MVP 演进方向。
>
> 核心判断：
>
> **不要继续把 `a2a-coding` 定义为一个 Agent Runner 或 Remote Agent 产品，而应该逐步演进为一个 Agent-agnostic 的 Engineering Control Plane（AI 软件研发控制平面）。**

---

# 1. 项目当前定位

`a2a-coding` 当前的核心能力可以抽象为：

```text
Orchestrator
     │
     ▼
   Bridge
     │
     ▼
  Machine
     │
     ▼
Agent Adapter
     │
     ▼
Claude Code / Codex / OpenCode / ...
     │
     ▼
Project Workspace
```

当前系统已经具备几个重要抽象：

* Orch
* Bridge
* Machine
* Project
* Agent Adapter
* Task / Session
* Agent 执行生命周期
* 多项目、多机器的基础能力

这实际上已经构成了一个 Agent 编排系统的雏形。

但随着 Claude Code、Codex、Cursor、Factory、Devin 等产品不断提供 Remote / Self-hosted / BYOM / Runner 能力，仅仅继续强化：

> Cloud → Machine → Agent

已经很难形成长期竞争壁垒。

因此，项目后续应该**提升抽象层级**。

---

# 2. 核心战略判断

## 2.1 不做 Agent 本身

项目应该长期坚持：

> **Never Build an Agent. Build the Infrastructure Around Agents.**

即：

```text
不负责：
- 模型
- Agent Prompt
- Agent Reasoning
- Agent Memory
- Agent Tool System
- Agent IDE
```

而负责：

```text
负责：
- Requirement
- Project
- Task
- Dependency
- Agent Routing
- Machine Routing
- Workflow
- Execution State
- Permission
- Approval
- Audit
```

Agent 本身应该被视为一种：

> **Execution Capability**

而不是整个系统的核心对象。

---

# 3. 目标产品定位

未来不应该把项目描述为：

> A2A Coding Agent

也不应该定位为：

> Remote Coding Agent

或者：

> Agent Runner

更适合的定位是：

> **Agent-agnostic Engineering Control Plane**

中文：

> **面向多项目、多机器、多 Agent 的 AI 软件研发控制平面。**

其核心价值是：

> 让企业或个人可以同时使用 Claude Code、Codex、OpenCode、Qoder、自研 Agent 等不同 Agent，并将它们组织成一个统一的研发协作系统。

---

# 4. 为什么不能只做 Remote Agent

当前市场已经出现大量类似能力：

```text
Cloud
  ↓
Remote / Self-hosted Runner
  ↓
User Machine
  ↓
Agent
```

代表方向包括：

* Claude Code Remote / Self-hosted Environment
* Cursor Cloud Agents / My Machines
* Devin Outposts
* Factory BYOM
* Ona Runners
* Astro Agent Runner
* GitHub Actions Self-hosted Runner
* GitLab Runner
* Buildkite Agent
* AWS SSM Agent

这些产品说明：

> **“本地机器主动连接云端，然后接受任务执行”已经成为一种成熟的基础模式。**

因此：

```text
Machine 反向注册
+
Heartbeat
+
Outbound Connection
+
Task Pull
+
Remote Execution
```

应该被视为基础设施，而不是核心产品壁垒。

---

# 5. 真正应该竞争的方向

未来的竞争核心应该从：

```text
谁能更好地运行 Agent
```

转向：

```text
谁能更好地组织不同 Agent 完成一个真实的软件研发任务
```

也就是：

```text
Requirement
      ↓
Project
      ↓
Task Graph
      ↓
Agent Routing
      ↓
Machine Routing
      ↓
Execution
      ↓
Review
      ↓
Testing
      ↓
Integration
```

这里最重要的变化是：

> **系统管理的是 Work，而不是 Agent。**

---

# 6. 产品核心抽象

未来建议建立以下核心对象：

```text
Organization
    │
    ├── User
    │
    ├── Project
    │
    ├── Machine
    │
    ├── Agent
    │
    ├── Requirement
    │
    ├── Task
    │
    ├── Workflow
    │
    └── Execution
```

其中：

### Requirement

用户提出的业务需求。

例如：

```text
增加微信登录
```

---

### Project

一个实际的软件项目。

例如：

```text
Backend
Frontend
Mobile
Admin
Data Service
```

---

### Agent

一种执行能力。

例如：

```text
Claude Code
Codex
OpenCode
Qoder
Custom Agent
```

Agent 不应该和 Project 强绑定。

---

### Machine

实际执行环境。

例如：

```text
Mac Mini
Linux Server
Windows PC
Cloud VM
Kubernetes
On-prem Server
```

---

### Task

一个可以执行的工作单元。

例如：

```text
Implement OAuth API
Update database schema
Implement login UI
Add integration test
```

---

### Workflow

任务在一个 Project 内如何执行。

例如：

```text
Requirement
    ↓
Analysis
    ↓
Implementation
    ↓
Test
    ↓
Review
```

---

# 7. 三层总体架构

未来整体架构建议明确分为三层：

```text
┌─────────────────────────────────────┐
│          Control Plane              │
│                                     │
│ Requirement / Project / Task / DAG  │
│ Dependency / Approval / State       │
└─────────────────┬───────────────────┘
                  │
                  │ Agent Fabric
                  ▼
┌─────────────────────────────────────┐
│          Agent Fabric               │
│                                     │
│ Claude │ Codex │ OpenCode │ Qoder  │
│ Cursor │ Custom Agent │ A2A Agent   │
└─────────────────┬───────────────────┘
                  │
                  │ Runner
                  ▼
┌─────────────────────────────────────┐
│          Execution Plane            │
│                                     │
│ Machine A │ Machine B │ Machine C   │
│ VM        │ Mac       │ Server      │
│ K8s       │ Local     │ On-Prem     │
└─────────────────────────────────────┘
```

---

# 8. Control Plane

Control Plane 是未来产品的核心。

负责：

```text
Requirement
Project
Task
Dependency
Workflow
Agent Routing
Machine Routing
Execution State
Approval
Permission
Audit
```

它回答的是：

> **应该做什么、由谁做、什么时候做、依赖什么、现在做到哪里。**

而不是：

> Agent 应该如何思考。

---

# 9. Agent Fabric

Agent Fabric 是 Agent 适配层。

目标：

> 让不同 Agent 以统一接口接入系统。

例如：

```text
Claude Code
      │
Codex
      │
OpenCode
      │
Qoder
      │
Custom Agent
      │
A2A Agent
      │
      ▼
Agent Adapter Interface
```

统一暴露：

```text
start()
send()
status()
cancel()
logs()
result()
```

不同 Agent 的具体差异由 Adapter 消化。

---

# 10. Execution Plane

Execution Plane 是用户自己的执行环境。

例如：

```text
Machine A
Machine B
Machine C
```

每台机器运行：

```text
Runner
```

Runner 负责：

```text
Register
Heartbeat
Capability Discovery
Task Pull
Task Execution
Event Streaming
Result Reporting
```

因此未来建议：

```text
Machine
   │
   ▼
Runner
```

成为一个稳定的基础组件。

---

# 11. Machine 反向注册 Bridge

这是当前架构应该继续保留的重要能力。

但概念上应该从：

```text
Machine → Bridge
```

升级为：

```text
Runner → Control Plane
```

典型流程：

```text
User installs Runner
        │
        ▼
Runner starts
        │
        ▼
Register
        │
        ▼
Control Plane
        │
        ▼
Runner Heartbeat
```

Runner 主动建立出站连接。

不要求：

```text
公网 IP
入站端口
VPN
公网暴露 Agent
```

这样可以天然支持：

```text
家庭电脑
公司内网
企业服务器
私有云
VPC
Mac Mini
开发者电脑
```

---

# 12. Runner 不应该绑定某一个 Agent

Runner 应该是：

> **Machine-level Runtime**

而不是：

> Claude Runner / Codex Runner

例如：

```text
Machine A
└── Runner
    ├── Claude Code
    ├── Codex
    └── OpenCode
```

甚至：

```text
Machine B
└── Runner
    ├── Qoder
    └── Custom Agent
```

Control Plane 根据任务选择：

```text
Project
+
Machine
+
Agent
```

---

# 13. Agent 与 Machine 解耦

未来应该支持：

```text
Agent Capability
       +
Machine Capability
       +
Project Requirement
       ↓
Scheduler
```

例如：

```text
Task:
iOS UI implementation

Machine capabilities:
macOS
Xcode

Agent capabilities:
Codex

        ↓

Machine B + Codex
```

而：

```text
Task:
Linux backend deployment

Machine capabilities:
Linux
Docker

Agent:
Claude Code

        ↓

Machine A + Claude Code
```

这会使系统从简单的：

> Agent 调度

升级成：

> **Capability-based execution scheduling**

---

# 14. Global Orch 与 Project PM

这是未来架构中的一个重要边界。

不建议让 Global Orch 负责所有细节。

建议采用：

```text
                 Global Orch
                     │
                     │ Requirement
                     ▼
              Project Manager
                     │
              Project Workflow
                     │
            ┌────────┼────────┐
            ▼        ▼        ▼
          Agent    Agent    Agent
```

---

# 15. Global Orch 的职责

Global Orch 负责：

```text
理解整体 Requirement
识别涉及哪些 Project
建立跨 Project Dependency
分配 Project-level Task
协调多个 Project
汇总最终结果
```

例如：

```text
Requirement:
增加支付功能
```

Global Orch 识别：

```text
Backend Project
Frontend Project
Mobile Project
QA Project
```

形成：

```text
Backend
   │
   ├── API
   └── Payment Model
        │
        ▼
Frontend
        │
        ▼
Mobile
        │
        ▼
Integration Test
```

---

# 16. Project PM 的职责

每个 Project 可以拥有自己的 Project Manager Agent。

Project PM 负责：

```text
需求分析
技术方案
任务拆分
项目内部依赖
Coding
Testing
Review
Project-specific Workflow
```

例如 Backend Project：

```text
Project PM
    │
    ├── Analyze
    ├── Design API
    ├── Database
    ├── Coding
    ├── Unit Test
    └── Review
```

Frontend Project 可以有完全不同的流程。

---

# 17. 为什么要让 Project 自己拥有 Workflow

不同项目的研发方式可能完全不同。

例如：

Backend：

```text
Analysis
→ Design
→ Coding
→ Unit Test
→ Integration Test
```

Frontend：

```text
Requirement
→ UI Design
→ Coding
→ Browser Test
→ Review
```

Mobile：

```text
Requirement
→ iOS Design
→ Coding
→ Simulator Test
→ Device Test
```

因此：

> **Global Orch 不应该强制所有 Project 使用同一套研发流程。**

Global Orch 管理：

```text
Cross-project orchestration
```

Project PM 管理：

```text
Project-level workflow
```

---

# 18. 最终形成两级 Orchestration

```text
                Requirement
                     │
                     ▼
              ┌─────────────┐
              │ Global Orch  │
              └──────┬──────┘
                     │
          Cross-project Tasks
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
 Project PM A    Project PM B   Project PM C
       │             │             │
   Workflow A     Workflow B     Workflow C
       │             │             │
    Agents         Agents         Agents
       │             │             │
    Machines       Machines       Machines
```

这是未来系统非常重要的核心架构。

# 20. A2A 的位置

A2A 不应该成为整个系统的唯一底层通信方式。

建议重新定义：

```text
A2A = Agent Interoperability
```

即：

```text
Agent ↔ Agent
```

而系统自己的 Runner Protocol 负责：

```text
Control Plane ↔ Runner
```

整体：

```text
Control Plane
      │
      │ Runner Protocol
      ▼
    Runner
      │
      ▼
    Agent
      │
      │ A2A
      ▼
 Other Agent
```

这样可以避免整个项目被某一个 Agent Protocol 绑定。

---

# 21. Transport Layer

Runner Protocol 与 Transport 解耦。

未来可以支持：

```text
HTTPS
WebSocket
Long Polling
SSH
MQTT
```

不同环境选择不同方式。

例如：

```text
普通互联网
→ HTTPS / WebSocket

企业内网
→ HTTPS

极端受限网络
→ MQTT

特殊运维环境
→ SSH
```

因此：

> SSH 可以成为一种 Transport，而不是整个系统的架构。

---

# 22. 为什么不建议把 SSH 作为核心

SSH 很轻量，但它天然更偏：

```text
Machine access
```

而你的目标是：

```text
Work orchestration
```

未来需要处理：

```text
Task Queue
Offline Machine
Retry
Heartbeat
Capability
Session
Event
State
Approval
Audit
```

这些能力并不天然属于 SSH。

所以：

```text
Runner Protocol
      │
      ├── HTTPS
      ├── WebSocket
      ├── MQTT
      └── SSH
```

比：

```text
Everything = SSH
```

更适合长期演进。

# 23. Cloud + Private Agent

这是项目未来一个非常值得验证的场景。

用户拥有：

```text
Cloud Account
```

但代码和 Agent 都部署在：

```text
Private Machine
```

架构：

```text
                 Cloud
        ┌─────────────────────┐
        │ Control Plane       │
        │                     │
        │ Global Orch         │
        │ Project Graph       │
        │ Task State          │
        └──────────┬──────────┘
                   │
             Outbound Channel
                   │
                   ▼
        ┌─────────────────────┐
        │ Private Machine     │
        │                     │
        │ Runner              │
        │ Project PM          │
        │ Claude/Codex/etc.   │
        └─────────────────────┘
```

这样用户无需把代码上传到云端。

# 24. 更进一步：Cloud PM → Private PM

未来可以形成：

```text
Cloud PM
    │
    ▼
Private Project PM
    │
    ▼
Local Agents
```

例如：

```text
User
 │
 ▼
Cloud Project Manager
 │
 │ “实现支付功能”
 ▼
Private Backend PM
 │
 ├── Claude Code
 ├── Codex
 └── OpenCode
```

这形成：

> **Cloud-level orchestration + Private execution orchestration**

这可能是项目非常值得深入验证的方向。

# 25. “用户自有控制面”也是潜在价值

除了 SaaS 模式，未来应该支持：

```text
Cloud Control Plane
```

和：

```text
Self-hosted Control Plane
```

两种模式。

例如：

```text
                    Control Plane
                  /               \
                 /                 \
             Cloud               Self-hosted
               │                    │
             Runner                Runner
               │                    │
             Agent                 Agent
```

企业可以选择：

```text
控制面也私有化
```

而个人用户：

```text
使用 SaaS Cloud
```

这样商业模式更加灵活。

# 27. MVP 不应该做得太大

第一阶段只验证一个核心场景：

> **一个 Requirement 驱动多个 Project，在多个 Machine 上使用不同 Agent 并行完成工作。**

例如：

```text
Requirement:
“增加 OAuth 登录”
```

系统：

```text
Global Orch
     │
     ├── Backend Project
     │      ↓
     │   Claude Code
     │      ↓
     │   Machine A
     │
     ├── Frontend Project
     │      ↓
     │   Codex
     │      ↓
     │   Machine B
     │
     └── QA Project
            ↓
         OpenCode
            ↓
         Machine C
```

最后：

```text
Integration
     ↓
Global Orch
     ↓
User
```

# 29. 第一阶段不要做


---

# 30. MVP 成功标准

不要以：

```text
Agent 数量
Runner 数量
代码量
```

作为成功指标。

真正应该验证：

### Case 1

一个 Requirement：

```text
Backend + Frontend
```

是否可以自动协同完成？

### Case 2

Backend 和 Frontend 是否可以运行在不同机器？

### Case 3

两个项目是否可以使用不同 Agent？

### Case 4

其中一个 Agent 失败后，是否可以继续执行？

### Case 5

Project PM 是否可以独立管理自己的 Workflow？

如果这些都成立，说明核心产品方向成立。

# 32. 竞品策略

不建议把竞争对象定义为：

```text
Cursor
Claude Code
Codex
```

因为这些产品本身就是 Agent。

你的定位应该是：

```text
Cursor / Claude / Codex / OpenCode
             ↓
        Agent Fabric
             ↓
       Your Control Plane
```

也就是说：

> **不是替代 Agent，而是让不同 Agent 可以共同工作。**

---

# 33. 与 Agent 厂商的关系

未来最好把 Agent 厂商视为：

> **执行能力提供商**

而不是竞争对手。

例如：

```text
Claude Code
Codex
OpenCode
Qoder
```

都可以成为：

```text
Agent Adapter
```

你的产品负责：

```text
什么时候使用
谁使用
在哪里使用
做什么任务
依赖什么
什么时候结束
失败怎么办
如何汇总
```

Agent 负责：

```text
怎么完成任务
```

# 34. 最重要的产品原则

## Principle 1

> **Do not build another Agent.**

---

## Principle 2

> **Agent is a replaceable execution capability.**

---

## Principle 3

> **Project is a first-class citizen.**

---

## Principle 4

> **Machine is an execution resource, not the product.**

---

## Principle 5

> **Global Orch coordinates Projects; Project PM manages Project workflows.**

---

## Principle 6

> **A2A is an interoperability protocol, not the entire system architecture.**

---

## Principle 7

> **Cloud manages orchestration; users own execution.**

# 36. 最终判断

当前市场已经验证：

> **Remote Agent + Self-hosted Runner 是一个真实需求。**

但同时也说明：

> **这一层正在快速基础设施化。**

因此，不建议把 `a2a-coding` 的未来核心价值建立在：

```text
Machine Reverse Registration
Remote Agent
A2A Transport
Runner
```

这些能力之上。

这些应该成为产品的基础设施。

真正值得继续投入的是：

```text
             Requirement
                   │
                   ▼
          Cross-Project Planning
                   │
                   ▼
            Project PM
                   │
                   ▼
           Project Workflow
                   │
                   ▼
          Agent Orchestration
                   │
                   ▼
          Cross-Machine Execution
```

最终形成：

> **一个不拥有 Agent，但可以组织所有 Agent 的研发控制平面。**

# 37. 项目未来的一句话定义

推荐未来统一使用：

> **a2a-coding is an agent-agnostic engineering control plane that coordinates AI software engineers across projects, machines, and execution environments.**

中文：

> **a2a-coding 是一个面向多项目、多机器、多执行环境的 Agent-agnostic AI 软件研发控制平面。**

核心理念：

```text
                    ┌──────────────┐
                    │  Requirement │
                    └───────┬──────┘

                            ▼

                            │
                            ▼

                            │

                            │
                            ▼
                      HOW to build
                            │

                            │
```

**不做 Agent。**

# 38. 当前最重要的下一步

在继续大规模开发之前，建议只验证一个问题：

> **“一个自然语言 Requirement，能否真正驱动两个位于不同机器、使用不同 Agent 的 Project 完成一次完整的软件功能交付？”**

如果答案是 Yes，那么继续发展 `a2a-coding` 是有意义的。

如果答案是 No，则应该优先修正产品抽象，而不是继续增加 Agent、Transport 或 UI 能力。

因此，下一阶段的开发重点应该不是：

```text
更多 Agent
更多协议
更多 UI
```

而是：

```text
Requirement
    ↓
Cross-project Task Graph
    ↓
Project PM
    ↓
Agent Routing
    ↓
Machine Routing
    ↓
Execution
    ↓
Integration
    ↓
Result
```

这条链路，就是 `a2a-coding` 最值得验证的核心产品闭环。
