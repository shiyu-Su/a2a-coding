# 需求流程规范（内核）

> **规范版本戳**：v0.9.4（2026-09-28）
>
> 本文件是流程规范内核，与具体项目无关，可整体复制到任意项目使用。
> 引擎对齐（步骤如何挂到状态机与工具面）见同目录 `引擎映射.md`，不属于本可复制内核。
> 花括号 `{...}` 为占位符，落地时按项目替换。

## 0. 绝对规则

- **不得擅自改代码** — 用户没有明确说「改/实现/加/修」等实现动词时，禁止编辑任何代码文件。用户提问、分析、反馈问题时，只回答/分析，不动代码。
- **用户测试反馈后必须等待确认** — 测试发现问题后，只分析根因、汇报方案，等待用户确认「改」之后再动手修改。不得在汇报后自行继续修改或推进。
- **规范优于经验** — 任何与规范冲突的情况，以书面规则为准，不以经验或常识判断替代。

## 1. 流程骨架（Step 0–3）

每个需求从提出到验收通过的完整链路。多个需求可独立走此流程，累计构成本版本内容。用户提出改动需求时，必须从步骤 0 开始，禁止直接实现。

```
0. 需求提出即入板（创建观测态需求实体）→ 需求访谈 → 输出《需求确认单》
   ↓ 【用户确认需求内容】
1. 需求评估 + 输出改造文档（评估结论内嵌）→ doc/{版本}/
   ↓ 【用户确认改造文档】
2. 需求实现（拆子任务 → 子 agent 并行执行）
   ↓
3. 用户测试 + 反馈
   │
   ├─ 小修（不改方案边界、不加新行为）→ 增补轨：另立增补 Feature 挂主需求（见 Step 3 三档定性判据）
   ├─ 方案变（需再次确认方案）→ 主需求 cancel → 从步骤 0 起新建
   ├─ 发现影响使用/结构的新需求 → 用户确认当前需求状态 → 进入需求池 → 回到步骤 0
   ├─ 发现非影响性改进点 → 登记主需求改造文档 §6（一句话，不编号）
   └─ 用户确认「通过」（须全部增补 completed 之后） → 主需求完成
```

> **步骤 1（用户确认改造文档）之前禁止开始实现。改造文档输出后不能直接开始实现，必须等用户确认。**
> **步骤 3 是需求流程的终点。用户确认「通过」后该需求结束，禁止自行进入发版操作（回归测试、CHANGELOG 更新、git commit、tag 等）。**
> **步骤 2 产出的 plan 严禁包含发版相关步骤。发版操作只能由用户主动要求后通过发版流程执行。**

## 2. 每步的判据与产出物

### Step 0 需求访谈

- 目标：在进入技术方案之前，先确认「问题定义」是否正确。
- **需求提出即入板（强制判据，v0.9.3）**：用户提出需求时即创建需求实体（`a2a_feature_create`，显式传 `stage=需求分析` ∧ `approval=未发起`，初态 `waiting_approval`），停靠需求池；**创建后第一步**经 advance 登记字段特例（`to` = 当前态）把已落盘的已有文档经 `decisions` 登记进去（create 无 `decisions` 参数，已核实）。确认单过门 = `stage` 迁「改造方案」（即下文判据中的确认动作凭据）。
- **须经执行单元核实（orch 不得单方断言）**：「当前行为」与「影响范围（粗判）」以及**技术可行性假设**必须由**相关执行单元**核实或补充后才可定稿 —— orch 看不到单元内部实现，单方断言会失真。orch 负责**组织核实并收敛结论**；核实结论落进需求确认单（附单元与时间）。**技术可行性假设** = 若该假设不成立则整个方案路径需改变的事实（如 CLI 兼容性、协议行为、命令组合、文件解析方式等）；此类假设**不得仅作为方案设计阶段的待验证项**，必须在需求确认单阶段完成核实。
- 产出物：《需求确认单》。**强制要求：必须写入 `doc/{版本}/{topic}-需求确认单.md` 文件，不得仅在对话中输出或口头确认。** 使用同目录 `文档模板.md` 的模板。
- 判据（何时算做完）：需求确认单已落文件，**且已含相关单元的核实结论**，且用户确认「我理解你要解决的是不是这个问题」—— 确认的是问题，不是方案。**（v0.9.0）确认动作由引擎登记记录承载**：需求实体已进引擎时（提需求时即已创建，见 `引擎映射.md` §3.5），用户确认后宿主将其 `stage` 由 `需求分析` 迁至 `改造方案`，该迁移即本门的动作凭据；**确认内容的事实源仍是落文件的需求确认单**，本条文件判据不废。
- 只有需求确认单经用户确认后，才进入下一步。

### Step 1 需求评估 + 输出改造文档

- 需求评估：检查是否与架构冲突、是否有依赖、是否有更简方案、是否与现有需求冲突。评估后需引用 REQ-ID。结论：合理 / 需调整 / 不合理。
- **orch 组织确定方案与边界（组织权 / 收敛权，无单方决定权）**：orch 须**主动组织**跨单元边界的讨论与收敛 —— 提出初版边界 → 分发各相关执行单元 → 收「接受 / 反对 / 调整」→ 调整后再分发 → **必要时多轮**，直至**各单元明确接受且无重复改造**。
- **各单元的本侧方案由单元自己评估并回传**（本侧落点 / 改动量 / 风险 / 明确「**做什么**」与「**不做什么**」）；orch **不得替单元定本侧方案**，也不得**跳过单元确认自行拍板**。
- **防重复改造**：每个相关单元须回答「本侧是否可能与其它单元**重复改造同一功能**」；出现重复风险 → orch 收敛边界 → **再确认**。**例外**：确需**冗余容灾**时，必须**显式登记**（哪两处冗余、为何）。
- **跨单元边界确认是多轮的**：广播初版 → 各单元**逐项表态**（orch 每轮先列「待决项清单」，要求逐项「接受 / 反对 + 理由」，禁止泛泛讨论）→ orch 收敛调整 → **边界一旦变动须重新广播**（旧的「接受」失效）→ 循环至全部接受。**讨论用同一 `contextId` 续接**（要有记忆），**不得每轮新开 `contextId`**。**上限 ≤3 轮**；仍未达成 → **升级用户拍板**。**留痕**：每轮边界版本 + 各单元表态落改造文档（修订历史 +1 版，或附「边界确认记录」）。
- 产出物：**评估合理后，必须输出改造文档到 `doc/{版本}/{topic}-改造文档.md` 文件，不得仅在对话中输出。** 使用同目录 `文档模板.md` 的改造文档模板。评估结论内嵌在改造文档的「背景」或「方案设计」章节中。**§3.1 In-Scope 须按单元分列，并含各单元「不做什么」。**
- 判据：评估结论已明确（合理 / 需调整 / 不合理）；评估合理且改造文档已落文件（含内嵌评估结论）；**各相关单元已确认接受且无重复改造**；用户确认改造文档。**（v0.9.0）**改造文档落文件后宿主将需求实体的 `approval` 置 `待审批`；用户确认经 `approve` 落为引擎记录（`approval` → `已通过`），**`approve` 校验 `approval = 待审批`、不看 `stage`**（见 `引擎映射.md` §3 / §3.5）。
- **门语义见 `引擎映射.md` §3**：`approve` = **记录已发生的用户确认（一对一映射：不可预领、不可补领）**，宿主在收到用户确认后**立即**调用，**不是新增一次决策**；**禁止**在用户未确认方案前调用。
- **Step 0/1 不推进主链**（见 `引擎映射.md` §2）：这两步的产出物按本文件落文件，主链状态不承载；主链起点是 `waiting_approval`。**v0.9.0 补 / v0.9.3 升格**：需求实体**提需求即进引擎**（原「可提前」，现为 Step 0 强制判据「需求提出即入板」），初态仍 `waiting_approval`，Step 0/1 期间其携带 `stage`/`version`/`approval` **登记字段（观测面，不是状态机态**，值域与映射见 `引擎映射.md` §3.5）；登记字段的写入不改主链、不改本节任何判据条数。
- 评估为「需调整」时先调整方案并再次确认；「不合理」不进入实现。
- 必须等待用户确认改造文档后，才进入实现阶段。

### Step 2 需求实现

- 动作：按改造文档实现，拆为独立子任务并行执行。
- 判据：改造文档 §3.1 In Scope 全部落地；§4 验收标准中的实现级与回归级自测通过；无未同步的偏离。
- **硬约束（执行必走引擎）**：
  - **H1**：Step 2 的**前置** = 需求实体已存在（提需求即入板创建，见 Step 0；未走 Step 0 的旧形态下为先 `a2a_feature_create`，初态即 `waiting_approval`）**并同轮把 DAG 节点清单贴给用户**；不建 Feature 就没有清单、用户看不到 ⇒ 绕过立刻可见；
  - **H2**：**实现期禁止 `mode="execute"` 不带 `featureId`** 的派发 —— 执行型派发必须挂在已 `approve` 的 Feature 下（`feature_required_for_execute`）；只读核实/调研走 `mode="inquiry"`；
  - **H3**：**例外须显式登记**（理由 / 降级路径 / 谁批）；**收口自检 = 行为复核** —— 列出实现期内 `feature_id IS NULL` 的任务清单，**逐个确认"未产生代码改动"**（由目标单元自报 / 门禁结果佐证），**不可省略**。
  - **H4 派发消息自包含**：拆 DAG 后派给执行单元的**每条任务消息**，必须**就地内嵌**「本节点的具体改造内容（做什么 / 不做什么 / 落点）/ 门禁定义 / 验收判据」的**要点全文** —— **不得以「读 `doc/{版本}/{topic}-改造文档.md`」作为唯一指令载体**（执行单元可能位于**异机**、无宿主侧文件系统访问权）；文档路径**仅可作背景引用**（同机的便利）。**增补轨的派发同样适用**；**跨单元边界确认类消息同样须将「待表态条目全文」带入消息**（防止异机收不到确认单），并以**同一 `contextId` 续接多轮表态**。本约束**不改变节点粒度纪律**（见本步「派给执行单元的任务节点要小」，单节点仍应约 10 分钟可完成）：**粒度管「多小」、自包含管「消息能否独立执行」**，二者互补；消息模板见 `文档模板.md` §3。
- **载体升级（标准动作条，v0.9.3）**：凡改动载体代码的 Feature（主需求与增补轨同款），在 **DAG 末位登记「载体升级」节点**（依赖全部实现节点；由执行单元自升级，回执经该节点 `advance(note)` 留痕；**替代此前另立独立运维 Feature 的形态**）。引擎不为此新增 stage / 状态 —— 升级在引擎态上就是 `executing` 内的一个节点，「实现完成后、验收前」的时序由依赖关系保证。
- **实现中如偏离改造文档**：实现方式、接口、行为与改造文档不一致时，必须同步更新改造文档（修订历史 +1 版），不得等实现完成后再补。
- **实现中发现 scope 外的问题**：

```
发现新问题
  → 判断是否影响需求A【验收标准】的达成
  → 否 → 超出需求A范围
      → 在主需求改造文档 §6 登记（一句话，不编号）
      → 继续需求A，不中断
  → 是 → 按 Step 3 三档定性判据分流
      → 不改方案边界、不加新行为（小修）→ 增补轨（另立增补 Feature 挂主需求，方案写入主需求改造文档「增补」节 +1 版）
      → 需再次确认方案（方案变）→ 主需求 cancel → 从步骤 0 起新建
```

- **禁止在需求 A 的实现中顺手修需求 B 的问题**。例外：纯格式问题可以直接修并同步说明；≤3 行/≤15min 的低成本修复可以在 CHANGELOG 中备注后直接修，不违反此规则。
- **派给执行单元的任务节点要小**：单节点应能在约 10 分钟内跑完（派发请求超时通常为数百秒，超时即判失败）；大改造拆多个小节点（避免「单节点过大 → 超时/截断」）；派发消息应注明「接近超时 / 上下文上限时先保门禁通过再报告」。
- （可选）鼓励用本系统自身的编排能力实施需求本身，顺带真机验证编排链路。

### Step 3 用户测试 + 反馈

- 动作：实现完成后仅向用户展示变更摘要和测试结果，等待用户反馈。禁止执行任何回归测试、CHANGELOG 更新、git 操作。
- 判据：用户给出明确反馈。用户确认「通过」后，同步更新改造文档修订历史（标记 final 版本）→ 需求完成，等待发版。
- **三档定性判据（分水岭，v0.9.3 成文）**：用户反馈中的问题按对「方案边界」的影响定档，档位决定挂载方式：
  - **小修（不改方案边界、不加新行为）** → 走**增补轨**：**另立增补 Feature** 并经 `a2a_feature_create(parentFeatureId=主需求 featureId)` 挂到主需求下；增补是完整的小需求流程（stage 同链），其方案写入**主需求改造文档的「增补」节（修订历史 +1 版）**，不另立改造文档；确认走增补 Feature 自己的 `approval`/`approve`。**主需求最后完成**：主需求最先实现、最后 `completed`，用户验收结论下在**全部增补 completed 之后**。增补 Feature 同样落 §7「同版串行纪律」（与主需求及其它增补不得同时 `executing`）。
    > 口径变更（引擎核实 2026-09-26）：此前「实现级增补 → 当前需求 `needs_input → executing` 续推」的写法**作废** —— `needs_input` 仅 `executing` 可进可出、主链无回边、挂载白名单仅 `executing`/`waiting_approval`，验收段（`integrating`/`testing`/`reviewing`）无该路径。`needs_input` 回归其唯一语义：**执行期任务澄清**（见 `引擎映射.md` §2 / §6）。
  - **方案变（需用户再次确认方案 / 整体回炉）** → **主需求以 `a2a_feature_cancel` 终止** → 从步骤 0 起新建（新方案重走 `approve` 门）。
  - **新需求（影响使用或结构、与当前需求验收无关）** → 用户先确认当前需求的完成状态 → 进入需求池 → 从步骤 0 开始新需求。
- 发现非影响性改进点 → 一句话登记到主需求改造文档 §6，不展开。
- **验收须显式列「未覆盖验证项」**：凡「改了但未在真机碰到 / 未触发」的项（如未配置某端、需受控重启才能触发），验收时必须列出（含原因）并登记改造文档 §6，不得默认算通过。
- **编排链路改动必须真机 E2E**：凡改动「编排链路」（怎么派活、怎么收结果）的版本，Step 3 必须有一次真机端到端（真实执行单元拉起 → 派发 → 执行 → 回传）；若确以离线自测放行，必须在改造文档 §6 显式登记为遗留验证项，不得算通过（离线断言会掩盖真实缺口）。

**Step 3 的两张推进判据清单（v0.9.1 起）**

`executing → integrating` 之后的 `testing → reviewing`、`reviewing → completed` 两格由宿主 `advance` 驱动（见 `引擎映射.md` §2）。以下两张清单是**宿主侧的人判清单**——「每格推进前该核什么」的成文口径，**不是引擎的前置校验**（引擎不新增任何机器门）：

- **进「验收」前（testing → reviewing）**：
  1. **单元门禁全绿**——相关单元 typecheck / 单测通过，引用 Step 2 收口回执为凭；**根回归不前置**（回归属发版门，本步禁止执行，见上文动作条与 §1 绝对规则）。
  2. **真机验收动作完成并有回执**——回执载体 = `advance(note)` 留痕 + 改造文档修订历史（+1 版）。
  3. **未覆盖项已登记**——按上文「验收须显式列『未覆盖验证项』」条执行（回指该条，不另抄口径）。
- **进「完成」前（reviewing → completed）**：
  1. **用户验收结论明确**——用户原话留痕（经 `advance(note)` 承载）。
  2. **改造文档修订历史含 final 行**——字面口径与发版回归检测一致（修订历史表存在 `final` 行）。
  3. **全部增补已收口**——本需求名下增补 Feature 均已 `completed`（主需求最后完成，见上文三档定性判据）。
  4. **父改造文档 final 对照最新实现**——final 版的方案 / In Scope / 验收标准与含增补后的最新实现一致。
  5. **遗留待办均已登记去处**——未排期想法进需求池卡片，登记类项在主需求改造文档 §6，不得默认算完成。

- **各阶段文档（需求确认单 / 改造文档等）落盘后，推进时经 `a2a_feature_advance` 的 `decisions` 数组登记文档路径（每份一条，append 语义），供板上「产出登记」区关联展示；`note` 留作当轮说明，不承载文档清单。**

### 每步推进的强制条件

需求从 Step 0 → Step 1、Step 1 → Step 2、Step 2 → Step 3 推进之前，必须满足以下判据，否则不得进入下一步：

1. **文档已落地**：当前步骤对应文档已写入 `doc/{版本}/` 目录。
   - Step 0 输出：`{topic}-需求确认单.md`
   - Step 1 输出：`{topic}-改造文档.md`
   - Step 2/3 如有修订：同步更新改造文档（修订历史 +1 版）
2. **需求池标记以引擎为准**：需求「当前步骤」的事实源 = 引擎登记字段 `stage`/`approval`（读面 = 板需求池 + 排期面），不再另记台账（v0.9.3 起 planlog 版本待办退役，见 §7）。

## 3. 多轮对话流程纪律（AI 遵守）

AI 在跨轮对话中执行流程时，必须遵守以下纪律：

```
1. 每轮只进一个步骤
   用户的"确认/同意"只针对当前步骤，不隐含对后续步骤的授权。
   → 用户说"好"→ 只代表当前步骤通过，不能自动进入下一步。

2. 不得跨步输出
   禁止在同一轮回复中同时完成多个步骤。
   → 举例：不能在同一轮既输出需求确认单（步骤0）又输出改造文档（步骤1）。
   → 必须等用户对当前步骤的输出做出反应后，再进入下一步。

3. TODO continuation 不推进流程
   系统触发继续执行时，只完成当前已授权步骤内的剩余工作。
   → 步骤 2 的实现中途被系统 continuation 触发 → 继续实现，不自行进入步骤 3。
   → 步骤 3 被 continuation 触发 → 等待用户反馈结果或决策，不自行进入发版流程。

4. 每轮重置意图判断
   用户新的一轮输入，只根据本轮内容判断意图。
   → 用户说"改一下"→ 重新判断是哪个步骤，不是默认进入"实现"阶段（步骤 2）。
   → 用户说"看看效果"→ 只做展示/说明，不是默认进入"测试"阶段（步骤 3）。
   → 用户说"发版"→ 才进入发版流程。
```

## 4. 文档命名规范

每个需求在 Step 0 和 Step 1 必须产出两个文件，命名统一为：

| 文档 | 文件路径 | 命名格式 |
|------|----------|----------|
| 需求确认单 | `doc/{版本}/{topic}-需求确认单.md` | `{topic}-需求确认单.md` |
| 改造文档 | `doc/{版本}/{topic}-改造文档.md` | `{topic}-改造文档.md` |

- `{topic}` 为该需求的简短中文摘要（5-10 字），同一个需求的两个文件使用同一 `{topic}`，便于配对和追溯。
- 禁止单独使用 `需求确认单.md`、`改造文档.md` 等无 topic 前缀的文件名。
- 禁止混用 `方案`、`方案设计`、`实现方案`、`修复`、`优化`、`分析` 等后缀，统一使用 `改造文档` 作为后缀。
- **README 只做整体架构 / 配置描述**：不写版本号（`vX.Y.Z`）与需求 / 版本历史——版本历史归 `CHANGELOG.md`，需求与设计归 `doc/{版本}/`。

## 5. 开发中的文档同步

```
代码改动后必须同步更新文档，不允许出现「代码改了，文档还停在原版」的情况。
```

- 实现完成后立即检查 `doc/{版本}/` 是否需要更新
- 发版前必须做一次文档对齐，确保文档与代码一致
- 架构图、数据流、字段说明必须与实际代码对应

**文档更新时机（必须遵循）**：

| 时机 | 动作 | 修订历史标记 |
|------|------|-------------|
| 改造文档初稿完成 | 写入 `doc/{版本}/` | v1 |
| 实现中偏离原方案（接口/行为/范围变化） | 立即同步更新 | +1 版（v2、v3…） |
| 二次修改（用户测试发现问题后） | 修改代码后同步更新 | +1 版 |
| 增补轨定案（小修挂主需求，见 §2 Step 3） | 方案写入主需求改造文档「增补」节 | +1 版 |
| 用户确认测试通过后 | 最终审核对齐 | 标记 final 版本（final 版须对照含增补的最新实现） |

**登记字段与文档同步（v0.9.0）**：`stage`/`version`/`approval` 的**唯一事实源在引擎**，文档与任何台账不得另存一份字段值；登记字段的迁移与本节文档动作绑定 —— 需求确认单经用户确认 ⇒ `stage`「需求分析 → 改造方案」；改造文档落文件 ⇒ `approval`「未发起 → 待审批」；用户确认改造文档 ⇒ `approve` 落 `approval = 已通过`。板排期写（v0.9.2，仅写 `version`）**不触发**本段文档动作绑定（改版不要求搬文档；有产出物的改版走 §7 改版纪律第二档，由板自动搬文档并回写 `decisions`）。**文档仍是确认内容的事实源，登记字段只承载确认动作（谁 / 何时 / 对哪个阶段）**（见 `引擎映射.md` §3.5）。

## 6. 测试中的问题处理

回归测试或日常测试中发现的问题，**不得擅自修复**，必须走以下流程：

```
发现缺陷或异常
  → 记录问题现象
  → 分析根因 + 修复方案
  → 向用户汇报
  → 等待用户确认
  → 确认后再修改
  → 修改后重新测试
```

**例外**：纯格式问题（缩进、空格、注释）或 CI 配置修复，可以直接修并同步说明。

## 7. 版本管理

### 版本号规则

```
v<major>.<minor>.<patch>

v0.x.x  ← 当前阶段（持续迭代）
v1.0.0  ← 功能完备后正式定版
```

### REQ-ID 规则

- 格式：`REQ-YYYY-MM-DD-XX`，其中 `XX` 为**当日全仓序号**（v0.9.3 起去版本段——需求所属版本是引擎登记字段 `version`，可随排期改版，不进编号）。
- **存量号一律不迁移**：既有文档中的 `REQ-{版本}-YYYY-MM-DD-XX` 旧号保持原样；新格式自本修订落地后的**下一条新需求**起用。
- 同一需求的需求确认单与改造文档使用**同一个 REQ-ID**，便于配对追溯。
- 改造文档中引用需求时，写成 `REQ-YYYY-MM-DD-XX` 形式（引用存量旧需求时可照旧号原样引用）。

### 需求状态的事实源（版本待办退役）

v0.9.3 起，`planlog.md` 顶部的「版本待办」台账**废除** —— 需求及其状态的事实源 = **引擎登记字段 `stage` / `approval` / `version`**（值域与映射见 `引擎映射.md` §3.5），读面 = **板需求池 + 排期面**；文档与任何台账不得另存一份字段值（见 §5）。planlog 的历史登记职能改道：

| 原 planlog 职能 | 新落点 |
|---|---|
| 版本待办（需求清单与状态） | 引擎登记字段 + 板需求池/排期面 |
| 非影响性改进点登记 | 主需求改造文档 §6（一句话，不编号） |
| 未覆盖验证项 / 遗留验证项 | 主需求改造文档 §6（单处登记） |
| 跨版本登记项 / 未排期想法 | 需求池卡片 |

**同版串行纪律**：**同一版本内的多条需求必须串行推进**（一次只推进一条需求走到终点，再起下一条；「需求间并行」不排期，已废弃）—— 引擎只提供**项目粒度**的串行、**不提供需求间串行**，故串行只能由宿主在「过审」放行的时点把控（细则见 `引擎映射.md` §4.1；增补 Feature 同版本内一并排队）。

### 改版纪律（v0.9.3 新增）

需求在版本间挪动（改 `version`）按当前所处状态分两档：

1. **想法挪版（零善后）**：`stage = 需求分析` ∧ `approval = 未发起` ∧ 无 `decisions` 产出物登记 ⇒ 直接改版（板排期拖拽直达），不触发任何文档动作绑定（见 §5）。
2. **有产出物的改版**：已登记 `decisions` 产出物（需求确认单 / 改造文档已落文件）⇒ 由板**自动善后**：写 `version` + 将 `decisions` 登记文档 `mv` 至 `doc/{新版本}/` + `decisions` 追加新路径。**过渡态**：板受限 mv 能力落地前（v0.9.3 需求 2 承载），改版善后由宿主手工执行同等步骤。planlog 同步职能已退役，遗留台账的对账降级为宿主**择机**执行（非改版阻塞条件）。

**已发版锁叠加**：目标版本或原版本已在板版本台账中标记为 `released` ⇒ 不得排入/改动排期（见 §8）。

**排期写状态锁**：排期写仅 `stage = 需求分析` ∧ `approval = 未发起` 可写（板前台执法，409 `board_schedule_state_locked`）；宿主经 MCP 直写同受本纪律约束（后门不豁免）。

## 8. 发版流程（Release Flow）

当用户决定发布当前版本时执行。发版流程独立于需求流程，不对应某个具体需求。

```
0. 检查引擎需求状态 — 确认当前版本（version 登记值）名下全部需求实体均为 completed
1. 发版前文档审核：
   a. 审核 doc/{版本}/ 文档，确认与实际代码一致（已在需求流程中同步完成，此处仅验证）
   b. 更新 CHANGELOG.md，记录本次版本所有变更
   c. 更新 README.md（如有架构、API 或流程变化）
   d. 检查回归测试脚本，确认已有用例覆盖当前版本所有新增模块和检测项，
      如有新模块/新文件需补充对应检测用例
2. {回归测试命令}
3. 检查 reports/v{版本号}/regression-report.json 确认全部通过，用于版本记录
4. git add + commit
5. git tag v0.x.x
6. git push && git push --tags（同步到远程仓库）
7. 发布到目标环境
```

> **回归测试**：发版前必须执行回归测试，且必须先更新回归测试用例，再运行。每个版本有新文件、新模块时，必须在回归测试脚本中补充对应检测项（文件存在性、exports、依赖声明等）。
> **git push 代理兜底**：上传远程仓库（发版步骤 6 及一切 push）直连失败时（连接重置 / 空响应 / 无法连接 443），可改走本机代理重试：`git -c http.proxy=<proxy> -c https.proxy=<proxy> push`；推送成功后不必改全局 git 配置，仅当次命令级注入即可。
> **板标记 `released`（v0.9.4，原「登记已发版版本 v0.9.2」）**：发版步骤 4–7 完成后，在板上将版本标记为 `released`（版本台账 `.data/versions.json`，热生效免重启）——板前台排期锁的事实源；标记闸 = 该版本名下全部需求实体均 `completed`（与步骤 0 同判据），不满足 ⇒ 板拒绝标记；已发版版本不再排入/改动需求排期；宿主经 MCP 直写 `version` 同受此纪律约束（引擎侧校验留待 version 闭集定型，见 v0.10.x）。
> **登记 `stage = 发版`（v0.9.0）**：发版步骤 4–7 完成后，宿主将本版本已发版需求的 `stage` 写为 `发版` —— 经 `a2a_feature_advance` 的「`to` = 当前态 ∧ 带登记字段」特例（**不改状态机态**；该特例无终态守卫，`completed` 后仍可写入，见 `引擎映射.md` §3.5）。
