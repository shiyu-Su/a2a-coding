# 需求流程规范（内核）

> **规范版本戳**：v0.10.8（2026-10-16）
>
> 本文件是流程规范内核，与具体项目无关，可整体复制到任意项目使用。
> 引擎对齐（步骤如何挂到状态机与工具面）见同目录 `引擎映射.md`，不属于本可复制内核。
> 花括号 `{...}` 为占位符，落地时按项目替换。

## 0. 绝对规则

- **不得擅自改代码** — 用户没有明确说「改/实现/加/修」等实现动词时，禁止编辑任何代码文件。用户提问、分析、反馈问题时，只回答/分析，不动代码。
- **用户测试反馈后必须等待确认** — 测试发现问题后，只分析根因、汇报方案，等待用户确认「改」之后再动手修改。不得在汇报后自行继续修改或推进。
- **规范优于经验** — 任何与规范冲突的情况，以书面规则为准，不以经验或常识判断替代。

## 0.5 职责（组级职责 / project 级职责位）与出场时点

> **分野句**：`unit_agent` 是**职责位标识符**，指既有的「执行派发对象」；它**不是**「单元 = project」这一说法的引申（本规范所称「单元」= 引擎项目面中的一个 project，见 §7 —— 二者正交，不得互推）。

一条需求在每个 project 上涉及四个**职责位**。「职责位」= 一次派发以哪个身份出场，是**派发属性**，不是流程步骤、不是状态机态、不新增机器门、不新增产出物。四个职责位都是 **project 级**（每个 project 各自成立，不在组内合并成一个角色）。

**层级分野句（组级职责不是职责位）** —— 上表四个职责位都是 project 级的；本规范另有一层**组级职责**（见下「组级职责」块），它**不是**这四个职责位之一，也不经 `taskType` 派发。上句末段「四个职责位都是 **project 级**」的括注管的是 project 级职责位不在组内合并，**不排除组级另有职责**，二者层级不同、不得互推。

| 职责位 | 管什么 |
|---|---|
| **产品经理** | 本 project「**接不接**」这条需求（需求合理性评估的本单元结论） |
| **项目经理（PjM）** | **版本规划评估 → 定版本**（本 project 在本需求下落哪个 Project Version） |
| **研发经理** | 出改造方案 —— 钉为**本 project 的「本侧方案贡献」** |
| **执行单元 agent**（`unit_agent`，缺省职责位） | 领任务执行 |

**「工序 → 职责位」对照表（v0.10.2 增补三）** —— 每道工序由哪个职责位出场，**以本表为准**；未声明职责位的派发一律按**执行单元 agent**（缺省）出场。

| 工序 | 职责位 | 出场形态 |
|---|---|---|
| **Step 0 需求访谈 / 需求合理性评估** | **产品经理** | 参与既有工序（本 project「接不接」的结论），落进《需求确认单》；**不新增工序、不新增机器门、不新增产出物** |
| **Step 1 需求评估 + 边界轮（各单元回传本侧方案）** | **研发经理** | 边界轮内回传本侧方案与「做 / 不做」表态（见 §2 Step 1） |
| **（改造方案确认后）排期 / 版本规划评估** | **项目经理（PjM）** | §2 Step 2「PjM 版本规划工序」标准动作条；**= state `version_planning`**（按态名指称，非值域登记，见 `引擎映射.md` §1「不抄枚三句硬钉」②） |
| **Step 2 生成具体任务（本侧任务清单）** | **研发经理** | 复用其 Step 1 会话；产出**本 project** 的任务清单（宿主负责收敛与登记）；**= state `decomposing`**（同上，按态名指称） |
| **Step 2 节点执行 / Step 3 验收** | **执行单元 agent**（缺省） | DAG 节点派发（见 §2 Step 2 / Step 3） |

> **出场时点的唯一口径**：产品经理的出场在 **Step 0**（本表「Step 0」行）。上表是本规范内**唯一**一处「工序 → 职责位」映射，§2 各步只回指本表、不另存一份。

> **Step 0 的标注限定语（v0.10.2 增补五）**：**Step 0 的一切派发（含只读核实）一律标产品经理**；**只有不属于任何工序的临时探针 / 一次性盘点**方可不标（不标 ⇒ 静默落缺省职责位，等于漏标）；本条只管**派发侧**标注，组级职责（见上「组级职责」块）由宿主自办、不构成需标注的派发。此类派发亦须带 `featureId` —— 过渡期挂其所服务 Feature（含发版前盘点挂该版本内最近一条需求卡），正式归宿由流程档位机制另卡裁决。

> **「本侧方案贡献」的边界**：整份改造文档仍由宿主收敛、由 §2 Step 1 的判据把门；研发经理出场**不等于**该 project 有权另行定稿或改写他侧方案。

**组级职责** —— 组级职责 = 跨 project 的判断与协调，由宿主 agent 按出场承担，不是 project 级职责位、不落 `taskType`。表内分栏语义：**判断方 = 持该职责位的 LLM agent；执行方 = 引擎代码**。

| 组级职责 | 管什么 | 判断方 | 执行方 |
|---|---|---|---|
| **组级产品负责人** | 需求深挖 / 需求定性 / **触达面初判与裁决** / 组级产品文档两个写点（〔建组时创建初始组级产品文档 —— 其实现载体另卡 `26bfa4f5`，本规范不写实现〕·〔发版流程中补充完善 —— 写点见 §8 步骤 1〕）；**不定 Project Version、不写归属记录** —— 定版归本 project 的项目经理（§7「四条规则」），归属写库归宿主（§2 Step 2「PjM 版本规划工序」） | 宿主 agent（组级产品负责人出场） | 引擎代码（建版写口 / 归属写口） |
| **桥协调者** | 组内跨 project 协调 / 跨 project 契约影响判据 / 编排派发 | 宿主 agent（桥协调者出场） | 引擎代码（拓扑派发） |

① **承载** = **同一宿主 agent 按出场切换，非独立 agent** —— 组级职责不新增角色实体、不新增派发身份、不新增 stage 值域 / 机器门 / 产出物。

② **四项分立**：四者称谓互不相等，其中只有「宿主 agent」是角色实体（实体数 = 1，见下「宿主层定位」块）；`orch` 单元与编排桥是代码载体、桥协调者是其编排面出场身份。其中「编排桥」沿用既有词并回指 §5「登记字段与文档同步」内原句「本规范中「引擎」= 编排单元 `orch`，「编排桥」= 其常驻服务面」；「`orch` 单元」所指回指 §7「与既有纪律的分工（术语对齐）」内原句「本规范所称「**单元**」= 引擎项目面中的一个 project」。

③ **基数**：「1 个/组」= **规范期望、承载待裁**；凭据写运行事实：每请求可解析 `owner_group` ⇒ 运行态**可辨组、不可辨组内发言者**。

> **回指锚（两处）** —— ① 跨 project 契约影响判据的**事实源** = 协议契约中的协议版本本身（回指 §7「单元版本同升纪律」下注原句「**分组判据的事实源 = 协议契约中的协议版本本身**」—— **语义锚，不记行号**：该原句在本包内出现两处，可核性靠上引定位语，不靠唯一命中），本块只写「由谁判断」，不另存判据；②「编排派发」的驱动方身份回指 `引擎映射.md` §7「宿主（LLM）」同一实体，**不构成第二编排入口**

**宿主层定位（单一角色）** —— 宿主层（板轮 agent / 交互宿主）= **单一角色：角色实体 = 1，出场身份 = 多个**；不拆 agent 实体、不分 kind/model。职责分层由 project 级职责位（`taskType` 派发属性）实现（回指 §0.5 原句「四个职责位都是 **project 级**…」与 §7「接管说明」原句「不引入新角色实体」，与二者同源、**不是新断言**）。

**重开条件（登记为判据）** —— 满足以下任一 ⇒ **须走规范改版重新裁决**：① 组级两职责需要不同 model 档；② 桥协调者走向无人值守自治；③ 多组规模。

> 互指：复数责任主体的口径见 `引擎映射.md` §4.1「责任主体口径（v0.8.6 补）」（该处管责任主体为复数，本块只管角色实体数 = 1），二者互指不重复定义。

**业务知识外化原则** —— 宿主**不承载业务逻辑**；业务知识 = **文件**（组级产品文档），按需重读、不驻留会话。钉三句：**不进引擎、不扩登记字段、不作归属来源**。建组写点只写「该文档应在建组工序中产生，其实现载体另卡（`26bfa4f5`）」，**不写 board 行为**。

**会话复用纪律（派发侧，v0.10.2 增补五）** —— 「一次派发沿用谁的 `contextId`」的口径，与上表同属本节的职责位语义，不新增工序、不新增机器门、不新增产出物。**本表只定会话沿用，不是第二处「工序 → 职责位」映射** —— 工序由哪个职责位出场，仍以上方对照表为唯一准。

**复用范围的上界 = 「默认另起 + 显式登记的跨 step 例外」**：每个新任务节点默认**另起** `contextId`；例外**仅下表第 2 行这一处**，且**硬性要求同角色**（角色不同不得复用）。

| 转换 | 是否复用 | 依据 |
|---|---|---|
| **Step 0 → Step 1** | **不复用**（新起会话） | 换职责位（产品经理 → 研发经理） |
| **Step 1 → Step 2「生成具体任务」** | **复用** —— 同一 project 的研发经理**沿用其 Step 1 会话**的同一 `contextId` | 同一逻辑任务的连续触达（**硬性要求同角色**；本纪律唯一登记的跨 step 例外） |
| **Step 2 认领任务执行** | **全新会话** | 每个实现节点各自新起 |

> **不变量**：**同一 `contextId` 上任意时刻至多一个在飞轮次** ⇒ **并行节点不得共享**同一 `contextId`（各起一条会话线）。
>
> 本节只写语义（复用 / 另起的判据与上界），不写执行手段；跨 step 例外不得自行扩充，新增须走规范改版。同 step 内的多轮续接口径见 §2 Step 1。
>
> **归属纪律两补（v0.10.8）**：Step 0/1 的 `mode="inquiry"` 派发**必带 `featureId`**；该要求只约束**派发的归属声明**，**不改变本表既有的会话另起/复用判定**（本表仍只定会话沿用，见上「本表只定会话沿用」句）。提需求当刻如需先探针，归入当轮所立之卡（立卡 = Step 0 第一步，无空窗）。

**会话面分野** —— 本规范存在**两个正交的会话面**：**派发侧**（上方表格管辖：一次派发以哪个职责位出场、沿用谁的 `contextId`）/ **交互侧**（宿主与人的会话轮，现状粒度 = 一需求一会话、轮次单调累加、需求终结即会话终结、面内不切）。「派发侧默认另起 + 唯一跨 step 例外」**不外推**到交互侧；交互侧粒度**不构成**派发侧的第二份复用口径 —— §0.5 的适用范围 = 工序派发面，板侧宿主轮在其外、由板侧口径自管。交互侧在本规范内**抽象写**：不写记录载体 / 键结构 / 台账路径（属运行底座事实），不引入「阶段」一词（`stage` 已占用）。

**术语映射（三名一物）** —— 同一件事在三个面上各有一个名字，不得另立第四名：

| 面 | 名称 |
|---|---|
| 流程规范（本包正文用词） | **职责位** |
| 协议派发 | `taskType` |
| 执行单元侧配置 | `roles` |

> **组级职责不在这三个面内**：不落 `taskType`（组级职责一旦落 `taskType` 即为协议升版事件）、不落 `roles` 配置键；三名一物不得另立第四名。

> **本节只写语义**：职责位的取值清单、非法值处置、配置校验等**执法原文不进本包**（前瞻解耦见 `引擎映射.md` §8）；本包也不为职责位引入新 stage 或新状态机流转。

## 1. 流程骨架（Step 0–3）

每个需求从提出到验收通过的完整链路。多个需求可独立走此流程，累计构成本版本内容。用户提出改动需求时，必须从步骤 0 开始，禁止直接实现。

```
0. 需求提出即入板（创建观测态需求实体）→ 需求访谈 → 输出《需求确认单》
   ↓ 【用户确认需求内容】
1. 需求评估 + 输出改造文档（评估结论内嵌）→ doc/{版本}/
   ↓ 【用户确认改造文档】
2. 需求实现（版本规划（PjM）→ 本侧任务清单（dev_manager）→ 拆子任务 → 子 agent 并行执行）
   ↓
3. 用户测试 + 反馈
   │
   ├─ 小修（不改方案边界、不加新行为）→ 增补轨：另立增补 Feature 挂主需求（见 Step 3 三档定性判据）
   ├─ 方案变（需再次确认方案）→ 主需求 cancel → 从步骤 0 起新建
   ├─ 发现影响使用/结构的新需求 → 用户确认当前需求状态 → 进入需求池 → 回到步骤 0
   ├─ 发现非影响性改进点 → 登记主需求改造文档 §6（一句话，不编号）
   └─ 用户确认「通过」（须全部增补 completed 之后） → 主需求完成
```

> **步骤 1（用户确认改造文档）之前禁止开始实现。改造文档输出后不能直接开始实现，必须等用户确认。**
> **步骤 3 是需求流程的终点。用户确认「通过」后该需求结束，禁止自行进入发版操作（回归测试、CHANGELOG 更新、git commit、tag 等）。**
> **步骤 2 产出的 plan 严禁包含发版相关步骤。发版操作只能由用户主动要求后通过发版流程执行。**

## 2. 每步的判据与产出物

### Step 0 需求访谈

- 目标：在进入技术方案之前，先确认「问题定义」是否正确。
- **产品经理出场（v0.10.2 增补三）**：本步的**需求合理性评估**由本 project 的**产品经理职责位**参与（§0.5 对照表「Step 0」行），落点是「**本 project 接不接**」这条需求的结论；「**整条需求接不接**」（需求定性）属**组级产品负责人**职责（见 §0.5「组级职责」块），不在本条。该结论并入《需求确认单》的单元核实面（附单元与时间），**不新增工序、不新增机器门、不新增 stage 值域、不新增产出物**。
- **需求提出即入板（强制判据，v0.9.3 · v0.10.5 改述 create 契约 · v0.10.5 增补卡 `ec93e1bd` 主语扩围为甲案）**：**凡立卡（主轨 / 增补轨 / 承接轨）** ⇒ 第一步即本步：落**自己的**《需求确认单》并经门① 抬 `stage`（门② 的 ④⑤ 以此为前提，见 `引擎映射.md` §3 门②行）；**轨型间的其余差异口径见 §2 Step 3 / §2 Step 2，本条不扩。** 立卡即创建需求实体（`a2a_feature_create`，**初值恒定** —— `stage=需求分析` + `approval=未发起` 由引擎固定写入，create **不再收这两枚入参**；`version` 仍保留为入参。口径单源 = `引擎映射.md` §3.5「初值恒定」条，本条只回指、不另存一份），初态 `waiting_approval`，停靠需求池；**创建后第一步**经 advance 登记字段特例（`to` = 当前态）把已落盘的已有文档经 `decisions` 登记进去（create 无 `decisions` 参数，已核实）；**该登记现是门① 的引擎前提（v0.10.5 增补）** —— 《需求确认单》路径未登记进 `decisions` ⇒ 门① 的 `stage` 抬写被**结构化拒收、零写入**；**判据单源在 `引擎映射.md` §3 门①行**，本条只回指、不另存一份。确认单过门 = `stage` 迁「改造方案」（即下文判据中的确认动作凭据）。
- **须经执行单元核实（orch 不得单方断言）**：「当前行为」与「影响范围（粗判）」以及**技术可行性假设**必须由**相关执行单元**核实或补充后才可定稿 —— orch 看不到单元内部实现，单方断言会失真。orch 负责**组织核实并收敛结论**；核实结论落进需求确认单（附单元与时间）。**技术可行性假设** = 若该假设不成立则整个方案路径需改变的事实（如 CLI 兼容性、协议行为、命令组合、文件解析方式等）；此类假设**不得仅作为方案设计阶段的待验证项**，必须在需求确认单阶段完成核实。
- 产出物：《需求确认单》。**强制要求：必须写入 `doc/{版本}/{topic}-需求确认单.md` 文件，不得仅在对话中输出或口头确认。** 使用同目录 `文档模板.md` 的模板。
- 判据（何时算做完）：需求确认单已落文件，**且已含相关单元的核实结论**，且用户确认「我理解你要解决的是不是这个问题」—— 确认的是问题，不是方案。**（v0.9.0）确认动作由引擎登记记录承载**：需求实体已进引擎时（提需求时即已创建，见 `引擎映射.md` §3.5），用户确认后宿主将其 `stage` 由 `需求分析` 迁至 `改造方案`，该迁移即本门的动作凭据；**确认内容的事实源仍是落文件的需求确认单**，本条文件判据不废。
- 只有需求确认单经用户确认后，才进入下一步。

### Step 1 需求评估 + 输出改造文档

- 需求评估：检查是否与架构冲突、是否有依赖、是否有更简方案、是否与现有需求冲突。评估后需引用 REQ-ID。结论：合理 / 需调整 / 不合理。
- **orch 组织确定方案与边界（组织权 / 收敛权，无单方决定权）**：orch 须**主动组织**跨单元边界的讨论与收敛 —— 提出初版边界 → 分发各相关执行单元 → 收「接受 / 反对 / 调整」→ 调整后再分发 → **必要时多轮**，直至**各单元明确接受且无重复改造**。
- **各单元的本侧方案由单元自己评估并回传**（本侧落点 / 改动量 / 风险 / 明确「**做什么**」与「**不做什么**」）；出场身份 = 本 project 的**研发经理职责位**（§0.5 对照表「Step 1」行），「本 project 接不接」不属本问、已在 Step 0 表态；orch **不得替单元定本侧方案**，也不得**跳过单元确认自行拍板**。
- **防重复改造**：每个相关单元须回答「本侧是否可能与其它单元**重复改造同一功能**」；出现重复风险 → orch 收敛边界 → **再确认**。**例外**：确需**冗余容灾**时，必须**显式登记**（哪两处冗余、为何）。**单一写者（本条的直接引申 · 文件写入权分派）**：`flow/spec` 规范包的**字面正文**只由 **flow 节点**改写，他侧（含宿主与其它执行单元）**不得直改**；确需他侧写入本包的，走本条既有例外机制**显式登记**（谁写、为何、经哪个节点）。
- **跨单元边界确认是多轮的**：广播初版 → 各单元**逐项表态**（orch 每轮先列「待决项清单」，要求逐项「接受 / 反对 + 理由」，禁止泛泛讨论）→ orch 收敛调整 → **边界一旦变动须重新广播**（旧的「接受」失效）→ 循环至全部接受。（本条只管**同一 step 内**的边界轮；**跨 step** 的复用见 §0.5「会话复用纪律」）**讨论用同一 `contextId` 续接**（要有记忆），**不得每轮新开 `contextId`**。**上限 ≤3 轮**；仍未达成 → **升级用户拍板**。**留痕**：每轮边界版本 + 各单元表态落改造文档（修订历史 +1 版，或附「边界确认记录」）。
- 产出物：**评估合理后，必须输出改造文档到 `doc/{版本}/{topic}-改造文档.md` 文件，不得仅在对话中输出。** 使用同目录 `文档模板.md` 的改造文档模板。评估结论内嵌在改造文档的「背景」或「方案设计」章节中。**§3.1 In-Scope 须按单元分列，并含各单元「不做什么」。**
- 判据：评估结论已明确（合理 / 需调整 / 不合理）；评估合理且改造文档已落文件（含内嵌评估结论）；**各相关单元已确认接受且无重复改造**；用户确认改造文档。**（v0.9.0）**改造文档落文件后宿主将需求实体的 `approval` 置 `待审批`；用户确认经 `approve` 落为引擎记录（`approval` → `已通过`），`approve` 的过门判据见 `引擎映射.md` §3 门②行，**本条不另存一份**。
- **门语义见 `引擎映射.md` §3**：`approve` = **记录已发生的用户确认（一对一映射：不可预领、不可补领）**，宿主在收到用户确认后**立即**调用，**不是新增一次决策**；**禁止**在用户未确认方案前调用。
- **Step 0/1 不推进主链**（见 `引擎映射.md` §2）：这两步的产出物按本文件落文件，主链状态不承载；主链起点是 `waiting_approval`。**v0.9.0 补 / v0.9.3 升格 / v0.10.5 改述为回指**：需求实体**提需求即进引擎**（原「可提前」，现为 Step 0 强制判据「需求提出即入板」），初态仍 `waiting_approval`，Step 0/1 期间其携带 `stage`/`version`/`approval` **登记字段（观测面，不是状态机态）**；这三枚字段的**两条写路径**（**宿主显式写** · **引擎随 `state` 派生写**）与值域、映射的**单源在 `引擎映射.md` §3.5**，本条只回指、不另存一份；登记字段的写入（无论走哪条写路径）不改主链、不改本节任何判据条数。
- 评估为「需调整」时先调整方案并再次确认；「不合理」不进入实现。
- 必须等待用户确认改造文档后，才进入实现阶段。

### Step 2 需求实现

- 动作（分「生成」与「执行」两段，v0.10.2 增补五）：
  - **生成**：各 project 的**研发经理职责位**出**本侧任务清单**（本 project 要拆成哪些独立子任务、各自落点与判据），**复用其 Step 1 会话**（§0.5 对照表「Step 2 生成具体任务」行 +「会话复用纪律」表第 2 行）。
  - **执行**：节点执行的出场身份 = **执行单元 agent**（缺省职责位，§0.5 对照表「Step 2 节点执行 / Step 3 验收」行），按清单并行执行。
  - **宿主职责** = **收敛各 project 研发经理回传的本侧任务清单 + 在 `decomposing` 内登记节点 + 同轮把清单贴给用户**（「同轮」的时点口径见下 H1）；宿主**不替单元单方拆本侧任务**（收敛与登记权 ≠ 单方决定权，与 §0.5「本侧方案贡献」的边界同款）。
- 判据：改造文档 §3.1 In Scope 全部落地；§4 验收标准中的实现级与回归级自测通过；无未同步的偏离。
- **硬约束（执行必走引擎）**：
  - **H1**：Step 2 的**前置** = 需求实体已存在（提需求即入板创建，见 Step 0；未走 Step 0 的旧形态下为先 `a2a_feature_create`，初态即 `waiting_approval`）**并把 DAG 节点清单贴给用户**；**贴清单的时点（v0.10.5 后移）= `decomposing` 收口那一轮** —— 即**末枚节点登记完毕、宿主 `advance` 出 `decomposing` 之前**的那一轮，**不是 `approve` 当轮**（DAG 登记时点随挂载白名单收窄而倒转，见 `引擎映射.md` §4 三步序）；不建 Feature 就没有清单、用户看不到 ⇒ 绕过立刻可见；
  - **H2**：**实现期禁止 `mode="execute"` 不带 `featureId`** 的派发 —— 执行型派发必须挂在已 `approve` 的 Feature 下（`feature_required_for_execute`）；**且 `mode="execute"` 的 DAG 初版登记仅在 `decomposing` 合法**（v0.10.5 起登记时点倒转：`waiting_approval` 已摘出挂载白名单、`version_planning` 内不得登记节点，回指 `引擎映射.md` §4 三步序与挂载白名单。**执行期增量新节点**是另一处合法挂载点 —— 落在 `executing`，登记口径见 `引擎映射.md` §4 重派分两路第 (ii) 项）；只读核实/调研走 `mode="inquiry"`；
  - **H3**：**例外须显式登记**（理由 / 降级路径 / 谁批）；**收口自检 = 分支式校验、不预设结论** —— 实现期内 `feature_id IS NULL` 的任务应为**空集**（orch 已答：收紧后新行恒带 `feature_id` ⇒ **断言级默认**）；**非空 ⇒ 缺陷升级、逐口归因**；若引擎侧确认仍留合法写口，则本句改为**空集校验并点名到写口**，**不可省略**。
  - **H4 派发消息自包含**：登记节点后派给执行单元的**每条任务消息**，必须**就地内嵌**「本节点的具体改造内容（做什么 / 不做什么 / 落点）/ 门禁定义 / 验收判据」的**要点全文** —— **不得以「读 `doc/{版本}/{topic}-改造文档.md`」作为唯一指令载体**（执行单元可能位于**异机**、无宿主侧文件系统访问权）；文档路径**仅可作背景引用**（同机的便利）。**增补轨的派发同样适用**；**跨单元边界确认类消息同样须将「待表态条目全文」带入消息**（防止异机收不到确认单），并以**同一 `contextId` 续接多轮表态**。本约束**不改变节点粒度纪律**（见本步「派给执行单元的任务节点要小」，单节点仍应约 10 分钟可完成）：**粒度管「多小」、自包含管「消息能否独立执行」**，二者互补；消息模板见 `文档模板.md` §3。
- **依赖只声明直接前置（标准动作条 · 登记纪律，v0.10.5）**：登记节点时 `dependencies` **只声明直接前置**，冗余的传递边不得声明。照「载体升级」先例形态 —— **本条只管登记写法，引擎不为此新增任何能力**。
  - **判据（删边测试，机械可核）**：删去该边后该前置在**同一节点集**内仍传递可达 ⇒ 该边是**冗余边**，不得声明。
  - **「等全部前序」的唯一合法写法**：只声明前序集的**极大元**（没有任何另一前序传递地先于它的节点）。**两枚前序互不依赖 ⇒ 两枚都要声明（这是合法汇合，本纪律不禁止汇合）；一枚是另一枚的祖先 ⇒ 只声明后代那枚。**
  - **语义边界（只紧不松）**：约简前后**传递闭包恒等** ⇒ 就绪集、派发序、失败冻结闭包三者不变；**不得**以约简为名删任何真实等待。
  - **论域 = 同一 Feature 内的节点集**：节点跨轨搬动后（见本步「二次拆分的过渡期形态」第 4 条）须在**本轨节点集**上重取极小表示。
  - **「前置」= 等待关系，不是「数据流」的同义词**：为**定序**而声明的边同样是真实前置、**不得删** —— 同 project 的先后由引擎**项目粒度的串行**自然保证、不需边，而**跨 project 的定序只能靠声明边承载**（事实依据见 `引擎映射.md` §4.1 及其「并发语义矩阵」）。删边测试已天然护住此类边（无平行可达路径 ⇒ 非冗余）；本句只防把「只声明直接前置」**误读成「只声明数据依赖」**。
  - **执法主体 = 宿主**（在登记 `dependencies` 的时点把门）；各 project 研发经理回传的**本侧任务清单是输入**，其依赖列同样按极大元填。约简缺失**无任何机器告警**（与 `taskType`「漏标是静默的」同款形态），故只能由本条纪律出声。
  - **引擎侧零改动**：引擎不自动约简、不加校验、不新增机器门 / stage 值域 / 产出物。
- **载体升级（标准动作条，v0.9.3 · v0.10.5 按上条改写依赖措辞）**：凡改动载体代码的 Feature（主需求与增补轨同款），在 **DAG 末位登记「载体升级」节点**（依赖**全部实现**链的末端 —— 即按上条取该前序集的**极大元**；由执行单元自升级，回执经该节点 `advance(note)` 留痕；**替代此前另立独立运维 Feature 的形态**）。**「极大元」的约简只在「全部实现」这一前序集内部发生**：把前序集从「全部实现链」缩成「**本侧**链」属**放松**、违反上条「只紧不松」的语义边界，确要如此须另立需求；措辞改写时亦**不得丢掉「实现」二字**（丢掉会把 PjM 工序 / 增补工序吸进末位节点的前序集 = 语义变化）。引擎不为此新增产出物、不引入人判之外的机器门（句式语义回指 `引擎映射.md` §1「不新增」句式的消歧定义，本条不重述）—— 升级在引擎态上就是 `executing` 内的一个节点，「实现完成后、验收前」的时序由依赖关系保证。
- **宿主自办（标准动作条，v0.10.2 · 照「载体升级」「PjM 版本规划工序」先例形态）**：凡**归属写明「由宿主执行」的树外动作**（DAG 节点之外、由宿主亲自办的那类），按下列三条执行 —— **不新增产出物、不引入人判之外的机器门**（句式语义回指 `引擎映射.md` §1「不新增」句式的消歧定义，本条不重述〔不指 `state` / `stage` 值域的枚数〕）：与上述两条标准动作条同款，引擎不为此新增任何能力。
  1. **归属写明「由宿主在树外执行」的动作 ⇒ 宿主自己当轮做完并回填证据** —— **不得**转述为「待用户执行」然后不跟进。**构建、各类载体进程的重启都属此列**；唯一例外 = 该动作受「重启承载宿主自身的进程」这类**结构约束**（宿主无法自办重启时，须显式写明由谁在何时执行，并留痕跟进，不得默认放行）。
  2. **载体升级须清点本次需求改动所触及的全部载体（`{载体清单}`），不得只升一个**：本需求改动落在哪个单元，就升该单元的载体；**多单元同改 ⇒ 多载体同升**（漏升任一个 = 该侧仍以旧码运行）。「哪个单元有哪些载体」的清单是**宿主侧部署事实**，不在本规范内点名，由宿主在改造文档 §5 实施记录内逐单元列明并逐项销号。
  3. **判「载体是否还在跑旧码」用行为探针** —— 拿**本版本新增的一个取值**（如新扩入某枚举的候选值）向该载体打一发：被**结构化拒收**（如 `unknown_<字段名>=<原值>` 一类的错误码）⇒ 该载体还是旧码；放行 ⇒ 已是新码。**不看版本串、不看构建产物时间戳** —— 二者在旧码上都不会报警（版本串可照抄、产物可重建于旧源码之上），只会被动地「看起来已升」；行为探针是本条唯一的判据。
- **PjM 版本规划工序（标准动作条，v0.10.2 · 照「载体升级」先例形态 · v0.10.5 抬为 state `version_planning`）**：凡改动载体代码的**主需求**，在**改造方案确认之后**（`approve` 放行之后、Step 2 之内；**该工序 = state `version_planning`**，即 `approve` 的直接后继，见 `引擎映射.md` §2 表「Step 2 · PjM 版本规划」行与 §4 三步序）由**宿主发起**一道版本规划工序，出场身份是本 project 的**项目经理（PjM）职责位**（见 §0.5 对照表「（方案确认后）排期 / 版本规划评估」行；增补轨不重走本工序，见 Step 3 增补轨条）：
  - **工序内容**：PjM 就「本 project 在本需求下落哪个 Project Version」出**版本规划评估** —— 输入 = 改造文档 §3 In-Scope 的本 project 单元清单 + 边界轮各单元自报的候选号 + 本 project 现有 Project Version；结论经**用户确认**后落定。
  - **工序所在态（v0.10.5 抬态）**：本工序自占一格 state `version_planning`（`approve` 放行后落入、结论落库后宿主 `advance` 出至 `decomposing`），**不再挂在执行段之内**；引擎不为此新增产出物、不引入人判之外的机器门（句式语义回指 `引擎映射.md` §1「不新增」句式的消歧定义，本条不重述）—— 与「载体升级」同款，引擎不为此新增任何能力；时序由「`approve` 之后、`decomposing`（登记 DAG）之前」这一出场时点保证，**该态内不派发任何 DAG 节点**（工序会话是只读同步会话，见 `引擎映射.md` §4 第 3 条注）。
  - **落库顺序硬约束（「先建版 → 再写归属」，不可倒）**：**先**把结论要用到的 Project Version **建版**（经既有 project 版本建版写口），**再**经既有**归属写口**写入该需求的归属记录 —— **倒序必被拒**（归属写口因该 Project Version 尚未登记而拒绝）。建版与写归属**都是宿主动作**，**PjM 只出结论、不自行写库**。
    - **两道守卫在本顺序之前（v0.10.5 写明）**：① **门① 的 `version` 非空守卫** —— 需求确认门过门时该需求登记字段 `version` 为空 ⇒ 引擎**结构化拒收、整单零写入**（`state`/`stage`/`approval` 全不动，见 `引擎映射.md` §3 门表），故根本走不到本工序；② **归属写口的「未过 `approve` ⇒ 拒写」守卫**（见 `引擎映射.md` §3.5）。两道都把门在先，**本顺序只管「建版」与「写归属」这两写之间的先后**，不替代它们。
  - **归属初版回写后置**：`approve` 时**不落**归属记录 —— 归属初版 = 本工序结论的一次回写；执行期新触达的 project 再按本节增量补齐（写点时序见 `引擎映射.md` §3.5）。
  - **代价（登记于正文唯一一处）**：`approve` 与本工序结论落定之间，该需求在 project 版本面**无归属记录（暂空）** —— 已会签为**可接受**，读面（含板 project 级版本视图）**不为此加任何提示**；该空窗是**正常形态**，不得据此判「需求漏配版本」。
- **实现中如偏离改造文档**：实现方式、接口、行为与改造文档不一致时，必须同步更新改造文档（修订历史 +1 版），不得等实现完成后再补。
- **实现中发现 scope 外的问题**：

```
发现新问题
  → 判断是否影响需求A【验收标准】的达成
  → 否 → 超出需求A范围
      → 在主需求改造文档 §6 登记（一句话，不编号）
      → 继续需求A，不中断
  → 是 → 按 Step 3 三档定性判据分流
      → 不改方案边界、不加新行为（小修）→ 增补轨（另立增补 Feature 挂主需求，方案写入主需求改造文档「增补」节 +1 版）
      → 需再次确认方案（方案变）→ 主需求 cancel → 从步骤 0 起新建
```

- **禁止在需求 A 的实现中顺手修需求 B 的问题**。例外：纯格式问题可以直接修并同步说明；≤3 行/≤15min 的低成本修复可以在 CHANGELOG 中备注后直接修，不违反此规则。
- **派给执行单元的任务节点要小**：单节点应能在约 10 分钟内跑完（派发请求超时通常为数百秒，超时即判失败）；大改造拆多个小节点（避免「单节点过大 → 超时/截断」）；派发消息应注明「接近超时 / 上下文上限时先保门禁通过再报告」。
- **二次拆分的过渡期形态（标准动作条，v0.10.2 增补五 · 上条粒度纪律的兜底）**：节点因体量过大而满窗时，「把该失败节点拆小重做」在引擎里**还没有原语**，故按下列过渡形态执行 —— **待引擎补「失败节点可被拆小消解」的原语后本条即废止**（不得留成永久潜规则）。
  1. **先走不涉拆分的既有动作**：满窗先由执行侧既有的自动续跑路径续跑一次（由运行底座承担，本规范不描述其实现）；仍不成立则宿主**原地重派**（同节点、同会话，经 `advance(retryTaskIds)`）。
  2. **判据成立才进「拆」**：满窗 ∧（无实质产出 ∨ 续跑后仍满窗），或同一节点第二次仍失败。
  3. **派该 project 的研发经理复用其 Step 1 会话**出**拆小方案**（小节点清单 + 依赖 + 各自落点 / 判据 / 预估体量 + **下游如何处置**）；该派发为**只读**，**不登记节点**。
  4. **宿主另立承接轨**（`a2a_feature_create(parentFeatureId=本需求)`）并在轨内**重登记**：**须把原失败节点的下游闭包一并搬**；**依赖不得跨 Feature**，先后靠引擎「项目粒度的串行」（§7 同版串行纪律）自然成序。**承接轨的 `approve` 后继 = `decomposing`**（走 `approve → decomposing`，**跳过 `version_planning`** —— 判据 = 该轨挂有父需求 `parentFeatureId`；版本规划已随主轨落定、不重走，同 Step 3 增补轨条同款）。**承接轨同样须过门①（口径见 §2 Step 0）；其《改造文档》档名 = 主需求那一份**。**该步不必 cancel 主轨**：主轨「失败静止」（无可派发、无在飞）**不占名额**（名额口径单处定名见 §7「同版串行纪律」，本处只回指），故主轨停在 `executing` 静止时承接轨仍可过审放行；第 1 步的原地重派路径随之保留、不废。
  5. 承接轨过审后其新节点各为**新会话**（§0.5「会话复用纪律」表第 3 行）⇒ 引擎自动收敛 ⇒ 宿主验货。
  6. **主轨**按既有方式推进收口。
- （可选）鼓励用本系统自身的编排能力实施需求本身，顺带真机验证编排链路。

### Step 3 用户测试 + 反馈

- 动作：实现完成后仅向用户展示变更摘要和测试结果，宿主按两张推进判据清单连推 `integrating → testing → reviewing`，**在 `reviewing` 格前停、等用户反馈**。禁止执行任何回归测试、CHANGELOG 更新、git 操作。本步的出场身份 = **执行单元 agent**（缺省职责位，§0.5 对照表「Step 2 节点执行 / Step 3 验收」行）；增补轨另立 Feature，其各工序按同一对照表各自出场（不在本步内替换出场身份）。
- 判据：**用户明确反馈 = `reviewing → completed` 格的凭据**。用户确认「通过」后，同步更新改造文档修订历史（标记 final 版本）→ 需求完成，等待发版。
- **三档定性判据（分水岭，v0.9.3 成文）**：用户反馈中的问题按对「方案边界」的影响定档，档位决定挂载方式：
  - **小修（不改方案边界、不加新行为）** → 走**增补轨**：**另立增补 Feature** 并经 `a2a_feature_create(parentFeatureId=主需求 featureId)` 挂到主需求下；增补是完整的小需求流程（stage 同链，**含 Step 0 落自己的《需求确认单》，口径见 §2 Step 0**），其方案写入**主需求改造文档的「增补」节（修订历史 +1 版）**，不另立改造文档；确认走增补 Feature 自己的 `approval`/`approve`，其 **`approve` 后继 = `decomposing`**（走 `approve → decomposing`，**跳过 `version_planning`** —— 判据 = 该增补挂有父需求 `parentFeatureId`；不重走 PjM 工序故不进该格，见下）。**主需求最后完成**：主需求最先实现、最后 `completed`，用户验收结论下在**全部增补 completed 之后**。增补 Feature 同样落 §7「同版串行纪律」（与主需求及其它增补不得同时 `executing`）。**同子树互斥（★R3 措辞钉）**：同一主轨子树内（主需求 + 其全部增补轨 + 其承接轨）**同时至多一个 Feature 活跃**；主轨重派前须确认子树内无其它活跃轨。§7 名额口径解除的是**跨子树误计**，**不得读成同子树可并行** —— 上括注那句照原样生效。增补 Feature **必须与主轨同 Group Version**（`version` 一致）；跨 Group Version 的补充**不构成增补**（见下条『新需求』档）。**增补不重走 PjM 版本规划工序**（见 Step 2 该条）：其 Project Version **继承主轨既有结论**；**唯一例外** = 该增补触达**主轨未触达的新 project**，该 project 仍须按同款顺序**先建版、再写归属**。**「不重走工序 ≠ 不写归属」** —— 增补过门后仍须经同一归属写口补齐自己的归属记录。
    > 口径变更（引擎核实 2026-09-26）：此前「实现级增补 → 当前需求 `needs_input → executing` 续推」的写法**作废** —— `needs_input` 仅 `executing` 可进可出、主链无回边、挂载白名单仅 `executing`/`waiting_approval`，终验段（`integrating`/`testing`/`reviewing`）无该路径。`needs_input` 回归其唯一语义：**执行期任务澄清**（见 `引擎映射.md` §2 / §6）。
  - **方案变（需用户再次确认方案 / 整体回炉）** → **主需求以 `a2a_feature_cancel` 终止** → 从步骤 0 起新建（新方案重走 `approve` 门）。
  - **新需求（影响使用或结构、与当前需求验收无关）** → 用户先确认当前需求的完成状态 → 进入需求池 → 从步骤 0 开始新需求。**跨 Group Version 的补充需求一律按新需求处理**：不复用主轨的增补轨与改造文档『增补』节，从 Step 0 新建。
- 发现非影响性改进点 → 一句话登记到主需求改造文档 §6，不展开。
- **验收须显式列「未覆盖验证项」**：凡「改了但未在真机碰到 / 未触发」的项（如未配置某端、需受控重启才能触发），验收时必须列出（含原因）并登记改造文档 §6，不得默认算通过。
- **编排链路改动必须真机 E2E**：凡改动「编排链路」（怎么派活、怎么收结果）的版本，Step 3 必须有一次真机端到端（真实执行单元拉起 → 派发 → 执行 → 回传）；若确以离线自测放行，必须在改造文档 §6 显式登记为遗留验证项，不得算通过（离线断言会掩盖真实缺口）。

**Step 3 的两张推进判据清单（v0.9.1 起）**

`approve` 之后 `version_planning → decomposing` 两格由宿主推进（凭据 = PjM 结论与用户确认 / 各 project 研发经理本侧清单），**其人不设门**。`executing → integrating` 之后的 `testing → reviewing`、`reviewing → completed` 两格由宿主 `advance` 驱动（见 `引擎映射.md` §2）。以下两张清单是**宿主侧的人判清单**——「每格推进前该核什么」的成文口径，**不是引擎的前置校验**（引擎不新增任何机器门）：

- **进「验收」前（testing → reviewing）**：
  1. **单元门禁全绿**——相关单元 typecheck / 单测通过，引用 Step 2 收口回执为凭；**根回归不前置**（回归属发版门，本步禁止执行，见上文动作条与 §1 绝对规则）。
  2. **真机验收动作完成并有回执**——回执载体 = `advance(note)` 留痕 + 改造文档修订历史（+1 版）。
  3. **未覆盖项已登记**——按上文「验收须显式列『未覆盖验证项』」条执行（回指该条，不另抄口径）。
- **进「完成」前（reviewing → completed）**：
  1. **用户验收结论明确**——用户原话留痕（经 `advance(note)` 承载）。
  2. **改造文档修订历史含 final 行**——字面口径与发版回归检测一致（修订历史表存在 `final` 行）。
  3. **全部增补已收口**——本需求名下增补 Feature 均已 `completed`（主需求最后完成，见上文三档定性判据）（此处「收口」= 增补轨的**交付结论**，须 `completed`；与 §8 发版完成集合 {completed, cancelled} 语义不同，**不得互推**）。
  4. **父改造文档 final 对照最新实现**——final 版的方案 / In Scope / 验收标准与含增补后的最新实现一致。
  5. **遗留待办均已登记去处**——未排期想法进需求池卡片，登记类项在主需求改造文档 §6，不得默认算完成。

- **各阶段文档（需求确认单 / 改造文档等）落盘后，推进时经 `a2a_feature_advance` 的 `decisions` 数组登记文档路径**（每份一条；`decisions` 在引擎是**整值替换** —— 「append」是**调用方纪律**：每次登记须把既有条目连同新条目**全量重发**，只发新枚会把在册项打没）。登记的文档路径 = **操作面解析目录的凭据**，供板上「产出登记」区关联展示；`note` 留作当轮说明，不承载文档清单。

### 每步推进的强制条件

需求从 Step 0 → Step 1、Step 1 → Step 2、Step 2 → Step 3 推进之前，必须满足以下判据，否则不得进入下一步：

1. **文档已落地**：当前步骤对应文档已写入 `doc/{版本}/` 目录。
   - Step 0 输出：`{topic}-需求确认单.md`
   - Step 1 输出：`{topic}-改造文档.md`
   - Step 2/3 如有修订：同步更新改造文档（修订历史 +1 版）
2. **需求池标记以引擎为准（v0.10.5 事实源抬为 `state`）**：需求「当前步骤」的事实源 = 引擎主链 `state`；登记字段 `stage` 只是 `state` 的**观测面读投影**（`approval` 记两道门、`version` 记排期），三者的值域、两条写路径与映射**单源在 `引擎映射.md` §3.5**，本条只回指、**不另存一份字段值**（读面 = 板需求池 + 排期面 + 板 **project 级版本视图**），不再另记台账（v0.9.3 起 planlog 版本待办退役，见 §7）。

## 3. 多轮对话流程纪律（AI 遵守）

AI 在跨轮对话中执行流程时，必须遵守以下纪律：

```
1. 每轮只进一个步骤
   用户的"确认/同意"只针对当前步骤，不隐含对后续步骤的授权。
   → 用户说"好"→ 只代表当前步骤通过，不能自动进入下一步。

2. 不得跨步输出
   禁止在同一轮回复中同时完成多个步骤。
   → 举例：不能在同一轮既输出需求确认单（步骤0）又输出改造文档（步骤1）。
   → 必须等用户对当前步骤的输出做出反应后，再进入下一步。

3. TODO continuation 不推进流程
   系统触发继续执行时，只完成当前已授权步骤内的剩余工作。
   → 步骤 2 的实现中途被系统 continuation 触发 → 继续实现，不自行进入步骤 3。
   → 步骤 3 被 continuation 触发 → 等待用户反馈结果或决策，不自行进入发版流程。

4. 每轮重置意图判断
   用户新的一轮输入，只根据本轮内容判断意图。
   → 用户说"改一下"→ 重新判断是哪个步骤，不是默认进入"实现"阶段（步骤 2）。
   → 用户说"看看效果"→ 只做展示/说明，不是默认进入"测试"阶段（步骤 3）。
   → 用户说"发版"→ 才进入发版流程。
```

## 4. 文档命名规范

每个需求在 Step 0 和 Step 1 必须产出两个文件，命名统一为：

| 文档 | 文件路径 | 命名格式 |
|------|----------|----------|
| 需求确认单 | `doc/{版本}/{topic}-需求确认单.md` | `{topic}-需求确认单.md` |
| 改造文档 | `doc/{版本}/{topic}-改造文档.md` | `{topic}-改造文档.md` |
| 未排期停靠（池内卡）的两档文档 | `doc/pool/{topic}-需求确认单.md` · `doc/pool/{topic}-改造文档.md` | 与上两行**完全相同**（`{topic}-需求确认单.md` / `{topic}-改造文档.md`） |

- **`doc/pool/` 是唯一非版本目录**：上表 `{版本}` = 该需求登记字段 `version` 所指的 Group Version；`version` 为空（未排期停靠）⇒ 落点 = `doc/pool/`，**不设版本子目录**。卡片开始 Step 0 即把《需求确认单》写入 `doc/pool/`；**排期 ⇒ `mv` 至 `doc/{新版本}/`（走 §7「改版纪律」第二档）；撤排期回池 / 所属版本被删 ⇒ `mv` 回 `doc/pool/`**。
- **`pool` 不是版本号** —— 它只是未排期停靠档的目录名，不是 `{版本}` 的一个取值（`{版本}` 的指代域见 §7「两级版本与 Project Version」）。
- `{topic}` 为该需求的简短中文摘要（5-10 字），同一个需求的两个文件使用同一 `{topic}`，便于配对和追溯。
- 禁止单独使用 `需求确认单.md`、`改造文档.md` 等无 topic 前缀的文件名。
- 禁止混用 `方案`、`方案设计`、`实现方案`、`修复`、`优化`、`分析` 等后缀，统一使用 `改造文档` 作为后缀。
- **README 只做整体架构 / 使用说明**：逐键配置语义可外置到同目录 `配置说明.md`；不写版本号（`vX.Y.Z`）与需求 / 版本历史——版本历史归 `CHANGELOG.md`，需求与设计归 `doc/{版本}/`（未排期归 `doc/pool/`）。

## 5. 开发中的文档同步

```
代码改动后必须同步更新文档，不允许出现「代码改了，文档还停在原版」的情况。
```

- 实现完成后立即检查 `doc/{版本}/` 是否需要更新
- 发版前必须做一次文档对齐，确保文档与代码一致
- 架构图、数据流、字段说明必须与实际代码对应

**文档更新时机（必须遵循）**：

| 时机 | 动作 | 修订历史标记 |
|------|------|-------------|
| 改造文档初稿完成 | 写入 `doc/{版本}/` | v1 |
| 实现中偏离原方案（接口/行为/范围变化） | 立即同步更新 | +1 版（v2、v3…） |
| 二次修改（用户测试发现问题后） | 修改代码后同步更新 | +1 版 |
| 增补轨定案（小修挂主需求，见 §2 Step 3） | 方案写入主需求改造文档「增补」节 | +1 版 |
| 用户确认测试通过后 | 最终审核对齐 | 标记 final 版本（final 版须对照含增补的最新实现） |

**登记字段与文档同步（v0.9.0；v0.10.0 事实源口径微调）**：`stage`/`version`/`approval` 的**唯一事实源在引擎**（版本台账与排期/发版锁同在引擎执法；本规范中「引擎」= 编排单元 `orch`，「编排桥」= 其常驻服务面），文档与任何台账不得另存一份字段值；登记字段的迁移与本节文档动作绑定 —— 需求确认单经用户确认 ⇒ `stage`「需求分析 → 改造方案」；改造文档落文件 ⇒ `approval`「未发起 → 待审批」（该档名另为门② 的 ⑥，未登记 ⇒ 拒，见 `引擎映射.md` §3 门②行）；用户确认改造文档 ⇒ `approve` 落 `approval = 已通过`。**登记字段的引擎派生写**（引擎随 `state` 迁移的**同轮派生写入** `stage`，写路径见 `引擎映射.md` §3.5）**不触发**本段文档动作绑定 —— **不产生**修订历史 +1 版、**不要求**搬任何文档；绑定只挂在上句三处既有句式的人判动作上，派生写不构成第四处。板排期写（v0.9.2，仅写 `version`；v0.10.0 起经引擎排期写口执法）**不触发**本段文档动作绑定（改版不要求搬文档；有产出物的改版走 §7 改版纪律第二档：`version` 写经引擎，文档搬运由板/宿主执行〔mv 分家，见 §7〕并回写 `decisions`）。**文档仍是确认内容的事实源，登记字段只承载确认动作（谁 / 何时 / 对哪个阶段）**（见 `引擎映射.md` §3.5）。**归属（承诺集）事实源在引擎**（v0.10.1 起）：一条需求在本 Group Version 内触达哪些 project、各自落哪个 Project Version，以引擎的归属记录为唯一事实源；改造文档 §3 In-Scope 的单元清单是 **PjM 版本规划工序的输入**、归属记录是该工序的**输出**（过门之后由该工序结论经归属写口回写落库，见 §2 Step 2；二者不得并列为两个归属来源），**文档不得另存一份归属**，二者不一致时以引擎为准并同步文档。

## 6. 测试中的问题处理

回归测试或日常测试中发现的问题，**不得擅自修复**，必须走以下流程：

```
发现缺陷或异常
  → 记录问题现象
  → 分析根因 + 修复方案
  → 向用户汇报
  → 等待用户确认
  → 确认后再修改
  → 修改后重新测试
```

**例外**：纯格式问题（缩进、空格、注释）或 CI 配置修复，可以直接修并同步说明。

## 7. 版本管理

### 版本号规则

```
v<major>.<minor>.<patch>
```

### 两级版本与 Project Version（v0.10.1 新增）

版本对象分两级，**两级并存、各自记账**：

- **Group Version（组版本）** = 现有 `(owner_group, version)` 版本台账所记的号，语义不变 —— 它是**协调号 / 列车号**（一个版本内累计哪些需求、是否已发版）。本规范中 `doc/{版本}/`、`reports/v{版本}/` 等处的 `{版本}` **一律指 Group Version**。`doc/pool/` 是未排期停靠档、不构成版本档，不在此指代域内（见 §4）。
- **Project Version（项目版本）** = 每个 project 自己的版本号，按 `(owner_group, project_id, version)` 记在引擎的 **project 台账**，**不要求**与 Group Version 一致。一条需求触达哪些 project、各自落哪个 Project Version，构成该需求的**归属（承诺集）**，事实源在引擎（见 §5）。

**不变式**：同一 Group Version + 同一 project + 同一条主轨（含其全部增补）⇒ 同一 Project Version。落地方式为「**已存在则继承、不存在则新建**」；无父的主轨不受此约束；不做前瞻（判据只对已存在的承诺成立）。

**Project Version 的四条规则（PjM 接管档 · 版本号由本 project 的项目经理定）**：

定版者 = 本 project 的**项目经理（PjM）职责位**（见 §0.5）。链路：**边界轮各 project 单元自报候选号**（= 工序输入）→ **改造方案确认之后**由 PjM 出**版本规划评估** → 用户确认结论 → **宿主**按「**先建版、再写归属**」的顺序经既有写口落库（**PjM 只出结论、不自行写库**）。工序全文见 §2 Step 2「PjM 版本规划工序」。

> **接管说明（v0.10.2）**：此前「边界轮自报候选号 + 用户过门确认时顺带落库」的**代行档已由本档接管** —— 定版动作从「过门当轮的顺带结果」抬为「过门之后的一道工序」，归属初版随之**回写后置**（`approve` 不落归属，见 `引擎映射.md` §3.5）。**不变的部分**：版本号仍由 project 侧定、不引入新角色实体、不引入新机器门、不引入新 stage 值域；下述四条规则本身不动。

1. **缺省**：project 的首版继承当时的 Group Version 数值（一次性对齐，避免 `0.0.0` 噪音）。**无 `package.json` 载体的 project（如本流程规范包 `flow` 自身），其 Project Version 载体 = 本包的规范版本戳**，project 台账仍记同一数值 —— **不得因无 `package.json` 而视该 project 为「无版本」**。
2. **冲突**：同一 `(owner_group, project_id, version)` 重复建 ⇒ 拒绝（409）。
3. **改版**：某 Project Version **一经被归属引用即不可改**；仅在「未发版 ∧ 无任何归属」时可删可重建。
4. **复用**：**一经 `released` 即冻结，不得复用为后续归属目标**；要再发版必须抬到一个未 `released` 的号。

**预检**：各 project 单元在**边界轮自报候选版本号时，须对照已 `released` 的号并避开**；候选号随后由 PjM 在版本规划评估中复核，**冲突须在归属写入之前（§2 Step 2「先建版 → 再写归属」的那一步）收敛掉** —— 过门（`approve`）不再是收敛的截止点，因为归属初版已回写后置；引擎的冲突门只作兜底。

**与既有纪律的分工（术语对齐）**：本规范所称「**单元**」= 引擎项目面中的一个 project。下文「单元版本同升纪律」管的是「**何时必须对齐版本号**」（协议契约约束），Project Version 管的是「**版本号的身份与落库**」，**二者正交**，不得互相推断。**协议对端组的同升是部署约束，不被「project 版本号各自独立」豁免** —— 两侧要真并行运行的前提仍是同升，这跟 project 版本面是否独立记账无关。

**两级计数不得互校**：Group 侧收口计数由需求登记字段 `version` 派生，project 侧计数由归属记录派生，**两个计数不得横向相加、也不得要求相等**（同名版号在两级里互不染色）。

**发版是一个动作 + 级联**：发版只有**一个动作** —— 标记 Group Version 为 `released`；引擎在同一事务内把它名下**被触达**的 project 版本一并置 `released`（随后按上文四条规则的第 4 款冻结）。**不存在「某个 project 自己发自己的版」这一独立动作**；project 侧的收口判据**仅作展示字段**（供板与人对照），不是第二道发版门。未被该版任何需求触达的 project 不产生 project 版本行、不被发版。

### 单元版本同升纪律（按兼容契约分组 · v0.10.0 新增）

一个版本内的多个单元（可交付组件）**不默认同升**。v0.10.0 起停用「所有单元的 `package.json` 与 lock 一并 +1」的口径，改为**按兼容契约分组**——只有落在同一兼容契约内的单元才必须同升。

1. **协议对端成组**：两个单元之间若存在**双向协议契约**（互发请求体并据此判定 / 消费），则互为**协议对端**，构成一组 —— **组内协议版本必须一致**。协议版本按协议契约自身的版本规则演进，判据为：**可被对端完全忽略且不影响任何判定 / 消费语义的新增字段 ⇒ 不升版**（沿用当前协议版本）；**把可选 / 无约束项收紧为必填、变更取值集合成员、删字段、改字段语义、加必填请求体或必填参数 ⇒ 升版**。其中**单向不兼容的变更（更名 / 移除成员）须由部署侧在同一切换窗口内两侧同升，不得跨版本混跑**。
2. **产品版本各自独立**：成组约束**只作用于协议版本，不作用于产品版本** —— 组内各单元的发布版本号（各自 `package.json` 的 `version`）**各自独立**；下一版只动其中一个单元时，另一个**不随升**，**除非协议版本变了**。
3. **`board` 独立**：板与编排侧之间只有**只读查询面**（读状态、向对方发意图的 HTTP / MCP 面），**无双向协议锚** ⇒ 不构成协议对端、**不随任何单元同升**，版本单独走。
4. **`flow` 不参与同升**：本流程规范包**无 `package.json`**，不持有产品版本号，因此**不参与任何同升组**；但本包各文件的「**规范版本戳**」**仍随版本走**（每版齐翻；本口径本版保留，未与产品版本解耦）。**本包规范戳是本侧清单的唯一成员**：宿主侧对本包规范的**镜像快照**（宿主配置文件 / 工作区指令里内嵌的规范正文）**随版重导属宿主责任**，不在本包四戳清单内，本包不得据镜像未翻判本包漏戳。

> **分组判据的事实源 = 协议契约中的协议版本本身**，不在本规范内另存一份。本规范只写流程语义，**不引用协议契约的文件路径**（本包可整体复制到任意项目，跨包路径引用在复制后即悬空）。
> **落到发版操作**：同属一个版本 ≠ 同一个版本号 —— 各组可各自发版、各自记版本。不得因「同属一个版本」而强行对齐版本号，也不得因「另一单元未动」而阻挡本单元发版。

### REQ-ID 规则

- 格式：`REQ-YYYY-MM-DD-XX`，其中 `XX` 为**当日全仓序号**（v0.9.3 起去版本段——需求所属版本是引擎登记字段 `version`，可随排期改版，不进编号）。
- **存量号一律不迁移**：既有文档中的 `REQ-{版本}-YYYY-MM-DD-XX` 旧号保持原样；新格式自本修订落地后的**下一条新需求**起用。
- 同一需求的需求确认单与改造文档使用**同一个 REQ-ID**，便于配对追溯。
- 改造文档中引用需求时，写成 `REQ-YYYY-MM-DD-XX` 形式（引用存量旧需求时可照旧号原样引用）。

| 原 planlog 职能 | 新落点 |

| 版本待办（需求清单与状态） | 引擎登记字段 + 板需求池/排期面 |

> **过渡判据（本版新增格零回填）**：新入主链的两格其**唯一入边来自 `waiting_approval`**（只有 `approve` 这一个动作能进；v0.10.5 增补：该断言现由引擎**行前提**执法，不再只是叙述 —— 见 `引擎映射.md` §3 门②行）⇒ 存量需求早已离开 `waiting_approval` ⇒ 对这两格**结构上不可达、不回填**：它们的 `stage` 停留在各自最后一次写入的值，直至下一次真实迁移才归位（该滞后是**已知观测面噪音**，不得据此判「数据异常」，也不为此做任何一次性数据迁移）；本判据**只对新需求生效**。**判据 = 状态图结构本身，不引入任何日期或版本号阈值。**

**同版串行纪律（名额口径 · 全包单处定名，v0.10.5）**：**同一版本内的多条需求必须串行推进**（一次只推进一条需求走到终点，再起下一条；「需求间并行」不排期，已废弃）—— 引擎只提供**项目粒度**的串行、**不提供需求间串行**，故串行只能由宿主在「过审」放行的时点把控（细则见 `引擎映射.md` §4.1；增补 Feature 同版本内一并排队）。

- **定名「在占名额」** = 该 Feature 处于 { 活跃 `executing`、`version_planning`、`decomposing` } 之一。**本条是全包唯一的集合定义处** —— 其余各处提到「名额」一律只回指本条，**不得再列这三枚态**。
- **主轨「失败静止」不占名额**：停在 `executing` 的**失败静止**主轨**不占名额**（「失败静止」的判据不在本处重述，见 `引擎映射.md` §4 三步序第 4 条的二分判据）。
- **增补轨与承接轨同规**：两者都按**主轨**的同一套名额校验出场，且**不计为第二条主轨** —— 同版本内并存的增补 / 承接轨不额外占用名额（各自的 `approve` 后继口径见 §2 Step 3「增补轨」条与 §2 Step 2「二次拆分的过渡期形态」，本条不重述）。
- **同子树互斥**：同一主轨子树内（主需求 + 其全部增补轨 + 其承接轨）**同时至多一个 Feature 活跃**；主轨重派前须确认子树内无其它活跃轨。
- **名额至多一**：**禁止两个及以上主轨同时处于 `executing`**（原句照本条特例形态生效，不得因本条改写而删）；下一条主轨的 `approve` 时点 = 前一条主轨的「在占名额」清空。
- **纯流程纪律，引擎不执法**：引擎不校验名额、不产生拒绝、无任何机器告警（漏把名额是**静默的**，与 `taskType`「漏标是静默的」同款形态）—— 本条只能由宿主在「过审」放行的时点自行把门。

> **显示过滤不改事实源（v0.9.x）**：板各列对需求卡的显示过滤（含终态卡）属操作面职责，不写入引擎，也不得作为 §8 收口与标记 `released` 闸的计数数据源。任一需求实体在板面须**至少有一处可读**；未排期且终态的卡在板面无清单读面（组织空间需求清单读面已随 v0.9.6 组织作用域收敛退役），历史读面 = 经引擎 `a2a_feature_status` / `a2a_feature_trace` 查阅；不得因需求池不显示而默认算完成。

### 改版纪律（v0.9.3 新增）

需求在版本间挪动（改 `version`）按当前所处状态分档 —— 前两条是「可挪」的两种形态，第三条是过门后的收口条：

1. **想法挪版（零善后）**：`stage = 需求分析` ∧ `approval = 未发起` ∧ 无 `decisions` 产出物登记 ⇒ 直接改版（板排期拖拽直达），不触发任何文档动作绑定（见 §5）。
2. **有产出物的改版（收窄档，v0.10.1 · v0.10.7 起扩含「撤排期回池」两向）**：产出物已落文件（已登记 `decisions`）**但两道门皆未过**（`stage = 需求分析` ∧ `approval = 未发起`）⇒ **自动善后**：写 `version`（排期 = 写入新版号；撤排期回池 = 清空。经引擎排期写口，见下方「文档 mv 分家」条）+ 将 `decisions` 登记文档 `mv` 至目标目录 + `decisions` 登记新路径（引擎对该数组是**整值替换** ⇒ 既有条目须连同新条目**全量重发**，口径见 §2 末条）。**`mv` 目标目录双取值**：排期走**池 → 版** = `doc/pool/` → `doc/{新版本}/`；撤排期回池走**版 → 池** = `doc/{旧版}/` → `doc/pool/`（**含**下文「版本删除纪律」乙档清 `version` 的路径）。**两档不合并**：甲档（`state = cancelled`）**不走本条、文档不搬**。**过渡态**：板受限 mv 能力落地前（v0.9.3 需求 2 承载），改版善后由宿主手工执行同等步骤。planlog 同步职能已退役，遗留台账的对账降级为宿主**择机**执行（非改版阻塞条件）。
3. **过门之后不可挪版**（v0.10.1 收口条）：任一确认门已过（`stage` 迁至「改造方案」，或 `approval` 置 `待审批`/`已通过`）⇒ **该需求的 Group Version 不得再挪**（排期写状态锁的判据本就在第二档处收口，此处把规范口径对齐到锁）。此时方案与版本的绑定关系要变，**唯一出路是 §2 Step 3 的「方案变」档**：主需求 `cancel` → 从步骤 0 起新建，新卡重排到新 Group Version，归属在新卡过门后落。**唯一例外 = §7「版本删除纪律」** —— 该纪律下 `cancelled` 卡随台账行删除被清空 `version`，**不属本条的「挪版」**（本条管的是在两个存量版本之间改排期）。
   > **登记为既有规范缺陷（v0.10.1 核实）**：本节第二档在收窄之前**常规定义不可达** —— 挡点在需求确认门（`stage` 迁「改造方案」）而非 `approve` 门，与排期写状态锁的判据并不重合。本版**只改规范文本、不改锁的判据**。

**文档 mv 分家（v0.10.0 新增）**：改版善后的两类写**分家执行** —— `version` 写改道引擎（事实源在引擎，经 §2 Step 3 登记字段特例，排期写锁与 `released` 锁由引擎在事实源进程执法）；**文档 `mv` 仍由板/宿主执行**（文件系统不在引擎，引擎不碰 `doc/{版本}/`）。`decisions` 追加新路径经同一引擎写口登记。**撤排期回池与删版清 `version` 同款适用**（回池方向的两类写也分家：`version` 清空经引擎写口、文档 `mv` 回 `doc/pool/` 由板/宿主执行）。

**改版与归属的派生不变式（v0.10.1）**：归属记录所带的组版本，与该需求登记字段 `version` **同一写单定值、此后不漂移** —— 不存在「归属跟着 `version` 事后失效」这样一个流程动作（它是派生事实，不是待办）。因此**本节第二档的善后不含任何归属动作**：第二档恒在过门之前，而过门之前不落归属（见 §7「两级版本与 Project Version」与 `引擎映射.md` §3.5）。**无 Group Version ⇒ 无归属记录**，由该需求后续排期（写定 `version` 并过门）时补齐。**唯一例外 = §7「版本删除纪律」** —— 删版使归属记录所带组版本随台账行消解而成为该条所称的**只读历史引用**（不删、不回写、亦不改写），**不属本句的「漂移」**（不存在第二个版本值写入）。

**已发版锁叠加**：目标版本或原版本已在**引擎版本台账**中标记为 `released` ⇒ 不得排入/改动排期（事实源 = 引擎，板为读投影；见 §8）。桥不可达时板取**最后一次投影**判锁，**锁只紧不松**（拿不到台账投影 ⇒ 挡排期写，fail-closed，不得当作未发版放行）。

**排期写状态锁**：排期写仅 `stage = 需求分析` ∧ `approval = 未发起` 可写（**引擎执法**，409 `board_schedule_state_locked`；板为发起方与展示方）；宿主经 MCP 直写 `version` 同受引擎执法（后门不豁免）。**未排期停靠合法 ∧ 门① 需 `version` 非空（本句在全包的唯一落点）**：`version` 为空的需求卡停在需求池是**合法形态** —— 本锁对它开着、引擎不为此产生任何告警；但**需求确认门（门①）过门以该需求的 `version` 非空为前提** —— 未排期就过门 ⇒ 引擎**结构化拒收、整单零写入**（`state` / `stage` / `approval` 全不动，见 `引擎映射.md` §3 门表），拒后 `stage` 仍 `需求分析` ⇒ 本锁仍开 ⇒ 补写 `version` 后可重试。两句合起来的顺序含义：**「先排期写 `version`、再过门①」是唯一路径**，不存在「过了门① 再回头补排期」的形态（本条只写语义；拒因的错误码字面属执法原文，不进本包）。

**版本删除纪律（v0.10.7 新增）**：**Group Version 的删除 = 引擎版本台账行的删除与名下卡 `version` 清空的同一事务** —— 两笔写分步执行即成「幽灵版号链」（台账行已消而卡上仍挂该版号，或反之）。本条是 Group 档删除的**唯一规范落点**：引擎的放行判据与操作面的可达面都照本条，不另存一份。

- **放行判据（三条全过，任一不过 ⇒ 拒删、零写入，拒因带卡清单）**：
  1. **台账行存在 ∧ 版本状态在白名单内**：`status ∈ {`notstart`, `active`}`（即未开始、进行中 —— 三态值域单源在 `引擎映射.md` §3.5，本条只按名指称、不另立值域、不扩闭集）。表未就绪 / 无行 / 非法值 ⇒ **拒**（**只紧不松** —— 读不到即挡，不得当作可删放行）；`released`（已发版）不在放行集（回指上文「四条规则」第 4 款，不另述）。
  2. **名下每一张卡均属甲档或乙档**：**甲档** = `state = cancelled`；**乙档** = **未收口**（「收口」口径见 §8「收口口径」条，本条不另存一份）∧ `stage = 需求分析` ∧ `approval = 未发起`。两枚反例形须点名：`stage = 改造方案` ∧ `approval = 未发起`、`stage = 需求分析` ∧ `approval = 待审批` —— **`stage` 与 `approval` 是两次独立登记写、不保证同序，不得以 `stage` 单枚代判**。
     - **`completed` 卡挡删（明示判据，不是推论）**：清其 `version` 会使**已交付的卡**落入「未排期 ∧ 终态」的无清单读面档（见上文「显示过滤不改事实源」条），交付账随之断链。
     - **未收口且不处乙档的卡同样挡删**（含上列两枚反例形）。
  3. **删除不查归属行**：名下卡的归属记录**不随删版删除、不回写**，其组版本随台账行消解而成为**只读历史引用**（读面容忍该引用无对应台账行）；**亦不撤 project 台账行**。
- **两档善后分写、不得合并**：**甲档**（`cancelled`）⇒ 卡回需求池、**文档不搬**；**乙档**（未收口 ∧ `stage = 需求分析` ∧ `approval = 未发起` ∧ 已登记 `decisions`）⇒ 卡回需求池、其 `decisions` 登记文档**按上文「改版纪律」第二档的善后形态** `mv` 至未排期落点 `doc/pool/`。**已删版本的目录 = 历史档**（不得删、不得改写其中文档的 REQ-ID 与版本归属行）。删版清 `version` 使甲档卡**转入「显示过滤不改事实源」条既有的「未排期 ∧ 终态」无清单读面档** —— 本纪律是该档的一个**新入口**，不新设判据、不放松该条；**不得据「板面看不到」判交付遗漏**（历史读面 = 经引擎 `a2a_feature_status` / `a2a_feature_trace` 查阅）。
- **版号永久占用（本纪律的派生后果，须点明）**：project 台账行不撤 + 归属行不撤 ⇒ 上文「四条规则」第 3 款的「未发版 ∧ 无任何归属」**永不成立** ⇒ 该 Project Version **不可改、不可删、不可复用**（一经 `released` 后另按第 4 款冻结），即使其所属 Group 版已被删。**操作面附注**：若确需释放该 project 版号，由宿主在操作面先行撤归属（既有 project 台账删版口）—— 这是操作面手段，**非引擎判据、非机器前置**。
- **两级判据分立**：本条只管 **Group 档**的删除，与上文「四条规则」第 3 款（**project 档**）**不同构、不得互推**。
- **可达面同构**：操作面对删除版本的可达面须与本条判据**同构**，不得另存一份判据；两侧不一致时**以引擎为准**。
- **存量不迁移**：本条只对**新版**的删除生效，不追溯改写既有数据。

## 8. 发版流程（Release Flow）

当用户决定发布当前版本时执行。发版流程独立于需求流程，不对应某个具体需求。

```
0. 检查引擎需求状态 — 经引擎 Release 聚合面（「版本 → 需求集合」只读查询）确认当前版本名下全部需求实体均已收口（终态 ∈ {completed, cancelled}；failed 不算收口 —— 须先经 cancel 归档，见「收口口径」条）
1. 发版前文档审核：
   a. 审核 doc/{版本}/ 文档，确认与实际代码一致（已在需求流程中同步完成，此处仅验证）
   b. 更新 CHANGELOG.md，记录本次版本所有变更（记账面按 repo 落 · 见下「记账 / 身份分家」条）
   c. 更新 README.md（如有架构、API 或流程变化）
   d. 检查回归测试脚本，确认已有用例覆盖当前版本所有新增模块和检测项，
      如有新模块/新文件需补充对应检测用例
   e. 补充完善组级产品文档（出场 = 组级产品负责人，见 §0.5「组级职责」块；本行只写写点，不写实现载体）
2. {回归测试命令}
3. 检查 reports/v{版本号}/regression-report.json 确认全部通过，用于版本记录（{版本号} = Group Version）
4. git add + commit
5. git tag <project>/vX.Y.Z —— 按本次触达的每个 project 各打一枚（该 project 的 Project Version）；Group 级整体列车 tag 可另打，两者不互斥
6. git push && git push --tags（同步到远程仓库）
7. 发布到目标环境
```

> **记账 / 身份分家（v0.10.1 新增）**：**版本身份与 tag 按 project 落**（命名空间 `<project>/vX.Y.Z`，取该 project 自己的 Project Version），**发版记账（git commit / CHANGELOG / 回归报告）按 repo 落**。单仓多 project 时，**同一次 commit 可承载多个 project 的 tag** —— 这是分家的正常形态，不是异常。Group 级整体列车 tag 与 project tag **不互斥**（可以两个都打）。`doc/{版本}/` 与 `reports/v{版本号}/` 里的 `{版本}` / `{版本号}` **指代钉为 Group Version**（文档与回归报告不分 project）。`doc/pool/` 是未排期停靠档、不构成版本档，不在此指代域内（见 §4）。

> **收口口径（v0.9.5 起；v0.10.0 执行方改引擎）**：「收口」= 需求实体终态 ∈ {`completed`, `cancelled`}；`cancelled` 语义 = 该轨已终止、无遗留待办（**非豁免或缺陷绕行**）；`failed` 不计入收口（须先经 `cancel` 归档，见 `引擎映射.md` §6）。**收口是发版的必要非充分条件：版本名下全部卡均为 `cancelled`（无一张 `completed`）⇒ 该版本无任何交付，不得标记 `released`。** 本节「收口」专指**发版判据的完成集合**，不指 §2 Step 2 H3 的「收口自检」。判据本身不因事实源翻转而改动；v0.10.0 起收口核算由**引擎 Release 聚合面**执行（板不再以本地台账充当数据源）。**v0.10.1 补：本节的收口判据是 Group 级的、也是本版唯一的发版判据** —— 收口核算只看 Group Version 名下的需求集合，**不存在与之并列的 project 级第二道发版门**（project 侧口径见下「发版一个动作 + 级联」条）。

> **回归测试**：发版前必须执行回归测试，且必须先更新回归测试用例，再运行。每个版本有新文件、新模块时，必须在回归测试脚本中补充对应检测项（文件存在性、exports、依赖声明等）。
> **git push 代理兜底**：上传远程仓库（发版步骤 6 及一切 push）直连失败时（连接重置 / 空响应 / 无法连接 443），可改走本机代理重试：`git -c http.proxy=<proxy> -c https.proxy=<proxy> push`；推送成功后不必改全局 git 配置，仅当次命令级注入即可。
> **标记 `released`（v0.9.4 起 · v0.10.0 事实源落引擎，原「登记已发版版本 v0.9.2」）**：发版步骤 4–7 完成后，将版本标记为 `released` —— **事实源 = 引擎版本台账**（板为发起方与展示方，向引擎发意图；板的本地版本文件降为读缓存/降级投影，不再是写目标）。**标记闸由引擎在事实源进程执法** = 该版本名下全部需求实体均已**收口**（与步骤 0 同判据；含 `failed` ⇒ 未收口、挡闸），不满足 ⇒ 引擎拒绝标记；已发版版本不再排入/改动需求排期；宿主经 MCP 直写 `version` 同受引擎执法（**引擎侧强制，非板**）。桥不可达时板取**最后一次引擎台账投影**判锁，**锁只紧不松**（拿不到投影 ⇒ 挡排期写，fail-closed，不得当作未发版放行）。
> **发版一个动作 + 级联（v0.10.1）**：本节只有**一个**发版动作 = 标记 **Group Version** 为 `released`。引擎在同一事务内把该 Group Version 名下**被触达**的 project 版本一并置 `released`（随即冻结，见 §7 四条规则第 4 款），交付事实随同落入交付快照。**因此不存在「Group 已发版而某 project 仍 `open`」这一存续形态**，也不需要为 project 另开一道发版口。**project 侧的收口判据降为展示字段**（板/人可对照着看，不产生拒绝、不构成门）；Group 计数与 project 计数**不得横向相加或相等校验**（见 §7）。
> **登记 `stage = 发版`（v0.9.0 · v0.10.0 跟随事实源）**：发版步骤 4–7 完成后，宿主将本版本已发版需求的 `stage` 写为 `发版` —— 经 `a2a_feature_advance` 的「`to` = 当前态 ∧ 带登记字段」特例（**不改状态机态**；该特例无终态守卫，`completed` 后仍可写入，见 `引擎映射.md` §3.5）。（`cancelled` 卡**不参与**此写入 —— 其轨未交付任何内容，写 `发版` 会在版本面误导；引擎 Release 聚合面的完成集合计数不受此影响。）**`stage = 发版` 保持 Group 级（v0.10.1）**：project 级的发版凭据只落 project 台账与交付快照，**不扩 `stage` 值域**、不为 project 另立阶段。
