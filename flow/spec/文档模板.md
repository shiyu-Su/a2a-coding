# 文档模板

> 本文件是需求流程产出物（需求确认单 / 改造文档）的模板单一来源，与流程规范内核 `需求流程.md` 配套使用。
> 落地到项目时，可将本文件复制到项目的模板目录（如 `doc/_templates/`）；引入本规范包时保持本文件为唯一来源，避免多处手抄分叉。

## 1. 需求确认单模板

# 需求确认单

**REQ-ID**: REQ-YYYY-MM-XX
**来源**: 用户反馈 / 自发现 / 技术债 / 产品规划
**原始描述**:
> 用户的原始语句，一字不改

**要解决什么问题**:
- 当前行为: 
- 期望行为: 

**影响范围（粗判）**: 涉及模块/层（如：注册中心 / MCP 桥 / 执行层适配 / 会话映射 / 鉴权）

**成功标准（用户语言）**: 怎样算"做好了"

**参考/竞品**: （如有）

**优先级**: P0(阻塞发版) / P1(重要) / P2(锦上添花)

## 2. 改造文档模板

每个版本目录下的方案文档必须包含以下章节：

# vX.Y.Z 标题

## 0. 需求信息
- REQ-ID: REQ-YYYY-MM-XX

改造文档中引用需求时，REQ-ID 格式为 `REQ-v0.x.x-YYYY-MM-DD-XX`（如 `REQ-v0.9.1-2026-07-21-01`），其中 XX 为该版本当日内的序号。
- 需求来源: 用户反馈 / 自发现 / 技术债 / 产品规划
- 原始需求: 用户原始描述或问题现象
- 优先级: P0 / P1 / P2

## 1. 背景
为什么需要这个改动？当前存在的问题或缺失的能力。

## 2. 方案设计
具体实现方案，包含数据流、关键代码逻辑、接口变更等。

## 3. 变更范围

### 3.1 In Scope（涉及文件 + 改动量评估）
| 文件 | 改动类型 | 改动量 | 说明 |
|------|----------|--------|------|

### 3.2 Out of Scope（显式声明本次不做的事）
- ...（明确列出，防止 scope creep）
- 实现过程中发现的新问题（非本次 In Scope）→ 登记到 planlog.md，不在此次实现
- **配置改动亦计为改动**：`config.json` / `*.default` 模板 / 依赖版本等改动须计入 §3.1，不得表述为「零改动 / 不动」

## 4. 验收标准

### 4.1 实现级（单元场景）
逐个功能点的验证，输入→预期输出。

### 4.2 场景级（用户视角）
站在用户角度验证：用户看到/体验到什么。

### 4.3 回归级（不破坏现有功能）
确认没有破坏已有功能的具体验证点。

## 5. 修订历史
| 版本 | 日期 | 修订人 | 说明 |
|------|------|--------|------|
| v1 | YYYY-MM-DD | - | 初稿 |
| v2 | YYYY-MM-DD | - | 对齐实际实现（实现完成后更新） |
| v3 | YYYY-MM-DD | - | 二次修改：xxx（用户测试发现问题后更新） |
