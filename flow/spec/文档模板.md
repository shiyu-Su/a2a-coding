# 文档模板

> **规范版本戳**：v0.11.0（2026-10-20）
>
> 本文件是需求流程产出物（需求确认单 / 改造文档 / 派发消息）的模板单一来源，与流程规范内核 `需求流程.md` 配套使用。
> 落地到项目时，可将本文件复制到项目的模板目录（如 `doc/_templates/`）；引入本规范包时保持本文件为唯一来源，避免多处手抄分叉。

## 1. 需求确认单 · 板侧渲染规范

> **形态（v0.11.0 降档）**：确认单**不以文件形态产出** —— 现版 = **引擎侧结构化在册**三件套（`docVersion` + `sections` + 每节**依据指向**），节清单、取值、幂等键与执法口径单源在 `引擎映射.md` §3.6。本节据此由「落盘文件模板」**降档为板侧用户视图的渲染规范**：只规定怎么把在册现版渲给人看，**不规定落点、不另立第二份节清单或语义**。
> **渲染侧无编辑口**：确认 / 异议 / 补充三动作一律经板转发进引擎，**均不直接改在册正文**；口径漂移只经新一轮合成重出现版。

**头部六项**（逐取自册现版与本轮坐标，渲染侧不推导、不补写）：`docVersion`（本轮确认单版本，口径 `v{round}`，恒随轮、**不设子版本**）· `docHash`（现版正文哈希 ⇒ 与用户确认时所指那份比对，是判 `stale` 的原料）· **REQ-ID** `REQ-YYYY-MM-DD-XX`（XX = 当日全仓序号）· **版本归属** v{X.Y.Z}（可随排期改版；未排期停靠 ⇒ 此行写「未排期」）· **Feature** `{featureId}` · **本轮 `basisRev`**（本轮所据口径；派生键、不落列）。原头部里的「来源 / 用户原话」不占这六项：随开轮入参 `sources`（自由文本材料）在该轮依据层呈现。

**正文五节**（**闭集、实现侧 id 固定** = `problem` / `impact` / `constraints` / `open-questions` / `decisions`，登记序 = `docHash` 的冻结序列化序；**对用户只显渲染名、不裸写 id**，模板不另立节名体系。下表是**对照**，不是第二份事实源：落库标题取在册 `title` 现值，id 只用于锚依据与幂等）：

| 渲染名（沿用现名） | 实现侧 id | 渲染要点 |
|---|---|---|
| 要解决什么问题 | `problem` | 当前行为 / 期望行为；确认的是**问题**，不是方案 |
| 关键核实结论（按 project 分块） | `impact` | 「当前行为 / 影响范围（粗判）/ 技术可行性假设」须经执行单元核实，逐块见下「分块纪律」 |
| 跨 project 综合结论 | `constraints` | **编号条只留跨 project 综合结论**（逐条编号，通常含：读面与行为现状、改动面粗判、依赖与顺序结论、体量预估、数据面（影响迁移归属））；单 project 的事实写进各自块内，不上提 |
| 待用户裁决 | `open-questions` | 逐项列，用户逐项裁决（接受建议 / 另裁），裁完**销号**；全裁完 = 现版可进门① |
| 成功标准（用户语言） | `decisions` | 怎样算「做好了」—— 用户可自验的动作级描述 |

**每节挂「依据（n）」折叠层**：**默认视图只显节正文 + 一枚「依据（n）」折叠标记**（n = 该节依据条数），**展开才见依据**。依据层装三类料：① 该节的**三值答复**（`relevance` / `decision` / `reason` / `based_on_rev`，随条带 **project 标识**与该块 inquiry `{taskId}`）；② 该节所据的**合成轮 `round`**（本轮 `basisRev` ⇄ 块首 `based_on_rev` 不符 ⇒ 该条标 `stale` 并提示，**不覆写、不自动开轮**）；③ **用户补充条目回执**。技术可行性假设（若不成立则整个方案路径需变）必须在**本阶段**核实完毕，不得留到方案设计阶段。
> **整单缺失的渲法**：缺节 / 正文脏 / 超上限 ⇒ 整单不命中在册，渲染侧显「本轮无现版」并指向失败原因 —— **禁止渲空串或截断**（那会造出「看着在册、实际缺半」的确认单 = 伪造门① 前提）。

**分块纪律（`impact` 节）**：每块块首先记一行三值答复（`relevance` = involved · `decision` = accepted / rejected（**仅 involved 时有值，否则 NULL**）· `reason`（**判为不参与 / 不接受时必填**）· `based_on_rev` = {rev}），括注带 project 标识与该块 inquiry `{taskId}`；三值答复的取值与执法口径单源在引擎，本节只给渲染落点、不抄一份。
> **汇总一行**（判为 `not_involved` 的 project **不平铺成块**）：不参与 = {project A}（{reason 摘要}）· {project B}（{reason 摘要}）—— 默认视图只此一行，不得逐 project 展开。

**三档判据行**（改锚**引擎收口态与合成态**，语义单源见 `引擎映射.md` §3.6，本节不另存一份）：**待澄清** = 本轮存在三值 `pending` 行；**进行中** = 整格 `settled` 未真；**核实完成** = `settled` 真 ∧ 合成行 `synthesis.state`（= 该行的任务态出参 `taskState`，**与整格 `settled` 不混读**）= `completed` 且 `docHash` 已在册。三值答复、`settled` 与 `synthesis.state` 一律回读引擎，orch 不得单方断言。

**原型 / 流程附件（条件附属视图，不占五节闭集）**：仅当需求含**用户可见的界面 / 流程变化**时挂；无则显「无」。附件允许后补 —— 原型 / 流程稿常在 Step 1 边界轮才定稿，定稿后**经板以补充开新一轮**重现该节（**不回填现版**，见上「渲染侧无编辑口」），实现口径转译进改造文档（引用原型，不重复贴图）。**显式确认判据**：须经用户**单独显式确认**，留痕 = 该节依据层一枚确认回执（「原型 v{n} 经用户确认」），不得混在技术边界表态里默认通过；有原型未确认 ⇒ 改造文档不得置「待审批」→ approve。

**裁决 / 异议 / 补充锚 `sectionId`**：三动作都定位到**具体版本的具体段落**，锚 `(docVersion, sectionId)`，与 `doc_objection` 的幂等键 `(docVersion, sectionId, objectionId)` **同形**；上表「待用户裁决」的逐条编号即取 `sectionId`，不另立第二套编号。

**原属落盘正文、现移出闭集的两项**：「与其它需求的顺序」（同版串行建议，吃前序产出的排后面；单需求版本可写「无」）改由板侧版本内需求列表呈现；「修订历史」不再有表 —— 修订轨迹 = `docVersion` 逐轮序列，已确认档按「确认时所指那份的哈希 ⇄ 现版哈希」比较派生。

## 2. 改造文档模板

# 改造文档 — {topic}（{一句话概括}）

**REQ-ID**: `REQ-YYYY-MM-DD-XX`（与需求确认单同号配对）
**Feature**: `{featureId}`（版本 v{X.Y.Z} · 涉及单元 · stage=改造方案）
**确认单**: `doc/{版本}/{topic}-需求确认单.md`（v{n}，用户 YYYY-MM-DD 定稿）
> 两档模板头部的 `{版本}` 目录段：`version` 非空 ⇒ `doc/{版本}/`；未排期停靠 ⇒ `doc/pool/`（本行与「版本归属」行同款替换，其余各行不另存一份口径）。正式文本见 `需求流程.md` §4「文档命名规范」。
**Step 0 合成轮**: 第 1 轮 `{taskId}`… · 第 2 轮 `{taskId}`…（**产品经理会话** `{contextId}`；**合成轮 ≠ 边界轮次** —— 合成轮是 Step 0 的反复讨论轮（用户驱动、无轮次上限，口径变只标 `stale`、**不自动开轮**），边界轮属 Step 1，两套纪律**不得互读**）
**Step 1 边界轮次**: R1 `{taskId}`… · R2 `{taskId}`… · …（**研发经理会话** `{contextId}`，R1–R3 续用同一条）
> 本模板内 `R1` 有三种所指 = **需求代号 R1**（本版需求编号）／**Step 1 边界轮次序号 R1**（上一行）／**Step 0 合成轮**（其上那行）：指边界轮次写「边界轮次 R{n}」，指合成轮只写「第 {n} 合成轮」、**不写 R 序号**，**不得裸写 `R1`**。
> 以上**两条会话线不共享**（Step 0 → Step 1 换职责位 ⇒ 另起 `contextId`；同一轮次内部续用同一条），逐轮留 taskId 便于追溯 —— 口径见 `需求流程.md` §0.5「会话复用纪律」（派发侧）；宿主与人的交互侧会话粒度见 `需求流程.md` §0.5「会话面分野」，模板不另存口径。
**原型**: {有 UI/流程变化时，引用确认单「原型/流程附件」槽的定稿稿；无则整行省略}

## §1 背景与评估

> 目标（要达成什么，1–4 条）+ 需求评估结论**内嵌**在此（与架构冲突 / 依赖 / 更简方案 / 与现有需求冲突 ⇒ 合理 / 需调整 / 不合理）。

## §2 方案设计

> 定稿口径：各单元「做什么 / 不做什么」。口径逐条编号；多轮边界讨论中新增或改写的条目标 ★R{轮次}，用户亲自定案的条目标 ★用户。
> 大需求子节（按需挂）：
> - **改动面清单**：file:line 逐点（行号注明所锚定的 HEAD commit，实现偏离即更新）
> - **数据迁移**：存量数据形态 / 迁移方案 / 迁移判据

## §3 In-Scope（按单元分列）

> 规范硬要求：按单元分列，每单元必须含明确「**不做什么**」；逐单元自答「是否与其它单元重复改造同一功能」（确需冗余容灾 ⇒ 显式登记哪两处、为何）。
> **本表（§3 In-Scope）是方案边界的事实源，不是归属 / 承诺集的机器判据**（v0.10.1）：归属以引擎记录为准，本表只是过门时落归属初版的**输入**。

| 单元 | 做什么 | 不做什么 |
|---|---|---|
| {board / flow / …} | | |

## §4 验收标准

> 三级：实现级（单测 / typecheck）/ 回归级 / 真机验收清单（动作级描述，用户可照着逐步点）。
> 大需求子节（按需挂）：**测试锚面**——哪些回归用例要真改、零改组（防误伤）、新增锚、体量预估（src / 测试行数）。

## §5 实施记录（Step 2 起回填）

> - **`version_planning` 凭据**（PjM 版本规划工序 · 凡改载体代码的**主需求**）：= 本 project **项目经理（PjM）**的版本规划结论 + **用户确认** + **「先建版 → 再写归属」顺序回执**（倒序必被归属写口拒绝；增补轨与承接轨跳过本格、不重走本工序）。工序全文见 `需求流程.md` §2 Step 2「PjM 版本规划工序」
> - **DAG 拆法蓝图**（**由各 project 的研发经理产出本侧任务清单**，宿主收敛后登记，见 `需求流程.md` §0.5）：节点 + 依赖 + 硬约束顺序（**依赖列只填直接前置 —— 含为定序而声明的边**，见 `需求流程.md` §2 Step 2；须先于后节点的写明 ★必须先于）；**逐 project 记「本侧会话线 `contextId`」** = 该 project 研发经理的 Step 1 会话线，供 Step 2「生成具体任务」复用（**不登记则复用做不成**）
> - **`decomposing` 会话线** = 该 project **研发经理的 Step 1 `contextId`（沿用、不另起）**：与上一条「本侧会话线 `contextId`」是同一登记项，本槽只把它钉到 `decomposing` 这一格 —— 依据 `需求流程.md` §0.5「会话复用纪律」表第 2 行（**跨 step 复用的唯一登记例外**）
> - 派发回执要点；实现偏离（**偏离须同步更新 §2/§3 并修订历史 +1**，不得事后补）
> - 载体升级节点回执（凡改载体代码的 Feature，DAG 末位登记）

## §6 登记区

> 规范指定落点，随时追加，不展开：
> - **边界确认记录**：每轮边界版本 + 各单元逐项表态（接受 / 反对 / 调整）
> - **非影响性改进点**：一句话，不编号
> - **未覆盖验证项 / 遗留验证项**：逐项含原因，不得默认算通过
> - **增补节**：增补轨（小修）方案写入此处（修订历史 +1），不另立改造文档

## §7 修订历史

> 初稿 v1；实现偏离 / 增补定案 / 二次修改均 +1；用户验收通过后标 **final**（final 须对照含增补的最新实现；**修订历史含 final 行 = 需求完成与发版的判据**）。

## 3. 派发消息模板

> 与 `需求流程.md` §2 的 **H4 派发消息自包含**配套：派给执行单元的每条任务消息必须**能独立执行**。执行单元可能位于**异机**、读不到宿主侧 `doc/` 文件，故「改造要点」必须**就地内嵌全文** —— **不得**以「去读 `doc/{版本}/{topic}-改造文档.md`」作为**唯一指令载体**（文档路径仅作**背景引用**，同机时才便利）。

最小模板（键不可省，值按节点填写）：

```
【需求 {REQ-ID} · Step 2 节点 {节点标签}】
职责位（可选，缺省不填）：taskType = <仅当本节点不以执行单元 agent 出场时填，语义见 需求流程.md §0.5>
改造要点（内嵌全文，来自改造文档 §2.x 的本节点子集）：
  - 做什么：
  - 不做什么：
  - 落点（文件 / 符号 / 接口）：
验收判据（机械可核）：
  - <输入 → 预期输出；命令 / 断言形式>
门禁：
  - <typecheck / lint / test 命令；本需求为规范文本时 = spec 一致性自检：引用编号 / 术语与规范一致>
超时纪律：接近超时 / 上下文上限时，先保门禁通过再报告。
实现偏离：实现方式 / 接口 / 行为与改造文档不一致时，逐条回传（并触发改造文档修订历史 +1 版）。
文档路径（optional，同机时便利，仅作背景引用）：
  - doc/{版本}/{topic}-改造文档.md §2.x
```

> - **粒度不变**：本模板不改变节点粒度纪律 —— 单节点仍应约 10 分钟可完成（见 `需求流程.md` §2「派给执行单元的任务节点要小」）；大改造拆多个小节点。
> - **实现级增补同样适用**：增补节点的派发消息同样内嵌增补要点全文。
> - **跨单元边界确认类消息同样适用**：须将「待表态条目全文」带入消息（防止异机收不到确认单），并以**同一 `contextId` 续接多轮表态**（见 `需求流程.md` §2 Step 1「留痕」条；**跨 step 的复用见 `需求流程.md` §0.5「会话复用纪律」**）。
> - **职责位占位可选**：缺省**不填 = 执行单元 agent**（`unit_agent`），此时正文不注入该行；仅当节点以其它职责位出场时才带上。「那一行」是**面向人的外壳**，机器判据不靠它；取值清单与执法口径不在本模板（语义见 `需求流程.md` §0.5）；**组级职责不落本行、不进 `taskType`**（见 `需求流程.md` §0.5「组级职责」块）。
