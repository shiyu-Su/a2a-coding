# 文档模板

> **规范版本戳**：v0.9.3（2026-09-26）
>
> 本文件是需求流程产出物（需求确认单 / 改造文档 / 派发消息）的模板单一来源，与流程规范内核 `需求流程.md` 配套使用。
> 落地到项目时，可将本文件复制到项目的模板目录（如 `doc/_templates/`）；引入本规范包时保持本文件为唯一来源，避免多处手抄分叉。

## 1. 需求确认单模板

# 需求确认单

**REQ-ID**: REQ-YYYY-MM-DD-XX
**来源**: 用户反馈 / 自发现 / 技术债 / 产品规划
**原始描述**:
> 用户的原始语句，一字不改

**要解决什么问题**:
- 当前行为: 
- 期望行为: 

**影响范围（粗判）**: 涉及模块/层（如：注册中心 / MCP 桥 / 执行层适配 / 会话映射 / 鉴权）

**成功标准（用户语言）**: 怎样算"做好了"

**参考/竞品**: （如有）

**优先级**: P0(阻塞发版) / P1(重要) / P2(锦上添花)

## 2. 改造文档模板

每个版本目录下的方案文档必须包含以下章节：

# vX.Y.Z 标题

## 0. 需求信息
- REQ-ID: REQ-YYYY-MM-DD-XX

改造文档中引用需求时，REQ-ID 格式为 `REQ-YYYY-MM-DD-XX`（如 `REQ-2026-09-26-01`），其中 XX 为当日全仓序号（v0.9.3 起去版本段，见 `需求流程.md` §7；存量旧号 `REQ-v0.x.x-YYYY-MM-DD-XX` 保持原样不迁移）。
- 需求来源: 用户反馈 / 自发现 / 技术债 / 产品规划
- 原始需求: 用户原始描述或问题现象
- 优先级: P0 / P1 / P2

## 1. 背景
为什么需要这个改动？当前存在的问题或缺失的能力。

## 2. 方案设计
具体实现方案，包含数据流、关键代码逻辑、接口变更等。
文档中的流程图 / 架构图 / 时序图优先使用 mermaid 代码块（```mermaid）书写，板上文档页会渲染为图形；ASCII 字符画仅作临时示意，不入正式文档。

## 3. 变更范围

### 3.1 In Scope（涉及文件 + 改动量评估）
| 文件 | 改动类型 | 改动量 | 说明 |
|------|----------|--------|------|

### 3.2 Out of Scope（显式声明本次不做的事）
- ...（明确列出，防止 scope creep）
- 实现过程中发现的新问题（非本次 In Scope）→ 按归属登记（影响本需求验收 → 增补节／增补 Feature；非影响性改进点 → §6 登记与批注），不在此次实现
- **配置改动亦计为改动**：`config.json` / `*.default` 模板 / 依赖版本等改动须计入 §3.1，不得表述为「零改动 / 不动」

## 4. 验收标准

### 4.1 实现级（单元场景）
逐个功能点的验证，输入→预期输出。

### 4.2 场景级（用户视角）
站在用户角度验证：用户看到/体验到什么。

### 4.3 回归级（不破坏现有功能）
确认没有破坏已有功能的具体验证点。

## 5. 修订历史
| 版本 | 日期 | 修订人 | 说明 |
|------|------|--------|------|
| v1 | YYYY-MM-DD | - | 初稿 |
| v2 | YYYY-MM-DD | - | 对齐实际实现（实现完成后更新） |
| v3 | YYYY-MM-DD | - | 二次修改：xxx（用户测试发现问题后更新） |

修订历史含「增补」相关行时的口径：**增补 Feature 的方案内容写入本改造文档的「增补」节**（主需求与增补轨同款，见 `需求流程.md` §2 Step 3 三档定性判据），修订历史对应行标「随增补 REQ-xxx」；**增补 Feature 不自带改造文档**。

## 6. 登记与批注
承载登记类信息（planlog 退役后的唯一去处）：
- **非影响性改进点批注**：一句话登记、不编号，随归属需求写入其改造文档本节。
- **未覆盖验证项**：「改了但未在真机碰到 / 未触发」的项（含原因），验收时逐项列出并登记本节，不得默认算通过。
- **遗留验证项**：离线自测放行、待后续真机补验的项目，登记本节并注明触发条件。

## 3. 派发消息模板

> 与 `需求流程.md` §2 的 **H4 派发消息自包含**配套：派给执行单元的每条任务消息必须**能独立执行**。执行单元可能位于**异机**、读不到宿主侧 `doc/` 文件，故「改造要点」必须**就地内嵌全文** —— **不得**以「去读 `doc/{版本}/{topic}-改造文档.md`」作为**唯一指令载体**（文档路径仅作**背景引用**，同机时才便利）。

最小模板（键不可省，值按节点填写）：

```
【需求 {REQ-ID} · Step 2 节点 {节点标签}】
改造要点（内嵌全文，来自改造文档 §2.x 的本节点子集）：
  - 做什么：
  - 不做什么：
  - 落点（文件 / 符号 / 接口）：
验收判据（机械可核）：
  - <输入 → 预期输出；命令 / 断言形式>
门禁：
  - <typecheck / lint / test 命令；本需求为规范文本时 = spec 一致性自检：引用编号 / 术语与规范一致>
超时纪律：接近超时 / 上下文上限时，先保门禁通过再报告。
实现偏离：实现方式 / 接口 / 行为与改造文档不一致时，逐条回传（并触发改造文档修订历史 +1 版）。
文档路径（optional，同机时便利，仅作背景引用）：
  - doc/{版本}/{topic}-改造文档.md §2.x
```

> - **粒度不变**：本模板不改变节点粒度纪律 —— 单节点仍应约 10 分钟可完成（见 `需求流程.md` §2「派给执行单元的任务节点要小」）；大改造拆多个小节点。
> - **实现级增补同样适用**：增补节点的派发消息同样内嵌增补要点全文。
> - **跨单元边界确认类消息同样适用**：须将「待表态条目全文」带入消息（防止异机收不到确认单），并以**同一 `contextId` 续接多轮表态**（见 `需求流程.md` §2 Step 1「留痕」条）。
