# 引擎映射

> **规范版本戳**：v0.11.0（2026-10-20）
>
> 本文件属于**流程规范包内核**，与同目录 [`需求流程.md`](./需求流程.md) 配套：前者定义 Step 0-3 的判据与产出物，本文件定义同一套流程如何落到 Feature 引擎的状态机上。
> **项目无关**：不绑定任何具体仓库、项目或宿主实现。

## 1. 核心命题

需求流程的每一步，都对应 Feature 状态机上的一个状态；每次状态推进，都有**唯一确定的驱动方**（宿主 / 用户 / 引擎自身）。宿主不再"逐步派活 + 轮询催办"，而是**在关键点做状态机操作**，其余交给引擎。

**为什么必须引擎化**：MCP 是**拉模型**，callback 无法唤醒宿主会话。因此"宿主逐条 `a2a_call` + 自己轮询"会把整条需求的进度**绑死在 LLM 会话**上：宿主一停，任务即停；宿主一长，上下文即爆。**引擎驱动是让任务在宿主不参与时继续推进的唯一方式**。

**状态机速览**（v0.4.1 REQ-04 收敛后）：

- **主链 = 引擎 `state` 的有序投影**：**态数与态名以引擎状态机的定义作为唯一事实源**，本规范不另立 state 清单、不登记枚数 —— 本规范只写**每格由谁推进**（§2 / §5）与**每格推进前的人判清单**（`需求流程.md` §2 Step 3）。引擎增 / 退 state **不要求**同步修订本规范。
- **异常态（3）**：`needs_input` / `failed` / `cancelled`
- **终态（3）**：`completed` / `failed` / `cancelled`

> **不抄枚三句硬钉（v0.10.5 起）**：
> ① 本包**不得**另立 `state` 值域清单，也**不得**另立 `state`→`stage` 的映射表 —— 二者的单源都在引擎代码。
> ② **允许按态名指称具体格**（如 `executing`→`integrating`、`reviewing`→`completed`）—— 指称是叙述手段，不构成值域登记、不构成第二份清单。
> ③ 按态名指称之处**由引擎变更事件驱动同步**：引擎改名 / 改语义 ⇒ 随变更事件通知本包修订；本包**不自行改名**、不自行推测新名。

> **口径注（v0.6.1 REQ-05 起）**：`failed` 语义**收窄**为 **DAG 非法（环 / 悬空）fail-fast 专用** —— **业务失败不再产出 Feature `failed` 终态**（Feature 停在 `executing` 静止，见 §4 二分判据）；`blocked` 是**良性终态**，**不计入「全完成」**。上述「异常态 / 终态」均就 **Feature 级**而言：**节点 `failed` 可经重派复活**（见 §5 `retryTaskIds`），Feature 不因业务失败进入终态。**`failed` 仍为终态，但可经 `cancel` 归档（放行面见 §6）**。

> **「不新增」句式的消歧定义（v0.10.5 起 · 全包唯一一处）**：本包内「不新增 `stage` 值域 / 不引入新机器门 / 不为此新增任何能力」一类句式，语义 = **不新增产出物、不引入人判之外的机器门**，**不指 `state` 值域与 `stage` 值域的枚数**（枚数可随引擎演进而增删）；枚数事实源见 §3.5。其余各处该族句式一律照本条理解，**不逐处改写**。

**引擎只做「需求实现」**：主链起点 = `waiting_approval`（= Step 1 产出→门的停靠点；**v0.9.0 起需求实体可于提需求时创建并长停靠在此** —— `stage`/`version`/`approval` 是**登记字段（观测面），不是状态机态**，见 §3.5）；`approve` 是**唯一准入**（**后继 = `version_planning`，不是 `executing`**，见 §2 / §3 门表；**行前提形态（v0.10.5 增补）**：准入按**行前提**把关，**不按 `to` 取值点名** —— 从 `waiting_approval` 出发**凡改动 `state` 的迁移**，前提恒为该需求 `approval = 已通过` ∧ `version` 非空，而 `已通过` 的唯一写口是 `approve` ⇒ **等价于「除 `approve` 外无前进口」**，引擎将来新增任何前进边都不复现旁路；**`to` = 当前态的登记字段写入不属迁移**，见 §3.5；**v0.9.0 起并校验 §3 门②行过门判据**）。`executing → integrating` 是**引擎自动**（**全部节点 `completed`**；收敛且存在失败 ⇒ **不转移**，见 §4 二分判据）；`integrating → testing → reviewing → completed` 由**宿主 `advance`**。

## 2. 步骤 ↔ Feature 状态 ↔ 驱动方

| 流程步骤 | Feature 状态 | 驱动方 |
|---|---|---|
| Step 0 需求访谈 → 需求确认单 | **（主链不推进；实体或已进引擎，`stage`=`需求分析`，§3.5）** | **板开轮 + 引擎合成**（v0.11.0 改指：本轮答复收口后由**引擎自行物化并执行 `task_key='synthesis'` 的合成轻量循环**，产出**结构化在册**《需求确认单》现版（`docVersion` + `sections` + 每节依据指向，执法原文见 §3.6 A / B）—— **宿主在此不再承担综合分析 turn、确认单不再另落文件**；用户的确认 / 异议 / 补充三动作**一律由板转发**进引擎） |
| 【确认需求内容】 | **（主链不推进）** | **用户确认，经板转发**（凭据分两半，v0.9.0 定形 · v0.11.0 换载体：确认**内容** = 引擎侧**结构化在册**的《需求确认单》现版（§3.6 A，**不落文件**）；确认**动作** = 用户经板以 `gate1_confirm` 的留痕（§3 门①行前提 ③）∧ `stage`「需求分析 → 改造方案」迁移的引擎记录，见 §3.5；不新增状态机流转） |
| Step 1 评估 + 改造文档 | **（引擎不参与）** | 宿主（+ 各单元本侧评估/边界确认） |
| 【确认改造文档】 | `waiting_approval → version_planning` | **用户 `a2a_feature_approve`**（**唯一准入**；宿主在收到确认后立即调用；后继格见 §3 门表） |
| **Step 2 · PjM 版本规划** | `version_planning` | **宿主发起、用户确认结论**（本 project 的项目经理职责位出评估；结论落定后宿主按「**先建版、再写归属**」经引擎写口落库，工序全文见 `需求流程.md` §2 Step 2） |
| **Step 2 · 生成具体任务** | `decomposing` | **各 project 的研发经理出本侧任务清单** + 宿主**收敛清单、登记 DAG 并同轮把清单贴给用户**（分工见 `需求流程.md` §0.5） |
| **Step 2 需求实现** | `executing` | **引擎自动**（拓扑派发（并行/串行的资源约束由运行底座决定）· 等待 · 失败传播=冻结依赖闭包） |
| Step 3 测试 / 反馈 → 通过 | `integrating → testing → reviewing → completed` | **宿主 `advance`** |
| 任务需澄清 | ` → needs_input` | **引擎自动**（任务 `input-required`）。**注（2026-09-26 引擎核实）**：`needs_input` 仅 `executing` 可进可出、主链无回边、挂载白名单仅 `executing`/`waiting_approval` ⇒ 终验段（`integrating`/`testing`/`reviewing`）无该路径；`needs_input` 唯一语义 = **执行期任务澄清**（见 `需求流程.md` §2 Step 3） |
| 任务失败 | `executing`（**不离开**，非转移） | **引擎自动**（仅冻结**依赖闭包**下游：未派发者置 `blocked`、**在飞不动**；无可派发且无在飞且存在失败 ⇒ **保持 `executing` 静止**，账单经事件 `feature.failure_report` + `a2a_feature_status`（可选 `text` / `contextId`））（账单按 **失败 episode** 发，口径见 §4） |

> **Step 2 的起点**：需求实体**提需求即创建**（板 `a2a_feature_create`；初值**恒定** —— `stage=需求分析` + `approval=未发起`，create 不再收这两枚登记字段入参，见 §3.5「初值恒定」条），初态一律 `waiting_approval`。门① 过门以 `version` **非空**为前提（未排期 ⇒ 结构化拒收、零写入，见 §3 门表）；改造文档落文件 ⇒ 宿主置 `approval=待审批` → 用户确认经 `a2a_feature_approve` 放行（过门判据见 §3 门②行）⇒ `state → version_planning`（**不是 `executing`**）→ PjM 版本规划结论落库后宿主 `advance` ⇒ `decomposing` → 登记 DAG 完毕宿主 `advance` ⇒ `executing`，引擎接管派发。

读法：一张需求 = 一个 Feature；一行 = 一次状态变更（或一次**非转移操作**，如「任务失败」停在 `executing`、**登记字段写入**〔`advance`「`to` = 当前态 ∧ 带登记字段」特例，见 §3.5〕）；「驱动方」列即该变更的**发起者**。Step 0/1 不推进主链；`approve` 之后的 `version_planning → decomposing` 两格连推与 Step 3 内部三态连推（`integrating → testing → reviewing`），均由宿主 `advance`，中途不必停。**新两格不派发任何节点** ⇒ 上表两枚异常态行（需澄清 / 任务失败）只作用于 `executing`，不向这两格扩展（专项口径见 §6）。**「不必停」仅指中间态不停靠**（v0.9.1 补）—— 每一格转移仍须 `note` 带凭据（判据清单见 `需求流程.md` §2 Step 3），且 `reviewing → completed` 之前必须有明确的用户验收结论。

## 3. 两道确认门的挂载

流程里**只有两个用户介入点**，两者都显式挂到状态机，不是散落在正文里的"人工约定"：

| 门 | 语义 | 挂载方式 |
|---|---|---|
| **需求确认门** | 「我理解你要解决的是不是这个问题」 | **不在状态机上**（主链不推进）：凭据分两半（v0.9.0 定形 · v0.11.0 换内容载体）—— 确认**内容** = **引擎侧结构化在册的《需求确认单》现版**（`docVersion` + `sections` + 每节依据指向，形状与写口映射见 §3.6 A；**自 v0.11.0 起确认单不再落文件**）；确认**动作** = **`stage`「需求分析 → 改造方案」迁移的引擎记录**（§3.5；实体已进引擎时承载，不扩值域）叠加用户经板以 `gate1_confirm` 的留痕。**过门判据 = 三前提（v0.11.0 由两条抬为三条 · 本行是全包唯一单源，`需求流程.md` §2 Step 0 只回指不另存）**：**① 该需求 `version` 非空** —— 未排期过门 ⇒ **结构化拒收、整单零写入**（`state`/`stage`/`approval` 全不动；拒后 `stage` 仍 `需求分析` ⇒ 排期锁仍开，补写 `version` 后重试）· **② 引擎侧在册有现版** —— `docVersion` 存在 ∧ `sections` **非空**（脏正文 / 缺节只落 `sections: []` ⇒ 不命中，**不存在第二套「算 sections」的解析**）· **③ 用户经板以 `gate1_confirm` 确认过该现版**（幂等键 `(featureId, round, docHash)`）。**执法位分档（防后人误读）**：**①② 是引擎的结构化拒收点**（任一不过 ⇒ 该登记写零写入）；**③ 是门① 的动作凭据、不是第四道机器闩** —— `gate1_confirm` **只留痕、不流转**（真推进仍是门②行的 `approve`，见 §3.6），其把关在版本钉 + 板面呈现，**不得夸称引擎据此拒收**。守卫**不判 `state`、不校验 stage 迁移序**；错误码字面属执法原文，不在本包。**版本钉（v0.11.0）**：确认对象是**版本**、不是这张卡 —— `docVersion` 或 `docHash` 一变 ⇒ 此前确认一律 **stale**、门① **回未过**（板面回「待确认」），须对该现版重新确认；**不设子版本**（`docVersion = v{round}` 恒随轮）。**双档条（v0.11.0 · 存量兼容）**：前提 ② 认**两档任一命中** —— **旧档** = 该需求 `decisions` 已登记本需求的《需求确认单》**档名**（补登记须**全量重发** —— `decisions` 在引擎是**整值替换**）**∨ 新档** = 本轮「需求分析」合成行在册且 `sections` 非空；**旧档必须保留**（存量卡的 `decisions` 只有文件路径，删档即打死存量）、**存量不迁移 ⇒ ②③ 的在册 / 确认形态只对新卡生效**。又：本行前提**只管门① 这一道**，不蕴含门② 已过的 `approval` ⇒ `stage` 抬「改造方案」而 `approval` 仍 `未发起` 是门① 的**合法落点**，但**不得据此改 `state`**（改 `state` 的前提见门②行）；**本前提是登记写自身的判据**（与门②行「登记写不属迁移」的豁免不冲突 —— 豁免只免**门② 行前提**，未免门① 前提）。（**反向蕴含（v0.11.0 同步改点名）**：门② 过门判据含**本行前提 ①②**，见门②行 ③④ —— 本行抬为三前提后，门② 抄的是 **①② 两枚**而非「本行全部」，前提 ③ 的 `gate1_confirm` 留痕**不进**门② 六条）；**本行登记写落库成功 = 该 Group Version `notstart→active` 自动转换的主触发点**（回指 §3.5「版本状态不是登记字段」条）。**前置**：**相关执行单元的事实核实结论已进入在册现版**（v0.11.0：核实结论随本轮成员回执进入合成入参，不再由宿主持有后单方断言）。v0.4.1 REQ-04 起，Step 0/1 不推进主链 |
| **改造文档确认门** | 「方案经用户确认后才开始实现」 | **唯一准入 = `approve`**：`waiting_approval → version_planning`（v0.10.5 起后继抬为 `version_planning`，**不再是 `executing`** —— PjM 版本规划与拆任务两格在 `approve` 之后）。**过门判据 = 六条（v0.10.5 增补卡 `ec93e1bd` 起，本行是全包唯一单源；由此前两条收紧为六条）**：① `state` 仍为本表 §2 该行的 `waiting_approval` · ② `approval` 仍为 `待审批`（①② **原有、不动**）· ③ `version` 非空 · ④ 《需求确认单》**已在册**（③④ **照抄本表门①行的前提 ①②** —— **v0.11.0 同步改点名**：门① 判据已抬为**三前提**，本行照抄的是其中 **①② 两枚**（在册按门①行**双档条**同源判定，不造第二套判据）；**门① 前提 ③ 的 `gate1_confirm` 留痕不进本行六条** —— 本行仍只查既有事实，不查确认动作）· ⑤ `stage = 改造方案` · ⑥ `decisions` 含**任一** `-改造文档.md` 档名（增补轨 / 承接轨登记的是**主需求那一份**，**判据不带轨型分支** —— 「须是主需求那一份」是人判纪律，见 `需求流程.md` §2 Step 0）；**④⑥ 各按 `approve` 当场值查**（`decisions` 是整值替换 ⇒ ④ 不被 ⑤ 蕴含）；任一不过 ⇒ **结构化拒收、零迁移**，错误码 `feature_approval_not_ready`（③④⑤⑥ 各自的拒因错误码字面属执法原文，不在本包）。**划界**：六条**不校验 stage 迁移序**（与门①行同款口径）—— ⑤ 只查 `stage` 的**当前值**，不查它经由哪条迁移抵达。**★范围句**：**六条只约束 `approve` 这一个动作、不约束 `approval` 的登记写侧**（`advance`「`to` = 当前态 ∧ 带登记字段」的登记写不受本行约束，见下「豁免」条与 §3.5）。**硬钉锚**：本行按名指称既有态与既有登记字段取值，**不构成值域登记**（§1「不抄枚三句硬钉」②）。**语义**：**记录已发生的用户确认（一对一映射：不可预领、不可补领）** —— 宿主在收到用户确认后**立即**调用，**不是新增一次用户决策**；**禁止**在用户未确认方案前调用。**前置**：各相关执行单元已确认**接受该边界且无重复改造**（多轮收敛，≤3 轮未达成则升级用户）。未 `approve` 前调度器停在等待点，不派发任何执行任务；**且 `advance` 不得替代本门** —— 行前提 = `approval = 已通过` ∧ `version` 非空：凡从 `waiting_approval` 出发**改动 `state`** 的 `advance`，前提不成立即**结构化拒收、零迁移**；**按行前提把关、不点名任何 `to` 取值**。**豁免**：`to` = 当前态 ∧ 带登记字段的**登记写不是迁移**、不受本前提约束（**排期写 `version`**、**Step 0 首步 `decisions` 登记《需求确认单》**两例照常合法，见 §3.5 —— 后者 v0.11.0 起**只存量卡仍需**，新卡的确认单凭**在册现版**过门、不再登记路径，见门①行双档条） |

> 两个门把「流程纪律」变成「状态机约束」：不是靠宿主自觉，而是**未过门则推进被拒**（非法流转 fail-fast）。

### 3.5 登记字段 ↔ 流程步骤映射（v0.9.0 起）

`features` 携带登记字段 `stage` / `version` / `approval` / `parentFeatureId` —— **观测面，不是状态机态**：不改 §1 的主链 / 异常态 / 终态，**本段**（登记字段 ↔ 步骤映射）**不增状态机**判据条数、不增产出物（本段不裁各步骤自身的判据条数，步骤判据见 `需求流程.md` §2）。需求实体可于提需求时即创建（初态仍 `waiting_approval`）。

**登记字段有两条写路径（v0.10.5 起）**：

1. **宿主显式写** —— 经 `a2a_feature_advance` 的「`to` = 当前态 ∧ 带登记字段」**显式特例**（照 `retryTaskIds` 先例，**状态机零改动**；该特例无终态守卫，否则 `发版` 写不进去）；
2. **引擎随 `state` 派生写** —— 引擎在 `state` 迁移的**同轮**派生写入 `stage`，**不是宿主动作**、不额外要求一次 `advance`；派生写**不触发** `需求流程.md` §5 的文档动作绑定（不产生修订历史 +1、不要求搬文档）。**哪个 state 落哪个 stage 的对应关系，单源在引擎代码**，本包不重述（见 §1「不抄枚三句硬钉」①）。

- **`stage`（阶段）** 值域 = `需求分析` / `改造方案` / `改造` / `回归` / `验收` / `发版`（**六枚全启用**）—— 其中 `需求分析` / `改造方案` / `发版` 由**宿主显式写**，`改造` / `回归` / `验收` 由**引擎随 `state` 派生写**（两条写路径见上）。**一致性判据**：任一时刻 `state` 与 `stage` 不一致 ⇒ **以 `state` 为准并回写 `stage`**（主链的事实源是 `state`，`stage` 只是观测面）。
- **`approval`（门状态）** 值域 = `未发起` / `待审批` / `已通过`（**单向、无回边**）；**过门判据见 §3 门②行**（本处不另存一份）。**口径变更（v0.10.5 增补卡 `ec93e1bd`）**：`approval = 待审批` 仍是「用户确认已发生」的**唯一动作凭据**；§3 门②行 ③–⑥ 校验的是**既有事实**（`version` / `decisions` / `stage` 的当前值），**不引入 stage 迁移序校验**、不做 `stage`↔`state` 同步门。
- **`parentFeatureId`（父链，v0.9.3 起）**：增补 Feature 挂主需求之用的登记字段 —— **仅 `create` 一次性写入**（`a2a_feature_create(parentFeatureId=…)`）；advance 特例（`to` = 当前态 ∧ 带登记字段）**不开放**补写/改写父字段（创建后不可变更）。校验 **fail-closed**（父不存在 / 非法 ⇒ 拒绝，同 `owner_group` 口径）；**父链不递归**（父必须是主需求，增补之下不得再挂增补）。
- **初值恒定（v0.10.5 起重写，原「缺省（向后兼容）」条作废）**：`create` **不再收 `stage` / `approval` 两枚入参**，初值由引擎硬编码固定 —— `stage = 需求分析` + `approval = 未发起`（**新契约下无兼容分叉**：不存在「不传 ⇒ 落 `改造方案` + `待审批`」的旧缺省形态，也不存在「板建卡显式传两参」的第二形态，一切需求卡从 `需求分析` 起步）。`version` **保留为入参**（未排期停靠 / 撤排期 / released 锁 / 板拖拽建卡都依赖它）。写手：门① 前 `version` 由**板发起排期写**、宿主经 MCP 直写同受引擎排期锁执法；`approval` 由**宿主 agent** 在改造文档落文件后置 `待审批`。**v0.9.2 起 `version` 的排期写由板发起；v0.10.0 起经引擎排期写口承载**（经 advance 特例、`to` = 当前态、装配仅 `version` 一字段、不携带 stage/approval；排期写锁与 `released` 锁由引擎在事实源进程执法，宿主经 MCP 直写同受执法，后门不豁免）。
- **版本状态不是登记字段（v0.9.2 起；事实源 v0.10.0 起 = 引擎版本台账）**：版本状态（三态 `notstart`/`active`/`released`）的事实源 = **引擎版本台账**（`versions` 表，按 `(owner_group, version)` 键；标记 `released` 时与状态**同事务**落 `releases` 快照），**引擎判断版本状态、在事实源进程执法排期锁与 `released` 锁**（宿主经 MCP 直写 `version` 同受执法，后门不豁免；发版闸判据见 `需求流程.md` §8）。板为**读投影**：板本地版本文件降为读缓存/降级投影（非第二事实源、不再是写目标），桥不可达时板取**最后一次引擎台账投影**判锁、**锁只紧不松**（拿不到投影 ⇒ 挡排期写，fail-closed）。`notstart→active` 自动转换由引擎在**该版本名下首张卡过需求确认门（门① = `stage`「需求分析 → 改造方案」的登记写落库成功）**时内部幂等触发（`version.activated` 事件留痕），板只读结果；**`approve` 放行与首个节点派发不再是触发点** —— 二者发生时该版本必已 `active`，保留作**幂等兜底**。触发判据是**登记写**、不是 `state` 迁移（故「登记字段写入不属迁移」句不构成例外）；事件须可区分触发来源。
- **两级台账并置（v0.10.1 起）**：版本面自此分两级，**同在引擎、同一事实源进程**——
  - **Group 台账**（上一条所说者，语义 / 三态 / 自动转换 / 排期锁 / `released` 锁**一律不动**）= 按 `(owner_group, version)` 记 Group Version，承载**协调号 / 列车号**语义与「版本 → 需求集合」的聚合。**限定语**：上句「一律不动」中，唯**自动转换的触发点**本版随门① 前移（见上一条），机制与三态值域不动 —— **不构成对「一律不动」的放松**。**台账行的删除**不在本条语义内，判据见 `需求流程.md` §7「版本删除纪律」。
  - **project 台账**（新增）= 按 `(owner_group, project_id, version)` 记 Project Version，**两态 `open` / `released`**；**不进** `notstart→active` 自动转换（那是 Group 侧的节奏），其 `released` **由 Group 级发版动作在同一事务内级联置入**（见 `需求流程.md` §7「发版是一个动作 + 级联」）。
  - **归属（承诺集）**（新增）= 一条需求触达哪些 project、各自落哪个 Project Version；**写点 = 过门（`approve`）之后、最早为 PjM 版本规划工序结论落定之时、执行期新增执行节点时增量补齐**（**新增节点同轮须重发全量归属**，同值幂等、重发安全）。**`approve` 本身不落归属初版（v0.10.2 起回写后置）** —— **改造文档 §3 In-Scope 的单元清单是 PjM 工序的「输入」，归属记录是该工序的「输出」，二者不得并列为两个归属来源**。写入顺序 = **先经 project 台账建版、再经归属写口落归属**（倒序被归属写口拒绝；时序理由见 `需求流程.md` §2 Step 2「PjM 版本规划工序」）。**未过门 ⇒ 归属写拒**；归属一经引用，其 Project Version **不可改**、一经 `released` **不可复用为后续归属目标**。归属记录**不随任务清理而消失**，也不因 Feature 终态 / `cancel` 被级联删除。**亦不因 Group 版删除而级联删除**（删版只消解台账行与需求 `version`，见 `需求流程.md` §7）。归属所记的组版本与需求登记字段 `version` **同单写定、此后不漂移**（派生不变式，非流程动作）。
  - 两级计数字段**不得横向相加或相等校验**；project 侧收口判据**仅作展示**、不构成第二道发版门（口径见 `需求流程.md` §7 / §8）。板的 project 级版本视图是**只读投影**，本版**不落库、不加写面**。

**凭据切分（v0.11.0 换内容载体）**：确认**动作**（谁 / 何时 / 对哪个阶段）= **引擎记录**；确认**内容**的事实源自本版起**两式并立** —— 《需求确认单》= **引擎侧结构化在册现版**（`docVersion` + `sections` + 每节依据指向，形状见 §3.6 A；**该档不再落文件**）· 《改造文档》= **仍是文件事实源**（落文件判据不废，见 `需求流程.md` §2「每步推进的强制条件」）。**两式互不吞**：本段只换确认单的载体，**不放宽** `需求流程.md` §7「文档 mv 分家」条那句**逐字保留的原文 ——「文件系统不在引擎，引擎不碰 `doc/{版本}/`」**。**辖域钉另起**：该句辖域**只管目标仓库文件面**（`doc/{版本}/` 等落盘文件），引擎侧**结构化在册**的确认单是**引擎事实源、不属仓库文件** ⇒ 「引擎物化并执行 synthesis 以产出在册现版」不在该句辖域内、**不构成对它的第一次例外**（该句原文与其辖域钉的单源都在 `需求流程.md` §7，本处按引号回指、不另立第二份定义）。

### 3.6 阶段面（Stage Run / Stage Task · v0.11.0 R1 起）

> 本节是 R1 **阶段面执法原文的唯一单源**：`需求流程.md` §0.5「派发纪律双句辖域注」与 §2 Step 0「开轮换面」两处只写语义并回指本节，本节不重贴那两处的语义句。键名 / 事件名**以引擎落地代码为事实源**（未落地的名字不写进本节）。**辖域（v0.11.0 结算轮同步）**：本节除新增外，并**带动**了 §2 表 Step 0 两行的驱动方、§3 门①行的过门判据（两条抬为**三条** + 双档条）、§3 门②行 ④ 的回指点名、§3.5「凭据切分」的内容载体 —— 这些是本节语义的**直接冲突面**，随本卡同改；**未动**的是 §1 主链、「不新增」三件套辖域注、§3 门②行六条的**条数与结构**、§3.5 登记字段值域、§5 工具面清单、§7 同版串行与 `需求流程.md` §2 Step 2 标准动作条。

- **Stage Run / Stage Task 语义（零新表）**：阶段实例由 `(feature_id, stage, round)` **派生** —— 不建 `stage_runs` / `stage_tasks` 表，只给 `tasks` 扩列；一格阶段轮 = 一个 `(stage, round)`；**Stage Task = 带 `task_key` 的 `tasks` 行**（`mode='stage'`；`task_key` 非空 = 「本行由开轮物化产生」的唯一凭据，缺键行不组入轮格，手工写出的 `round` 不构成一轮的事实）。**`pending` 不落行**：开轮即一事务物化「每成员一行」，应收集恒 = 本轮物化行集（离线成员、`queued` 未派发行照旧计入分母），「还没回执」只由 `answer_state='pending'` 承载、**不另立占位行**。三枚答复列值域归引擎：`relevance` ∈ `pending`/`involved`/`not_involved` · `decision` ∈ `pending`/`accepted`/`rejected`（**仅 `involved` 行有值，否则 NULL** —— 该 NULL 是合法缺省形状，不等于「未回执」）· `reason` 自由文本（`not_involved` / `rejected` **必填**）。
- **开轮物化 = 写口 `stage_round_open`**：`stage` **必填且取 `FEATURE_STAGES` 闭集原值**（脏值会炸掉整条读口 ⇒ 写前拒；不得取 Feature 的派生 `stage`、不得自造阶段名）；缺 `targetProjects` ⇒ **本组全员、不预筛**，给定 ⇒ 只物化那几位（定向轮），越出本组成员 ⇒ 整单拒、零写入。幂等走**两道索引闩**（事件键 `(featureId, stage, basisRev)` = 「同一口径 = 同一轮」；行键 `(feature_id, stage, task_key, project_id, round)` 撞 partial 唯一索引 ⇒ 返回既有轮），**不是**应用层的「先查在不在再决定插不插」。
- **另两枚写口只留痕、不流转**：`doc_objection` 落一枚 `stage.doc_objection` 事件（幂等按 `(docVersion, sectionId, objectionId)`），**只标记口径漂移 / 定向重评对象、不自动开轮**、不动任何行的 `answer_state`；`gate1_confirm` 落一枚 `stage.gate1_confirm` 事件（幂等按 `(featureId, round, docHash)`），**是记录动作** —— 真推进仍走 §3 门②行的 `approve`，本口错误码与文案与 `approve` 那一族**互不复用**（防执行侧混用真推状态机）。三者共同点：**均不改主链**（不触 `canTransition`、不改 `features.state`）。
- **三值答复结算**：回执**先按 A2A `state` 分诊、再取三值，两态不互推**（否则 `not_involved` 会被 `completed` 顶成假收口）；解析失败 ⇒ **自动重派一次**（重派必带格式契约原文 + 上轮失败原因，不得原样重发），仍不合契约 ⇒ `answer_state='invalid'` —— **不判任务失败、不落默认值、不静默收口**。
- **收口判据（阶段内、唯一一条）**：`answer_state='valid'` ∧ `based_on_rev` = 本轮 `basisRev` ∧（`relevance='involved'` ⇒ `decision ≠ 'pending'`）。`pending` / `invalid` / `stale` **一律挡收口且被指名**（名单随出参下发 —— 只给计数渲染不出「被指名」）；本轮零行 ⇒ 整格三态取 `null` **而不是 `true`**（空集合上的真空真会把「一轮还没物化完」显示成「已收齐」，直接伪造门① 前提）。其中 **`stale` 读时派生、不落列**：= 行 `based_on_rev` 非空且 ≠ 本轮 `basisRev`，由应用层判据现算（不进 SQL、不回填、不二次改写），库里那一行照旧是 `answer_state='valid'`，被挡在名单里的是**派生态**。
- **轮停在未收口 = 合法停靠形态**：未收口时引擎零写、只带回指名名单，板面长期可见即「未收口」告警面；**禁止**把这条「修复」成超时自动标 `not_involved`（那会污染 R2 基准），离线成员长期 `pending` 是**本条的直接后果**而非缺陷。
- **不复用 scheduler 收敛路径**：收口判定器**自建**，不接入 DAG 收敛 —— `executing → integrating` 的「全部节点 `completed`」判据对阶段行**全盲**是刻意排除，不得反过来当阶段面收口用；**收口不推进主链**（不改 `features.stage`、不构成门）。
- **`stage.round_settled` 事件**：payload `{featureId, stage, round, basisRev, settledAt}`，幂等键 `(featureId, stage, round)`，**只在本轮首次跃迁时写**（状态写 + 收口判定 + 事件写入落**同一事务**；未收口或已记过 ⇒ 零写）。**负向句**：本事件**不属需动作三时点、不构成第四时点**（回指 §7「需动作三时点不变」句，那三枚的枚数与内容照旧，本节不重述其原文）；**拉起面自本版起在引擎侧（v0.11.0 改锚）** —— 原「**唤醒面由板自管**（板侧心跳见本事件自行拉起综合分析 —— 引擎只发事件、不拉确认者、**不发文件**）」句对该事件的**旧形态**描述**就此作废**，不是并存的第二种读法：收口后由**引擎自行物化并执行 synthesis 任务**（见下条 B），板不再为本事件挂心跳档、用户与宿主在此都不必点任何东西。负向句只余一枚且**照旧为真** —— 引擎**不发仓库文件**（辖域见 §3.5「凭据切分」末与 `需求流程.md` §7「文档 mv 分家」辖域钉）。
- **`based_on_rev`**：= 引擎按冻结输入序列现算的 sha256 串（需求原文全文 / 本组成员 projectId **去重且排序** / `stage` / 宿主可选 `basisRevInput`，空值记字面 `-`），**不加 `features` 的 rev 列**；同一输入集必得同值，任一变化 ⇒ 旧答复全量 `stale` 并**提示需重开一轮、不自动开轮**。**负向句**：`based_on_rev` **不是版本对象** —— 不进 §3.5 的两级版本体系（Group 台账 / project 台账 / 归属都不收它）、**不触发单元版本同升**，与 `version` / Project Version 无派生关系。
- **结构化在册《需求确认单》（A · v0.11.0 起，替代「落文件 + `decisions` 登记路径」的新卡形态）**：现版 = **`docVersion` + `sections` + 每节依据指向**三件套，**都在引擎事实源**，不另存第二份。
  - **`docVersion`**：本轮确认单版本，口径 = **`v{round}`**（恒随轮、**不设子版本** —— 用户的异议 / 补充一律走新一轮，故不存在 `v1.1` 这一族）。
  - **`sections`**：**五节闭集**（`problem` / `impact` / `constraints` / `open-questions` / `decisions`），**登记序 = `docHash` 的冻结序列化序**（与入参序、JSON 键序、迭代序无关）；板侧与本包模板按同一清单渲染，**不得另立第二份节清单**。**缺任一节 / 正文脏 / 超上限 ⇒ 整单失败**，只落 `sections: []`（不命中在册）—— **禁止「缺节渲空串」或截断**（那会造出「看着在册、实际缺半」的确认单 = 伪造门① 前提）。
  - **每节依据指向**：节级 `sources[]` = **projectId 清单**（空数组 = 该节不指向具体成员）——「这一节的结论来自哪几位的回执」可追。**与开轮入参 `sources` 同名异义**，消歧见下「键形对照」句。
  - **三动作 → 写口映射（用户只见「文档 + 三个动作」，动作一律由板转发进引擎）**：确认 = **`gate1_confirm`**（幂等 `(featureId, round, docHash)`，见上「另两枚写口」条）· 异议 = **`doc_objection`**（幂等 `(docVersion, sectionId, objectionId)`，定位到**具体版本的具体段落**）· 补充 = **`stage_round_open` 带 `sources`** 开**新一轮**（可定向）。**异议与补充都不直接改在册正文** —— 口径漂移只经新一轮合成重出现版。
  - **版本钉（判据原文在 §3 门①行，此处只登记形状侧的落点）**：`docVersion` 或 `docHash` 一变 ⇒ 此前确认一律 **stale**、**门① 回未过**（板面按「已确认档 = 确认时所指那份的哈希 ⇄ 现版哈希」比较派生，回「待确认」）；**确认对象是版本，不是这张卡**。
  - **兼容**：**存量卡不迁移**（其 `decisions` 只有文件路径）—— 旧文件档与新在册档按 §3 门①行**双档条**任一命中即算在册，本节不要求存量重出。
- **synthesis 任务（B · 综合分析的引擎内执行体，v0.11.0 起）**：本轮**首次跃迁收口**时由**引擎自行物化并执行**（触发点 = 本条上句那枚 `stage.round_settled` **真写出之后**）。行形 = `mode='stage'` + **`task_key='synthesis'`** + `project_id='__engine__'` + 同本轮坐标，**幂等键 = `(feature, stage, round)`**（撞既有 partial 唯一索引 ⇒ 吞冲突回读既有行，**不预判、不跳过**）；引擎专用位 `__engine__` **不进 `machines` 配置、不入派发队列、不占读闸与写忙集**。**对用户不可见**：用户与宿主看到的是它产出的**在册现版**，不再有人在这里承担综合分析 turn。

## 4. Step 2 行为改写（本次核心）

**原**：宿主拆子任务 → 逐条 `a2a_call` 派发 → 自己记依赖 / 轮询 / 催办。进度随 LLM 会话走，宿主必须全程在线。

**新**：宿主把各 project 研发经理回传的**本侧任务清单**（清单由各 project 的**研发经理职责位**产出，见 `需求流程.md` §0.5「Step 2 生成具体任务」行）**一次性**收敛为 Feature DAG —— **三步序 = `create` → `approve` → `version_planning` → `decomposing`（登记 DAG）→ `executing`（拓扑派发）**：

1. `a2a_feature_create(...)` 建 Feature，拿到 `featureId`（此后停在 `waiting_approval`，不派发任何执行任务）；
2. 用户在改造文档确认门 `approve` ⇒ 落 `version_planning`；本 project 的 PjM 出**版本规划评估**、经用户确认结论后宿主按「**先建版、再写归属**」经引擎写口落库，落定后宿主 `advance` ⇒ `decomposing`；
3. 在 `decomposing` 内对每个任务节点调 `a2a_call(project, message, featureId, dependencies, inputs?)` **登记**（不立即派发）—— `dependencies` **只声明直接前置**，登记纪律见 `需求流程.md` §2 Step 2；**DAG 节点登记在 `decomposing`、不在 `waiting_approval`**（挂载白名单不含 `waiting_approval`）。PjM 版本规划与本侧任务清单的派发**不是 DAG 节点**（只读工序会话）。**归属 ≠ 挂载（v0.10.8 补）**：`mode="inquiry"` 的派发同样携带 `featureId`（见 §5），那只是**归属声明**（该次只读询问记在哪条需求名下）—— **不因此成为 DAG 节点**、**不进挂载白名单**（白名单只管 `mode="execute"` 的节点登记）；
4. 登记完毕宿主 `advance` ⇒ `executing`，**由调度器按 `dependencies` 拓扑派发（并行/串行的资源约束由运行底座决定）并自动推进**：就绪即派、等终态，推进判据为**二分** —— **全部节点 `completed`** ⇒ **自动** `executing → integrating`（不停、不交）；**收敛且存在失败**（无可派发 && 无在飞 && 存在失败 / 冻结）⇒ **不转移**：失败只冻结**依赖闭包**下游（未派发者置 `blocked`、**在飞不动**）、其余照跑，Feature **停在 `executing` 零动作**（= 静止，等宿主）。
   **关键措辞**：静止**不是状态转移**（停在主链 `executing`、不进入任何异常态）；**`blocked` 是良性终态、不计入「全完成」**（否则会把「冻结」误当成「全达终态」而错进 `integrating`）。

> **失败账单 episode 口径（v0.6.2 REQ-01 起）**：`feature.failure_report` 以**失败 episode** 为去重单位，**不以「失败节点集合」为单位** —— 同一次失败收敛只发一条账单；**episode 结束后的下一次失败收敛，必须再发一条**，即使失败节点集合与上一条完全相同。
> **episode 边界**：episode **始于一次失败收敛**（无可派发 && 无在飞 && 存在失败，即 §4 二分判据中的「收敛」），**结束于宿主的任一动作** —— `advance(retryTaskIds)` 重派 / 任何推进主链的 `advance` / 新增 `execute` 节点 / 进入 `needs_input` / `cancel`。
> **新两态不产账单（v0.10.5 起 · v0.10.8 措辞收口）**：`version_planning` / `decomposing` 两态**不登记任何 DAG 节点** ⇒ 不产生失败收敛、不发 `feature.failure_report`；上面两条 episode 判据**仍只针对 `executing`** 内的节点收敛，不向这两态扩展。
> **本规范只约束可观测语义**：**每一次失败收敛 ⇔ 恰好一条账单**（无论该收敛由宿主动作还是其它原因触发）；**去重键如何构造属运行底座实现**，不在规范内描述。

> **failureKind 值域登记（2026-10-21 宿主裁定 · 协议 2.4）**：节点级失败结算携带 `failureKind` 分类字段，**值域成员与语义**——`provider` = 厂商侧错误（欠费 / 鉴权 / 限流）；`model_queue` = 预留值（machine 恒不产出、orch 本轮不产出）。**产方 / 消费方**：产方 = machine（源头识别，orch 兜底）；消费方 = orch 落库，board 与看护只读展示。**划界**：`failureKind` 只分类**节点级失败结算**，不动 Feature 级 `failed`（DAG 非法专用，见 §1 口径注）的既有口径。**正交**：本登记不蕴含自动重派，重派与否仍**须宿主决策**、恒走 `advance(retryTaskIds)`（见下段与 §5）。

宿主在 Step 2 保留的编排职责 = **收敛**各 project 研发经理回传的**本侧任务清单**（收敛与登记权 **≠** 单方决定权 —— 宿主不替单元拆本侧任务，见 `需求流程.md` §0.5）、**登记 DAG**（把收敛后的清单落成有依赖关系的节点）、**同轮把清单贴给用户**、**判断何时 advance**（引擎停在 `needs_input`（澄清）或 `executing` 静止（失败收敛）时）。等待、轮询、续约、失败判定、状态推进全部由**代码组件**承担，LLM 不参与。**失败不得笼统按「失败 ⇒ 重派」处理** —— 失败收敛只把 Feature 停在 `executing` 静止，重派与否**须宿主决策**。**宿主重派与运行底座自动续跑是两条正交留痕**（重派 = `advance(retryTaskIds)`；自动续跑由运行底座在本节点内自行完成并另行留痕），读账时**不得混同**。**重派分两路、边界在节点集合**：**（i）重派既有失败节点** = `advance(..., retryTaskIds)`（重放 Feature 内已 `failed` 节点并解冻其被冻结下游 —— **不新增节点、Feature 态不变**）；**（ii）新增业务节点** = `a2a_call(mode="execute", featureId=…)` 登记（现成通道，不变）。二者不互相替代。

> **默认形态（2026-09-15 定）**：**自 v0.4.1 之后的新需求起，Step 2 默认采用本节的 Feature DAG 形态**。仅在特殊情形（如该需求本身正在改造调度引擎，用旧引擎跑会命中待修的失败传播）才可退化为逐步 `a2a_call` 派发，且**必须在改造文档中注明理由与降级路径**（登记口径见 `需求流程.md` §2 Step 2 H3；v0.4.1 的 REQ-03 即属此例外）。

### 4.1 同一版本内多需求必须串行（v0.6.2 起）

- **纪律**：**同一版本内的多条需求必须串行执行** —— 一条需求走到终点，再起下一条；「需求间并行」不排期（已废弃）。
- **宿主执行方式**：第 2 条及以后的 Feature **建卡后停在 `waiting_approval`**，**待前一条主轨「在占名额」清空才 `approve`** —— 「在占名额」的集合与「主轨失败静止不占名额」均由 `需求流程.md` §7「同版串行纪律」**单处定名**，本处只回指、**不重列三态集合**；`approve` 仍是唯一准入（`waiting_approval → version_planning`，见 §3 门表）；**禁止两个及以上 Feature 同时处于 `executing`**。
- **边界澄清**：引擎的串行能力**只到项目粒度、且跨 Feature 生效**（同一项目同一时刻只推进一项**写**工作；只读工作不受写忙集排队，但仍受写门（写在飞）与读闸 `maxConcurrentReads` 约束，见 §4.1 补充并发语义矩阵）；**引擎不提供需求间串行** ⇒ 该纪律**只能由宿主在「过审」这一动作的时点把控**，**不能依赖调度器**。
- **责任主体口径（v0.8.6 补）**：上两条**就同一个编排 agent / 同一组而言** —— 多编排 agent 接同一底座时「宿主」为复数，各自把控本组需求的过审时点；不同组的 Feature 同时 `executing` 不违反本纪律（各组项目集互斥，无共享资源冲突）；**角色实体数 = 1** 的口径见 `需求流程.md` §0.5「宿主层定位（单一角色）」块（该处管角色实体数，本条管责任主体为复数），互指不重复定义。
- （v0.9.1 交叉引用）「走到终点」的逐格推进判据清单见 `需求流程.md` §2 Step 3，`note` 留痕口径见 §2 读法与 §5。

#### 4.1 补充：并发语义矩阵（v0.8.10）

> 本节把本版定稿的「场景 × 可否并行」语义固化，作为 §4.1 主文四条 bullet 的补充，不改变主文编号与语义。事实源 = 本版冻结实现与真机实测（附脚注）。

**1. 串行单位 = project（不是 Feature）**

并发的串行单位是 **project**：同 project 串行、跨 project 真并行。「Feature 间串行」「Feature 内串行」等说法都只是「同 project 串行」的特例，不是独立规则。（**回注，v0.10.1**：本节的「project」指**调度面的执行单位**，与版本面的 project 台账 / 归属（§3.5）是同一套项目标识的**两个正交用途** —— 串行单位是 project 这一断言**不因 project 版本面而下沉或改动**，版本记账也不反过来影响认领序。）

**2. 四边矩阵（同 project 内）**

| 组合 | 可否并行 | 依据 |
|---|---|---|
| 读 × 写 | ✅ 可并行（**读不挡写**） | 只读档退出写忙集 |
| 写 × 读 | ❌ 等（**写挡读 —— 本版刻意不放开**） | 写档在飞 ⇒ 项目忙 ⇒ 同 project 读写节点一律等 |
| 读 × 读 | ✅ 门径可并行（受 machine 读闸 `maxConcurrentReads` 限；**缺省 1 ⇒ 实际仍串行**） | 只读档不入忙集 |
| 写 × 写 | ❌ 互斥 | 写档入忙集 |

**跨 project：一律真并行**（无跨项目闸）。

**3. 三条不变量（防后人误当缺陷修）**

- **同批同 project 至多认领一个**（`computeReadyNodes` 的批次布尔）**刻意不改** ⇒ 「同 project 一次只放一个」是防洪泛特性；下一个（约 30s 的调度拍 / 事件触发）才放第二个。
- **写优先只是候选窗（`LIMIT 50`）内序**，不是绝对序。
- DAG 只读节点在持续有写的 project 上**会被推迟** = 写优先的设计意图。

**4. 两把闸（machine 侧执法，与项目组正交）**

`agentConfig.maxConcurrentWrites` / `maxConcurrentReads`，**缺省 1/1**，**按 project 分席**、FIFO 排队；**派发预算从放行时刻起算**（不吃排队时长）。**orch 不做第二道闸**（避免两台限流器互相看不见）。

**5. 声明机制**

`a2a_call(readOnly=true)` → `tasks.lane='read'`（缺失 / 非 `true` ⇒ 按 write）→ `DispatchCommand.readOnly`；**inquiry 恒为 read 档**。**只读是「声明」不是「强制」**（引擎看不见任务动哪些文件）。

**6. 两个时钟不得相加**

orch 领取队列的等待 ≠ machine 本机闸内等待，二者独立计量，不得相加解释。

**7. 真机实测脚注（2026-09-24）**

- 读不挡写：`flow` 项目中 4 个只读在飞时登记写节点，仍被领（读不让写等）；
- 读不挡读：第 2、3 个只读在第 1 个仍在飞时被领；
- 写挡读：写在飞时只读报 `waitReason=project_busy`（`projectBusy.taskId` = 写节点）；
- 写互斥：写节点落定后下一个写才被领；
- 读闸配 `maxConcurrentReads=2` 后：同 project 同刻**最多 2 个**只读任务真并行（宿主机进程表实测），第三个等席；
- 跨 project 并行：上述所有探针跨项目同时跑。

## 5. 工具面

工具面为「**泛型工具 7 + Feature 工具组 6**」，静态注册、零重连：

- 泛型 7：`a2a_projects` / `a2a_call` / `a2a_task_status` / `a2a_tasks` / `a2a_cancel` / `a2a_events` / `a2a_wait`
- Feature 6：`a2a_feature_create` / `a2a_feature_status` / `a2a_feature_advance` / `a2a_feature_approve` / `a2a_feature_cancel` / `a2a_feature_trace`

用法要点：

- `a2a_feature_create(...)`：建 Feature（初态恒为 `waiting_approval`；登记字段初值恒定 `stage=需求分析` + `approval=未发起`，**二者不再是 create 入参**，见 §3.5「初值恒定」条）；登记字段入参**仅 `version` 保留**（排期语义，见 §3.5）；此外 **v0.9.3 起支持 optional `parentFeatureId`**（增补 Feature 挂主需求；一次性写入、创建后不可补写/改写，校验 fail-closed、父链不递归，见 §3.5）。
- `a2a_call(project, message, contextId?, wait?, mode, featureId)`：`mode` **必填**；**`featureId` 两种 mode 均必填**（v0.10.8 起）—— 任一 mode 缺 `featureId` ⇒ **结构化拒收、不建任务**（错误码字面属执法原文，不在本包）：
  - `mode="inquiry"`：只读询问/核实/调研 ⇒ **立即派发**，与既有行为一致；所带 `featureId` 只是**归属声明**（**归属 ≠ 挂载**，见 §4）—— 不登记 DAG 节点、不进挂载白名单；
  - `mode="execute"`：执行型派发 ⇒ **登记**该 Feature 的队列节点，由调度器按 `dependencies` 拓扑派发。
  - **`contextId` 的取值纪律**（何时续用同一会话 / 何时另起）见 `需求流程.md` §0.5「会话复用纪律」—— 本文件不另存一份口径。
- `a2a_feature_advance(featureId, to, note?, answer?, retryTaskIds?)`：推进主链，状态机校验合法后继；**`waiting_approval` 上任何改动 `state` 的 `to` 都被拒**（**不存在「换一个 `to` 值就能出该态」的写法** —— 唯一出路是 `approve`；`to` = 当前态的登记写不属本条，见 §3.5）；`answer` 用于 `needs_input` 补齐后续推。`retryTaskIds?`：**仅用于失败重派**（重派指定 `failed` 节点并解冻其被冻结下游）；**空集合 / 任一 id 非法 / 与 `answer` 同传 ⇒ 拒绝**（结构化错误、Feature 态不变）；`answer` 仍**仅**承载 `input-required` 澄清。**`note` 的推进凭据语义（v0.9.1）**：推进主链的每次 `advance` 以 `note` 携带本格判据的回执（门禁 / 真机验收 / 用户验收结论，清单见 `需求流程.md` §2 Step 3）—— 人判留痕，非机器校验；与「`to` = 当前态 ∧ 带登记字段」的登记写入是两回事（后者不改状态，见 §3.5）。
- `a2a_feature_approve(featureId)`：唯一审批门，`waiting_approval → version_planning`（v0.10.5 起后继抬为 `version_planning`，见 §3 门表）；过门判据见 §3 门②行。
- `a2a_feature_trace(featureId)`（v0.8.10 补）：**只读工具**，随 Feature 工具组静态注册，给出节点排队/等待的可观测面。出参要点：
  - 逐**非终态**节点给出：`waitReason` · `position`（位次，与实领序同键 = `queued_at`）· `waitedSince` · `lane` · `projectBusy{busy,taskId,machineId}` · `readOccupants[]`；
  - `waitReason` **闭集八值**：`awaiting_user` / `running_remote` / `queued` / `upstream_dependencies` / `feature_not_executing` / `project_busy` / `read_lane_running` / `ready_pending_dispatch`；
  - `projectBusy` **只反映写门**；写门没挡却还没开工时看 `readOccupants[]`（`waitReason='read_lane_running'`）。
- 任务结果与 Feature 态均落库，宿主可随时 `a2a_feature_status` / `a2a_tasks` 找回。
- `a2a_events` / `a2a_wait` 为**事件收件箱**的状态语义面：Feature 迁出（如 `executing → integrating`）与失败收敛的**可观测面**，供宿主感知并据此执行状态机操作。

## 6. 异常态处置

| 异常 | 状态 | 处置 |
|---|---|---|
| 任务需澄清 | `needs_input` | 引擎自动置入；用户给出澄清后，宿主以 `advance(to=executing, answer=…)` 并入原节点消息、重新派发，继续 DAG。**注（2026-09-26 引擎核实，与 §2 表同口径）**：`needs_input` 仅 `executing` 可进可出、主链无回边 ⇒ 终验段（`integrating`/`testing`/`reviewing`）无该路径，不存在「验收期澄清续推」的第二套说法 |
| 任务失败（业务失败） | **不进本表**（Feature 保持 `executing`） | 只冻结依赖闭包下游 + 收敛静止（见 §2 表「任务失败」行与 §4 二分判据）；`failed` 仅 DAG 非法专用（见 §1 口径注）。**`retryTaskIds` 仅 `executing` 内存在 `failed` 节点时适用**（`version_planning` / `decomposing` 两态不派发节点 ⇒ 无节点可重派、无重派面）。节点结算分类字段 `failureKind` 的值域登记见 §4。 |
| 新两态内的澄清（工序期） | **不进本表**（`version_planning` / `decomposing` 不挂 `needs_input`） | 工序内的澄清走**会话内多轮**（同一 `contextId` 续接、只读会话），**不改状态机态、不产 `input-required`**；`needs_input` 的挂载白名单仅 `executing`/`waiting_approval`，本行不改写该白名单 |
| 用户取消 | `cancelled` | 任意非终态经 `cancel` 终止；终态中仅 `failed` 可经 **`cancel` 操作口**归档为 `cancelled`（发版收口路径；**`advance` 面无此路径**），`completed` / `cancelled` 不可 |

> **负向注（v0.6.1 REQ-05 起）**：**失败收敛不进入本表任何一行**（不转 `needs_input`、不转 `failed`）—— 业务失败**不是异常态**：Feature 停在主链 `executing` **静止**（零动作、等宿主），账单经事件 `feature.failure_report` + `a2a_feature_status`（可选 `text` / `contextId`）承载。本表与 §2 表同口径，不存在第二套说法。（episode 口径见 §4）

## 7. 三方驱动边界

| 角色 | 该做 | 不该做 |
|---|---|---|
| **宿主（LLM）** | 组织各项目分析、汇总方案、**收敛本侧任务清单并登记 DAG**、判断何时推进、执行状态机操作；**`version_planning` / `decomposing` 两格内主持工序会话并 `advance` 推进**（v0.10.5 起） | 不逐条派活、不自己轮询、不催办、不替各 project 单方拆本侧任务 |
| **引擎（代码）** | 按 `dependencies` 拓扑派发（并行/串行的资源约束由运行底座决定）、等待终态、续约、失败传播（= 冻结依赖闭包）、`executing → integrating` 自动流转（全 `completed` 时） | 不判断方案好坏、不替用户拍板、不猜澄清内容；**不在 `version_planning` / `decomposing` 派发任何节点**（两态无节点 ⇒ 无失败收敛与账单，见 §4） |
| **用户** | 过两道确认门、答澄清、收结果 | 不必逐步催下一环 |

> **可观测语义（v0.7.1 REQ-01 起）**：宿主在**需动作三时点**——完成（Feature 离开 `executing` 进 `integrating`）· 失败收敛静止（**保持 `executing` 静止**）· 需澄清（`needs_input`）——经**运行底座（代码组件）给出的可观测信号**被感知，并据此执行状态机操作；**等待由运行底座（代码组件）承担，不靠人工提醒**，**LLM 不执行等待与轮询**；终态（`cancelled` / `failed`（DAG 非法））与 `timeout` **不属**需动作三时点。
>
> **需动作三时点不变（v0.10.5 起）**：上条三时点的**枚数与内容均不变** —— `version_planning` / `decomposing` 两态**不新增时点**（两态无节点收敛、无 `needs_input`，见 §4 / §6），由宿主自行 `advance` 推进，不靠运行底座唤醒。

边界一旦清楚，流程就不依赖"宿主记得住纪律"，而是依赖"状态机拒绝非法流转"。

> **观测面写入不属编排（v0.10.0 补）**：登记字段（`stage`/`version`/`approval`）与版本面（版本台账状态、排期写）的写入属**观测面写入**，不属编排 —— 与 §8 边界口径一致（**编排**指登记 DAG / 派发 / 推进主链），网页等操作面不得据此成为第二编排入口。

## 8. 前瞻解耦（写规范时必须遵守）

本文件的写法与三件事**解耦**，使未来演进**不改本规范**：

| 维度 | 现在 | 未来 | 本文件怎么写 |
|---|---|---|---|
| 操作面 | MCP 工具 | 网页服务（v0.8 / v0.9） | 门禁只写成**状态机操作**（`advance` / `approve` / `answer`），**不写死"调用某工具"**。网页与 MCP 是同一状态机的两个驱动口，网页**不得**成为第二编排入口（**编排**指登记 DAG / 派发 / 推进主链；登记字段的观测面写入不属编排） |
| 项目来源 | 各机自持，宿主经发现拿到 | orch 期望态 / 远程项目（v0.6.0） | 只写「派发到某项目」，**不描述"项目从哪来"** |
| Transport | Launcher + A2A | Runner 反向注册 pull（v0.7.0 修订；SSH 已废弃） | **不描述传输**，规范只谈状态与派发语义 |

一句话：规范描述**状态机语义**，实现细节（工具名、项目发现、传输）留给运行底座。这样换操作面、换项目来源、换传输，流程规范都不用改。
