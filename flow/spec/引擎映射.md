# 引擎映射

> **规范版本戳**：v0.9.1（2026-09-25）
>
> 本文件属于**流程规范包内核**，与同目录 [`需求流程.md`](./需求流程.md) 配套：前者定义 Step 0-3 的判据与产出物，本文件定义同一套流程如何落到 Feature 引擎的状态机上。
> **项目无关**：不绑定任何具体仓库、项目或宿主实现。

## 1. 核心命题

需求流程的每一步，都对应 Feature 状态机上的一个状态；每次状态推进，都有**唯一确定的驱动方**（宿主 / 用户 / 引擎自身）。宿主不再"逐步派活 + 轮询催办"，而是**在关键点做状态机操作**，其余交给引擎。

**为什么必须引擎化**：MCP 是**拉模型**，callback 无法唤醒宿主会话。因此"宿主逐条 `a2a_call` + 自己轮询"会把整条需求的进度**绑死在 LLM 会话**上：宿主一停，任务即停；宿主一长，上下文即爆。**引擎驱动是让任务在宿主不参与时继续推进的唯一方式**。

**状态机速览**（v0.4.1 REQ-04 收敛后）：

- **主链（6 态）**：`waiting_approval → executing → integrating → testing → reviewing → completed`
- **异常态（3）**：`needs_input` / `failed` / `cancelled`
- **终态（3）**：`completed` / `failed` / `cancelled`

> **口径注（v0.6.1 REQ-05 起）**：`failed` 语义**收窄**为 **DAG 非法（环 / 悬空）fail-fast 专用** —— **业务失败不再产出 Feature `failed` 终态**（Feature 停在 `executing` 静止，见 §4 二分判据）；`blocked` 是**良性终态**，**不计入「全完成」**。上述「异常态 / 终态」均就 **Feature 级**而言：**节点 `failed` 可经重派复活**（见 §5 `retryTaskIds`），Feature 不因业务失败进入终态。

**引擎只做「需求实现」**：主链起点 = `waiting_approval`（= Step 1 产出→门的停靠点；**v0.9.0 起需求实体可于提需求时创建并长停靠在此** —— `stage`/`version`/`approval` 是**登记字段（观测面），不是状态机态**，见 §3.5）；`approve` 是**唯一准入**（`advance(to="executing")` 被拒，错误码 `feature_approval_required`；**v0.9.0 起并校验 `approval = 待审批`**）。`executing → integrating` 是**引擎自动**（**全部节点 `completed`**；收敛且存在失败 ⇒ **不转移**，见 §4 二分判据）；`integrating → testing → reviewing → completed` 由**宿主 `advance`**。

## 2. 步骤 ↔ Feature 状态 ↔ 驱动方

| 流程步骤 | Feature 状态 | 驱动方 |
|---|---|---|
| Step 0 需求访谈 → 需求确认单 | **（主链不推进；实体或已进引擎，`stage`=`需求分析`，§3.5）** | 宿主（+ 用户确认）；产出物按流程落文件 |
| 【确认需求内容】 | **（主链不推进）** | **用户确认**（凭据分两半，v0.9.0：确认**内容** = 需求确认单落文件；确认**动作** = `stage`「需求分析 → 改造方案」迁移的引擎记录，见 §3.5；不新增状态机流转） |
| Step 1 评估 + 改造文档 | **（引擎不参与）** | 宿主（+ 各单元本侧评估/边界确认） |
| 【确认改造文档】 | `waiting_approval → executing` | **用户 `a2a_feature_approve`**（**唯一准入**；宿主在收到确认后立即调用） |
| **Step 2 需求实现** | `executing` | **引擎自动**（拓扑派发（并行/串行的资源约束由运行底座决定）· 等待 · 失败传播=冻结依赖闭包）+ 宿主**一次性**登记 DAG（**同轮把 DAG 清单贴给用户**） |
| Step 3 测试 / 反馈 → 通过 | `integrating → testing → reviewing → completed` | **宿主 `advance`** |
| 任务需澄清 | ` → needs_input` | **引擎自动**（任务 `input-required`） |
| 任务失败 | `executing`（**不离开**，非转移） | **引擎自动**（仅冻结**依赖闭包**下游：未派发者置 `blocked`、**在飞不动**；无可派发且无在飞且存在失败 ⇒ **保持 `executing` 静止**，账单经事件 `feature.failure_report` + `a2a_feature_status`（可选 `text` / `contextId`））（账单按 **失败 episode** 发，口径见 §4） |

> **Step 2 的起点**：需求实体**可于提需求时创建**（v0.9.0，板 `a2a_feature_create`，显式传 `stage=需求分析` + `approval=未发起`；缺省创建仍为 `stage=改造方案` + `approval=待审批` ⇒ 既有行为不变），初态一律 `waiting_approval` → 方案确认后登记 DAG 节点、`approval` 置 `待审批` → `a2a_feature_approve` 放行（校验 `approval = 待审批`）⇒ 引擎接管。

读法：一张需求 = 一个 Feature；一行 = 一次状态变更（或一次**非转移操作**，如「任务失败」停在 `executing`、**登记字段写入**〔`advance`「`to` = 当前态 ∧ 带登记字段」特例，见 §3.5〕）；「驱动方」列即该变更的**发起者**。Step 1 内部三态连推（`analyzing → planning → waiting_approval`）与 Step 3 内部三态连推，均由宿主 `advance`，中途不必停。**「不必停」仅指中间态不停靠**（v0.9.1 补）—— 每一格转移仍须 `note` 带凭据（判据清单见 `需求流程.md` §2 Step 3），且 `reviewing → completed` 之前必须有明确的用户验收结论。

## 3. 两道确认门的挂载

流程里**只有两个用户介入点**，两者都显式挂到状态机，不是散落在正文里的"人工约定"：

| 门 | 语义 | 挂载方式 |
|---|---|---|
| **需求确认门** | 「我理解你要解决的是不是这个问题」 | **不在状态机上**（主链不推进）：凭据分两半（v0.9.0）—— 确认**内容** = `doc/{版本}/{topic}-需求确认单.md` **落文件**；确认**动作** = **`stage`「需求分析 → 改造方案」迁移的引擎记录**（§3.5；实体已进引擎时承载，不扩值域）。前置：宿主持有**相关执行单元的事实核实**。v0.4.1 REQ-04 起，Step 0/1 不推进主链 |
| **改造文档确认门** | 「方案经用户确认后才开始实现」 | **唯一准入 = `approve`**：`waiting_approval → executing`；**v0.9.0 起 `approve` 校验 `approval = 待审批`、不看 `stage`**（不满足 ⇒ 结构化拒绝，错误码 `feature_approval_not_ready`）。**语义**：**记录已发生的用户确认（一对一映射：不可预领、不可补领）** —— 宿主在收到用户确认后**立即**调用，**不是新增一次用户决策**；**禁止**在用户未确认方案前调用。**前置**：各相关执行单元已确认**接受该边界且无重复改造**（多轮收敛，≤3 轮未达成则升级用户）。未 `approve` 前调度器停在等待点，不派发任何执行任务；且 **`advance(to="executing")` 被拒**（`feature_approval_required`） |

> 两个门把「流程纪律」变成「状态机约束」：不是靠宿主自觉，而是**未过门则推进被拒**（非法流转 fail-fast）。

### 3.5 登记字段 ↔ 流程步骤映射（v0.9.0 起）

`features` 携带三个**登记字段** `stage` / `version` / `approval` —— **观测面，不是状态机态**：不改 §1 的主链 / 异常态 / 终态，不增判据条数、不增产出物。需求实体可于提需求时即创建（初态仍 `waiting_approval`）；登记字段的写入经 `a2a_feature_advance` 的「`to` = 当前态 ∧ 带登记字段」**显式特例**（照 `retryTaskIds` 先例，**状态机零改动**；该特例无终态守卫，否则 `发版` 写不进去）。

- **`stage`（阶段）** 值域 = `需求分析` / `改造方案` / `改造` / `回归` / `发版` —— **只登记「引擎看不见的段」**（需求分析 / 改造方案 / 发版）；改造 / 回归 / 验收**由引擎态派生**，不重复登记。
- **`approval`（门状态）** 值域 = `未发起` / `待审批` / `已通过`（**单向、无回边**）；**`approve` 校验 `approval = 待审批`** —— **门看 `approval`，不看 `stage`**。
- **缺省（向后兼容）**：`create` 不传 ⇒ `stage = 改造方案` + `approval = 待审批` ⇒ 既有调用行为不变；板建需求显式传 `stage = 需求分析` + `approval = 未发起`。写手 = 宿主 agent（写完改造文档置 `待审批`）。

**映射表**：

| 场合 | 登记字段口径 |
|---|---|
| Step 2 / Step 3 期间 | `stage` 保持「改造方案」定值（改造 / 回归由引擎态派生，不写 `stage`） |
| 需求确认门凭据 | = 「`需求分析 → 改造方案` 迁移」的**引擎记录**（不扩值域） |

**凭据切分**：确认**动作**（谁 / 何时 / 对哪个阶段）= **引擎记录**；确认**内容** = **文件事实源**（需求确认单 / 改造文档落文件的判据不废，见 `需求流程.md` §2「每步推进的强制条件」）。

## 4. Step 2 行为改写（本次核心）

**原**：宿主拆子任务 → 逐条 `a2a_call` 派发 → 自己记依赖 / 轮询 / 催办。进度随 LLM 会话走，宿主必须全程在线。

**新**：宿主**一次性**把改造方案落为 Feature DAG：

1. `a2a_feature_create(...)` 建 Feature，拿到 `featureId`；
2. 对每个任务节点调 `a2a_call(project, message, featureId, dependencies, inputs?)` **登记**（不立即派发）；
3. 用户在改造文档确认门 `approve` 后，**由调度器按 `dependencies` 拓扑派发（并行/串行的资源约束由运行底座决定）并自动推进**：就绪即派、等终态，推进判据为**二分** —— **全部节点 `completed`** ⇒ **自动** `executing → integrating`（不停、不交）；**收敛且存在失败**（无可派发 && 无在飞 && 存在失败 / 冻结）⇒ **不转移**：失败只冻结**依赖闭包**下游（未派发者置 `blocked`、**在飞不动**）、其余照跑，Feature **停在 `executing` 零动作**（= 静止，等宿主）。
   **关键措辞**：静止**不是状态转移**（停在主链 `executing`、不进入任何异常态）；**`blocked` 是良性终态、不计入「全完成」**（否则会把「冻结」误当成「全达终态」而错进 `integrating`）。

> **失败账单 episode 口径（v0.6.2 REQ-01 起）**：`feature.failure_report` 以**失败 episode** 为去重单位，**不以「失败节点集合」为单位** —— 同一次失败收敛只发一条账单；**episode 结束后的下一次失败收敛，必须再发一条**，即使失败节点集合与上一条完全相同。
> **episode 边界**：episode **始于一次失败收敛**（无可派发 && 无在飞 && 存在失败，即 §4 二分判据中的「收敛」），**结束于宿主的任一动作** —— `advance(retryTaskIds)` 重派 / 任何推进主链的 `advance` / 新增 `execute` 节点 / 进入 `needs_input` / `cancel`。
> **本规范只约束可观测语义**：**每一次失败收敛 ⇔ 恰好一条账单**（无论该收敛由宿主动作还是其它原因触发）；**去重键如何构造属运行底座实现**，不在规范内描述。

宿主在 Step 2 保留的编排职责**只剩两件**：**拆 DAG**（把方案切成有依赖关系的节点）、**判断何时 advance**（引擎停在 `needs_input`（澄清）或 `executing` 静止（失败收敛）时）。等待、轮询、续约、失败判定、状态推进全部由**代码组件**承担，LLM 不参与。**重派分两路、边界在节点集合**：**（i）重派既有失败节点** = `advance(..., retryTaskIds)`（重放 Feature 内已 `failed` 节点并解冻其被冻结下游 —— **不新增节点、Feature 态不变**）；**（ii）新增业务节点** = `a2a_call(mode="execute", featureId=…)` 登记（现成通道，不变）。二者不互相替代。

> **默认形态（2026-09-15 定）**：**自 v0.4.1 之后的新需求起，Step 2 默认采用本节的 Feature DAG 形态**。仅在特殊情形（如该需求本身正在改造调度引擎，用旧引擎跑会命中待修的失败传播）才可退化为逐步 `a2a_call` 派发，且**必须在改造文档 / planlog 中注明理由与降级路径**（v0.4.1 的 REQ-03 即属此例外）。

### 4.1 同一版本内多需求必须串行（v0.6.2 起）

- **纪律**：**同一版本内的多条需求必须串行执行** —— 一条需求走到终点，再起下一条；「需求间并行」不排期（已废弃）。
- **宿主执行方式**：第 2 条及以后的 Feature **建好并登记 DAG 后停在 `waiting_approval`**，**仅在前一条需求 `completed` 之后**才过审放行（`waiting_approval → executing` 是唯一准入）；**禁止两个及以上 Feature 同时处于 `executing`**。
- **边界澄清**：引擎的串行能力**只到项目粒度、且跨 Feature 生效**（同一项目同一时刻只推进一项**写**工作；只读工作不受写忙集排队，但仍受写门（写在飞）与读闸 `maxConcurrentReads` 约束，见 §4.1 补充并发语义矩阵）；**引擎不提供需求间串行** ⇒ 该纪律**只能由宿主在「过审」这一动作的时点把控**，**不能依赖调度器**。
- **责任主体口径（v0.8.6 补）**：上两条**就同一个编排 agent / 同一组而言** —— 多编排 agent 接同一底座时「宿主」为复数，各自把控本组需求的过审时点；不同组的 Feature 同时 `executing` 不违反本纪律（各组项目集互斥，无共享资源冲突）。
- （v0.9.1 交叉引用）「走到终点」的逐格推进判据清单见 `需求流程.md` §2 Step 3，`note` 留痕口径见 §2 读法与 §5。

#### 4.1 补充：并发语义矩阵（v0.8.10）

> 本节把本版定稿的「场景 × 可否并行」语义固化，作为 §4.1 主文四条 bullet 的补充，不改变主文编号与语义。事实源 = 本版冻结实现与真机实测（附脚注）。

**1. 串行单位 = project（不是 Feature）**

并发的串行单位是 **project**：同 project 串行、跨 project 真并行。「Feature 间串行」「Feature 内串行」等说法都只是「同 project 串行」的特例，不是独立规则。

**2. 四边矩阵（同 project 内）**

| 组合 | 可否并行 | 依据 |
|---|---|---|
| 读 × 写 | ✅ 可并行（**读不挡写**） | 只读档退出写忙集 |
| 写 × 读 | ❌ 等（**写挡读 —— 本版刻意不放开**） | 写档在飞 ⇒ 项目忙 ⇒ 同 project 读写节点一律等 |
| 读 × 读 | ✅ 门径可并行（受 machine 读闸 `maxConcurrentReads` 限；**缺省 1 ⇒ 实际仍串行**） | 只读档不入忙集 |
| 写 × 写 | ❌ 互斥 | 写档入忙集 |

**跨 project：一律真并行**（无跨项目闸）。

**3. 三条不变量（防后人误当缺陷修）**

- **同批同 project 至多认领一个**（`computeReadyNodes` 的批次布尔）**刻意不改** ⇒ 「同 project 一次只放一个」是防洪泛特性；下一个（约 30s 的调度拍 / 事件触发）才放第二个。
- **写优先只是候选窗（`LIMIT 50`）内序**，不是绝对序。
- DAG 只读节点在持续有写的 project 上**会被推迟** = 写优先的设计意图。

**4. 两把闸（machine 侧执法，与项目组正交）**

`agentConfig.maxConcurrentWrites` / `maxConcurrentReads`，**缺省 1/1**，**按 project 分席**、FIFO 排队；**派发预算从放行时刻起算**（不吃排队时长）。**orch 不做第二道闸**（避免两台限流器互相看不见）。

**5. 声明机制**

`a2a_call(readOnly=true)` → `tasks.lane='read'`（缺失 / 非 `true` ⇒ 按 write）→ `DispatchCommand.readOnly`；**inquiry 恒为 read 档**。**只读是「声明」不是「强制」**（引擎看不见任务动哪些文件）。

**6. 两个时钟不得相加**

orch 领取队列的等待 ≠ machine 本机闸内等待，二者独立计量，不得相加解释。

**7. 真机实测脚注（2026-09-24）**

- 读不挡写：`flow` 项目中 4 个只读在飞时登记写节点，仍被领（读不让写等）；
- 读不挡读：第 2、3 个只读在第 1 个仍在飞时被领；
- 写挡读：写在飞时只读报 `waitReason=project_busy`（`projectBusy.taskId` = 写节点）；
- 写互斥：写节点落定后下一个写才被领；
- 读闸配 `maxConcurrentReads=2` 后：同 project 同刻**最多 2 个**只读任务真并行（宿主机进程表实测），第三个等席；
- 跨 project 并行：上述所有探针跨项目同时跑。

## 5. 工具面

工具面为「**泛型工具 7 + Feature 工具组 6**」，静态注册、零重连：

- 泛型 7：`a2a_projects` / `a2a_call` / `a2a_task_status` / `a2a_tasks` / `a2a_cancel` / `a2a_events` / `a2a_wait`
- Feature 6：`a2a_feature_create` / `a2a_feature_status` / `a2a_feature_advance` / `a2a_feature_approve` / `a2a_feature_cancel` / `a2a_feature_trace`

用法要点：

- `a2a_call(project, message, contextId?, wait?, mode, featureId?)`：`mode` **必填** ——
  - `mode="inquiry"`（**不得带 `featureId`**）：只读询问/核实/调研 ⇒ **立即派发**，与既有行为一致；
  - `mode="execute"`（**必带 `featureId`**）：执行型派发 ⇒ **登记**该 Feature 的队列节点，由调度器按 `dependencies` 拓扑派发。
  - 对偶校验错误码：`feature_required_for_execute` / `feature_not_allowed_for_inquiry`。
- `a2a_feature_advance(featureId, to, note?, answer?, retryTaskIds?)`：推进主链，状态机校验合法后继；**`to="executing"` 在 `waiting_approval` 被拒**（请用 `approve`）；`answer` 用于 `needs_input` 补齐后续推。`retryTaskIds?`：**仅用于失败重派**（重派指定 `failed` 节点并解冻其被冻结下游）；**空集合 / 任一 id 非法 / 与 `answer` 同传 ⇒ 拒绝**（结构化错误、Feature 态不变）；`answer` 仍**仅**承载 `input-required` 澄清。**`note` 的推进凭据语义（v0.9.1）**：推进主链的每次 `advance` 以 `note` 携带本格判据的回执（门禁 / 真机验收 / 用户验收结论，清单见 `需求流程.md` §2 Step 3）—— 人判留痕，非机器校验；与「`to` = 当前态 ∧ 带登记字段」的登记写入是两回事（后者不改状态，见 §3.5）。
- `a2a_feature_approve(featureId)`：唯一审批门，`waiting_approval → executing`。
- `a2a_feature_trace(featureId)`（v0.8.10 补）：**只读工具**，随 Feature 工具组静态注册，给出节点排队/等待的可观测面。出参要点：
  - 逐**非终态**节点给出：`waitReason` · `position`（位次，与实领序同键 = `queued_at`）· `waitedSince` · `lane` · `projectBusy{busy,taskId,machineId}` · `readOccupants[]`；
  - `waitReason` **闭集八值**：`awaiting_user` / `running_remote` / `queued` / `upstream_dependencies` / `feature_not_executing` / `project_busy` / `read_lane_running` / `ready_pending_dispatch`；
  - `projectBusy` **只反映写门**；写门没挡却还没开工时看 `readOccupants[]`（`waitReason='read_lane_running'`）。
- 任务结果与 Feature 态均落库，宿主可随时 `a2a_feature_status` / `a2a_tasks` 找回。
- `a2a_events` / `a2a_wait` 为**事件收件箱**的状态语义面：Feature 迁出（如 `executing → integrating`）与失败收敛的**可观测面**，供宿主感知并据此执行状态机操作。

## 6. 异常态处置

| 异常 | 状态 | 处置 |
|---|---|---|
| 任务需澄清 | `needs_input` | 引擎自动置入；用户给出澄清后，宿主以 `advance(to=executing, answer=…)` 并入原节点消息、重新派发，继续 DAG |
| 任务失败（业务失败） | **不进本表**（Feature 保持 `executing`） | 只冻结依赖闭包下游 + 收敛静止（见 §2 表「任务失败」行与 §4 二分判据）；`failed` 仅 DAG 非法专用（见 §1 口径注） |
| 用户取消 | `cancelled` | 任意非终态经 `cancel` 终止 |

> **负向注（v0.6.1 REQ-05 起）**：**失败收敛不进入本表任何一行**（不转 `needs_input`、不转 `failed`）—— 业务失败**不是异常态**：Feature 停在主链 `executing` **静止**（零动作、等宿主），账单经事件 `feature.failure_report` + `a2a_feature_status`（可选 `text` / `contextId`）承载。本表与 §2 表同口径，不存在第二套说法。（episode 口径见 §4）

## 7. 三方驱动边界

| 角色 | 该做 | 不该做 |
|---|---|---|
| **宿主（LLM）** | 组织各项目分析、汇总方案、把方案拆成 DAG、判断何时推进、执行状态机操作 | 不逐条派活、不自己轮询、不催办 |
| **引擎（代码）** | 按 `dependencies` 拓扑派发（并行/串行的资源约束由运行底座决定）、等待终态、续约、失败传播（= 冻结依赖闭包）、`executing → integrating` 自动流转（全 `completed` 时） | 不判断方案好坏、不替用户拍板、不猜澄清内容 |
| **用户** | 过两道确认门、答澄清、收结果 | 不必逐步催下一环 |

> **可观测语义（v0.7.1 REQ-01 起）**：宿主在**需动作三时点**——完成（Feature 离开 `executing` 进 `integrating`）· 失败收敛静止（**保持 `executing` 静止**）· 需澄清（`needs_input`）——经**运行底座（代码组件）给出的可观测信号**被感知，并据此执行状态机操作；**等待由运行底座（代码组件）承担，不靠人工提醒**，**LLM 不执行等待与轮询**；终态（`cancelled` / `failed`（DAG 非法））与 `timeout` **不属**需动作三时点。

边界一旦清楚，流程就不依赖"宿主记得住纪律"，而是依赖"状态机拒绝非法流转"。

## 8. 前瞻解耦（写规范时必须遵守）

本文件的写法与三件事**解耦**，使未来演进**不改本规范**：

| 维度 | 现在 | 未来 | 本文件怎么写 |
|---|---|---|---|
| 操作面 | MCP 工具 | 网页服务（v0.8 / v0.9） | 门禁只写成**状态机操作**（`advance` / `approve` / `answer`），**不写死"调用某工具"**。网页与 MCP 是同一状态机的两个驱动口，网页**不得**成为第二编排入口 |
| 项目来源 | 各机自持，宿主经发现拿到 | orch 期望态 / 远程项目（v0.6.0） | 只写「派发到某项目」，**不描述"项目从哪来"** |
| Transport | Launcher + A2A | Runner 反向注册 pull（v0.7.0 修订；SSH 已废弃） | **不描述传输**，规范只谈状态与派发语义 |

一句话：规范描述**状态机语义**，实现细节（工具名、项目发现、传输）留给运行底座。这样换操作面、换项目来源、换传输，流程规范都不用改。
