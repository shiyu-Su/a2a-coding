# 引擎映射

> 本文件属于**流程规范包内核**，与同目录 [`需求流程.md`](./需求流程.md) 配套：前者定义 Step 0-3 的判据与产出物，本文件定义同一套流程如何落到 Feature 引擎的状态机上。
> **项目无关**：不绑定任何具体仓库、项目或宿主实现。

## 1. 核心命题

需求流程的每一步，都对应 Feature 状态机上的一个状态；每次状态推进，都有**唯一确定的驱动方**（宿主 / 用户 / 引擎自身）。宿主不再"逐步派活 + 轮询催办"，而是**在关键点做状态机操作**，其余交给引擎。

**为什么必须引擎化**：stdio MCP 是**拉模型**，callback 无法唤醒宿主会话。因此"宿主逐条 `a2a_call` + 自己轮询"会把整条需求的进度**绑死在 LLM 会话**上：宿主一停，任务即停；宿主一长，上下文即爆。**引擎驱动是让任务在宿主不参与时继续推进的唯一方式**。

**状态机速览**（v0.4.1 REQ-04 收敛后）：

- **主链（6 态）**：`waiting_approval → executing → integrating → testing → reviewing → completed`
- **异常态（3）**：`needs_input` / `failed` / `cancelled`
- **终态（3）**：`completed` / `failed` / `cancelled`

> **口径注（v0.6.1 REQ-05 起）**：`failed` 语义**收窄**为 **DAG 非法（环 / 悬空）fail-fast 专用** —— **业务失败不再产出 Feature `failed` 终态**（Feature 停在 `executing` 静止，见 §4 二分判据）；`blocked` 是**良性终态**，**不计入「全完成」**。上述「异常态 / 终态」均就 **Feature 级**而言：**节点 `failed` 可经重派复活**（见 §5 `retryTaskIds`），Feature 不因业务失败进入终态。

**引擎只做「需求实现」**：主链起点 = `waiting_approval`（= Step 1 产出→门的停靠点）；`approve` 是**唯一准入**（`advance(to="executing")` 被拒，错误码 `feature_approval_required`）。`executing → integrating` 是**引擎自动**（**全部节点 `completed`**；收敛且存在失败 ⇒ **不转移**，见 §4 二分判据）；`integrating → testing → reviewing → completed` 由**宿主 `advance`**。

## 2. 步骤 ↔ Feature 状态 ↔ 驱动方

| 流程步骤 | Feature 状态 | 驱动方 |
|---|---|---|
| Step 0 需求访谈 → 需求确认单 | **（引擎不参与）** | 宿主（+ 用户确认）；产出物按流程落文件 |
| 【确认需求内容】 | **（引擎不参与）** | **用户确认**（凭据 = 需求确认单落文件；不再有状态机流转） |
| Step 1 评估 + 改造文档 | **（引擎不参与）** | 宿主（+ 各单元本侧评估/边界确认） |
| 【确认改造文档】 | `waiting_approval → executing` | **用户 `a2a_feature_approve`**（**唯一准入**；宿主在收到确认后立即调用） |
| **Step 2 需求实现** | `executing` | **引擎自动**（拓扑派发（并行/串行的资源约束由运行底座决定）· 等待 · 失败传播=冻结依赖闭包）+ 宿主**一次性**登记 DAG（**同轮把 DAG 清单贴给用户**） |
| Step 3 测试 / 反馈 → 通过 | `integrating → testing → reviewing → completed` | **宿主 `advance`** |
| 任务需澄清 | ` → needs_input` | **引擎自动**（任务 `input-required`） |
| 任务失败 | `executing`（**不离开**，非转移） | **引擎自动**（仅冻结**依赖闭包**下游：未派发者置 `blocked`、**在飞不动**；无可派发且无在飞且存在失败 ⇒ **保持 `executing` 静止**，账单经事件 `feature.failure_report` + `a2a_feature_status`（可选 `text` / `contextId`）） |

> **Step 2 的起点**：宿主在方案确认后 `a2a_feature_create`（初态即 `waiting_approval`）→ 登记 DAG 节点 → `a2a_feature_approve` 放行 ⇒ 引擎接管。

读法：一张需求 = 一个 Feature；一行 = 一次状态变更（或一次**非转移操作**，如「任务失败」停在 `executing`）；「驱动方」列即该变更的**发起者**。Step 1 内部三态连推（`analyzing → planning → waiting_approval`）与 Step 3 内部三态连推，均由宿主 `advance`，中途不必停。

## 3. 两道确认门的挂载

流程里**只有两个用户介入点**，两者都显式挂到状态机，不是散落在正文里的"人工约定"：

| 门 | 语义 | 挂载方式 |
|---|---|---|
| **需求确认门** | 「我理解你要解决的是不是这个问题」 | **不在状态机上**：凭据 = `doc/{版本}/{topic}-需求确认单.md` **落文件** + **用户确认**（前置：宿主持有**相关执行单元的事实核实**）。v0.4.1 REQ-04 起，Step 0/1 **引擎不参与** |
| **改造文档确认门** | 「方案经用户确认后才开始实现」 | **唯一准入 = `approve`**：`waiting_approval → executing`。**语义**：**记录已发生的用户确认（一对一映射：不可预领、不可补领）** —— 宿主在收到用户确认后**立即**调用，**不是新增一次用户决策**；**禁止**在用户未确认方案前调用。**前置**：各相关执行单元已确认**接受该边界且无重复改造**（多轮收敛，≤3 轮未达成则升级用户）。未 `approve` 前调度器停在等待点，不派发任何执行任务；且 **`advance(to="executing")` 被拒**（`feature_approval_required`） |

> 两个门把「流程纪律」变成「状态机约束」：不是靠宿主自觉，而是**未过门则推进被拒**（非法流转 fail-fast）。

## 4. Step 2 行为改写（本次核心）

**原**：宿主拆子任务 → 逐条 `a2a_call` 派发 → 自己记依赖 / 轮询 / 催办。进度随 LLM 会话走，宿主必须全程在线。

**新**：宿主**一次性**把改造方案落为 Feature DAG：

1. `a2a_feature_create(...)` 建 Feature，拿到 `featureId`；
2. 对每个任务节点调 `a2a_call(project, message, featureId, dependencies, inputs?)` **登记**（不立即派发）；
3. 用户在改造文档确认门 `approve` 后，**由调度器按 `dependencies` 拓扑派发（并行/串行的资源约束由运行底座决定）并自动推进**：就绪即派、等终态，推进判据为**二分** —— **全部节点 `completed`** ⇒ **自动** `executing → integrating`（不停、不交）；**收敛且存在失败**（无可派发 && 无在飞 && 存在失败 / 冻结）⇒ **不转移**：失败只冻结**依赖闭包**下游（未派发者置 `blocked`、**在飞不动**）、其余照跑，Feature **停在 `executing` 零动作**（= 静止，等宿主）。
   **关键措辞**：静止**不是状态转移**（停在主链 `executing`、不进入任何异常态）；**`blocked` 是良性终态、不计入「全完成」**（否则会把「冻结」误当成「全达终态」而错进 `integrating`）。

宿主在 Step 2 保留的编排职责**只剩两件**：**拆 DAG**（把方案切成有依赖关系的节点）、**判断何时 advance**（引擎停在 `needs_input`（澄清）或 `executing` 静止（失败收敛）时）。等待、轮询、续约、失败判定、状态推进全部由**代码组件**承担，LLM 不参与。**重派分两路、边界在节点集合**：**（i）重派既有失败节点** = `advance(..., retryTaskIds)`（重放 Feature 内已 `failed` 节点并解冻其被冻结下游 —— **不新增节点、Feature 态不变**）；**（ii）新增业务节点** = `a2a_call(mode="execute", featureId=…)` 登记（现成通道，不变）。二者不互相替代。

> **默认形态（2026-09-15 定）**：**自 v0.4.1 之后的新需求起，Step 2 默认采用本节的 Feature DAG 形态**。仅在特殊情形（如该需求本身正在改造调度引擎，用旧引擎跑会命中待修的失败传播）才可退化为逐步 `a2a_call` 派发，且**必须在改造文档 / planlog 中注明理由与降级路径**（v0.4.1 的 REQ-03 即属此例外）。

## 5. 工具面

工具面为「**泛型工具 7 + Feature 工具组 5**」，静态注册、零重连：

- 泛型 7：`a2a_projects` / `a2a_call` / `a2a_task_status` / `a2a_tasks` / `a2a_cancel` / `a2a_events` / `a2a_wait`
- Feature 5：`a2a_feature_create` / `a2a_feature_status` / `a2a_feature_advance` / `a2a_feature_approve` / `a2a_feature_cancel`

用法要点：

- `a2a_call(project, message, contextId?, wait?, mode, featureId?)`：`mode` **必填** ——
  - `mode="inquiry"`（**不得带 `featureId`**）：只读询问/核实/调研 ⇒ **立即派发**，与既有行为一致；
  - `mode="execute"`（**必带 `featureId`**）：执行型派发 ⇒ **登记**该 Feature 的队列节点，由调度器按 `dependencies` 拓扑派发。
  - 对偶校验错误码：`feature_required_for_execute` / `feature_not_allowed_for_inquiry`。
- `a2a_feature_advance(featureId, to, note?, answer?, retryTaskIds?)`：推进主链，状态机校验合法后继；**`to="executing"` 在 `waiting_approval` 被拒**（请用 `approve`）；`answer` 用于 `needs_input` 补齐后续推。`retryTaskIds?`：**仅用于失败重派**（重派指定 `failed` 节点并解冻其被冻结下游）；**空集合 / 任一 id 非法 / 与 `answer` 同传 ⇒ 拒绝**（结构化错误、Feature 态不变）；`answer` 仍**仅**承载 `input-required` 澄清。
- `a2a_feature_approve(featureId)`：唯一审批门，`waiting_approval → executing`。
- 任务结果与 Feature 态均落库，宿主可随时 `a2a_feature_status` / `a2a_tasks` 找回。

## 6. 异常态处置

| 异常 | 状态 | 处置 |
|---|---|---|
| 任务需澄清 | `needs_input` | 引擎自动置入；用户给出澄清后，宿主以 `advance(to=executing, answer=…)` 并入原节点消息、重新派发，继续 DAG |
| 任务失败（业务失败） | **不进本表**（Feature 保持 `executing`） | 只冻结依赖闭包下游 + 收敛静止（见 §2 表「任务失败」行与 §4 二分判据）；`failed` 仅 DAG 非法专用（见 §1 口径注） |
| 用户取消 | `cancelled` | 任意非终态经 `cancel` 终止 |

> **负向注（v0.6.1 REQ-05 起）**：**失败收敛不进入本表任何一行**（不转 `needs_input`、不转 `failed`）—— 业务失败**不是异常态**：Feature 停在主链 `executing` **静止**（零动作、等宿主），账单经事件 `feature.failure_report` + `a2a_feature_status`（可选 `text` / `contextId`）承载。本表与 §2 表同口径，不存在第二套说法。

## 7. 三方驱动边界

| 角色 | 该做 | 不该做 |
|---|---|---|
| **宿主（LLM）** | 组织各项目分析、汇总方案、把方案拆成 DAG、判断何时推进、执行状态机操作 | 不逐条派活、不自己轮询、不催办 |
| **引擎（代码）** | 按 `dependencies` 拓扑派发（并行/串行的资源约束由运行底座决定）、等待终态、续约、失败传播（= 冻结依赖闭包）、`executing → integrating` 自动流转（全 `completed` 时） | 不判断方案好坏、不替用户拍板、不猜澄清内容 |
| **用户** | 过两道确认门、答澄清、收结果 | 不必逐步催下一环 |

边界一旦清楚，流程就不依赖"宿主记得住纪律"，而是依赖"状态机拒绝非法流转"。

## 8. 前瞻解耦（写规范时必须遵守）

本文件的写法与三件事**解耦**，使未来演进**不改本规范**：

| 维度 | 现在 | 未来 | 本文件怎么写 |
|---|---|---|---|
| 操作面 | MCP 工具 | 网页服务（v0.8 / v0.9） | 门禁只写成**状态机操作**（`advance` / `approve` / `answer`），**不写死"调用某工具"**。网页与 MCP 是同一状态机的两个驱动口，网页**不得**成为第二编排入口 |
| 项目来源 | 各机自持，宿主经发现拿到 | orch 期望态 / 远程项目（v0.6.0） | 只写「派发到某项目」，**不描述"项目从哪来"** |
| Transport | Launcher + A2A | + SSH 等（v0.6.0） | **不描述传输**，规范只谈状态与派发语义 |

一句话：规范描述**状态机语义**，实现细节（工具名、项目发现、传输）留给运行底座。这样换操作面、换项目来源、换传输，流程规范都不用改。
